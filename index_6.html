Picking an ecommerce platform is really a decision about which layers you want to own: the storefront, the catalog and order logic, the payment flow, and the hosting underneath. Every platform below draws that line in a different place. If you have already settled the front-end question with a comparison like SitePoint's Astro vs Next.js guide, the next question is what sits behind it. Prices are from each vendor's pricing page as of November 2026.

Shopify is the fully managed option. Basic costs $29 a month with card rates from 2.9% plus 30 cents, and a 2% fee applies to orders processed through a third-party gateway on that plan. Developers get two routes: Liquid themes, or Hydrogen, Shopify's headless toolkit, where your framework owns routing and rendering and Hydrogen supplies the Storefront API client and cart. Templates exist for React Router on Oxygen and for Next.js on Vercel. Plus starts at $2,300 a month.

Whop is a business platform for taking payments and sending payouts, and it sits under a storefront you have already built rather than replacing it. The Checkout element runs in the browser with no server code and no API key on the page. You pass your own order ID as metadata, Whop copies it onto the payment, and your server fulfills from a signed webhook that follows the Standard Webhooks spec. Domestic cards cost 2.7% plus 30 cents with no monthly fee, buyers see payment methods chosen by their location across 195 countries, and the same balance pays out in over 200 countries, including to affiliates or sellers you onboard. Whop's own guide shows how to integrate a checkout API into a Next.js storefront end to end. The trade-off is that there is no catalog or shipping engine; you collect address fields at checkout and trigger fulfillment from the webhook.

WooCommerce is a free plugin on WordPress you host yourself, so you own updates, security, and performance. Its payment gateway, WooPayments, charges US merchants 2.9% plus 30 cents per card transaction, 1.5% more for international cards, 2% for currency conversion, and $25 per dispute. Everything is PHP hooks and filters, which makes it the natural pick for agencies already living in WordPress and the wrong pick for anyone who does not want to run a server.

BigCommerce hosts the back end and lets you bring any front end. Core is $29 a month billed annually, capped at $30,000 in trailing annual sales, and plans auto-upgrade as volume grows. There are no platform fees when you use an embedded payment provider, and a 2% fee on Core if you use another one. Catalyst, its reference storefront, is built on Next.js, React Server Components, and the Storefront GraphQL API, and deploys to Vercel.

Medusa is an open-source commerce framework in Node.js and TypeScript, with an MIT-licensed core and a commercial enterprise edition. SitePoint covered it when it was still a young Shopify alternative; it now has over 37,000 GitHub stars. Self-hosting is free. Medusa Cloud starts at $29 a month for development, $99 for launch, and $299 for scale, with no percentage of sales, and the company says you can export your data and self-host at any point.

Saleor is a GraphQL-native, API-only commerce platform written in Python and released under the BSD-3 license. Self-hosting is free. Saleor Cloud starts at $1,599 a month for up to $200,000 in monthly sales, with 0.8% on orders above that, and $3,999 a month at the next tier. It is built for teams with a dedicated engineering function and a large catalog, which is exactly who should pay that price.

Own only the storefront, and Shopify or BigCommerce will carry the rest. Own everything, and Medusa or Saleor give you a back end you can read. Already on WordPress, and WooCommerce is the obvious fit. Already have a storefront in Next.js or Astro and only need the money to move, and Whop is the shortest path. Whichever you pick, the checkout is where disputes start, so log what SitePoint's friendly fraud guide for developers recommends from day one.

#10400. Your SSL certificates can now last 200 days at most: The real risk isn’t renewal

Stay up to date with AI tools, model releases, and developer workflows that matter.

Every SSL certificate comes with a limited lifespan. Following the latest update from the CA/Browser Forum, the maximum lifetime of a certificate has fallen from 398 days to 200, and it will drop to 100 days in March 2027 and 47 days in 2029. Renewal is no longer an annual chore. It’s an ongoing task that only stays manageable with automation.

So what does this mean if you already look after sites with SSL certificates, and will it bring drastic changes? For many setups, very little will change. For others, one missed renewal can mean an outage. This article explains what’s changing and what to do if you’re in the second group.

Today, an SSL certificate is valid for 200 days at most. The limit applies when a certificate is issued, so the ones you already hold keep their original expiration date.

Where you feel it depends on how your certificates renew. Sites on managed hosting platforms or behind a content delivery network (CDN) usually renew automatically already, often every 90 days, so the new limit changes little. The pressure lands on setups where someone buys a certificate once a year and installs it by hand. At 47 days, that becomes about 12 renewals a year.

A certificate is a promise from a certificate authority that a key really belongs to a domain, and that promise gets less reliable the longer it runs. If a private key leaks, or a certificate is issued by mistake, it stays usable until it expires. Cutting the lifetime shrinks that window, so a problem that once lingered for over a year is now fixed in weeks.

Shorter lifetimes also make revocation, the process for canceling a bad certificate, far less critical. Revocation has never worked perfectly, but a certificate that expires within weeks matters much less if a cancellation doesn’t reach every browser.

Another reason is about people. A task done once a year is easy to forget and hard to check from outside. Browser makers have pushed for years to move the industry onto automatic renewal, on the logic that a process that runs every few weeks gets tested constantly. If it breaks, you notice quickly instead of discovering it on the day the certificate expires.

For most people, the first effect is simply more work. A certificate that once needed attention every year will soon need it every few weeks. Plus, each renewal is a small chance for something to go wrong. Multiply that by dozens of sites, mail servers, and devices, and the chance of one slipping through grows quickly.

The safety nets are also thinner. If you relied on the renewal emails, nothing is watching your certificates now. Additionally, with a shorter life, there’s less time between this should have renewed and this has expired.

An expired certificate doesn’t make a site slow or dated. It makes it unreachable for most visitors. Chrome, Firefox, and Safari all show a full-page warning that the connection isn’t private, and most people leave instead of clicking through. If the site uses HSTS, a setting that tells browsers to connect only over secure links, there is often no way to click through at all, and visitors are blocked outright until the certificate is fixed.

The damage doesn’t stop at the home page. Checkouts, contact forms, and logins that depend on the secure connection fail along with it, often without an error message that points at the real cause. Other systems break, too, because apps and integrations that call your site over a secure link refuse to connect to an expired certificate.

Nothing about your site has to change for any of this to happen. A date passes, and a site that worked on Friday is down on Monday. In a 47-day lifetime, that date comes around about every six weeks.

What closes that gap is a check that never relies on your server’s own account of events. Site24x7’s SSL/TLS certificate monitoring does exactly that. It reads the certificate installed on your web server from the cloud, the way a visitor’s browser would, and alerts you before it expires, using thresholds you choose. If a renewal fails quietly, you hear about it from the monitor and not from a customer.

For each certificate, it records the issuing authority, the owner, the issue date, the expiration date, and the days remaining, including on servers that host several certificates behind one address. That last number matters more as lifespans shrink. When a certificate lasts 47 days, the days left is the figure that tells you a renewal is overdue, and you can set your warning against it using the quarter-of-the-lifetime rule covered next.

Once a monitor is watching your certificates, the next question is when it should speak up.

Most expiration alerts are set to a fixed number of days: warn at 30 days left and escalate at seven. That works for a certificate that lasts a year and renews with a month to spare. It breaks when the whole certificate lasts for a limited number of days.

Here’s why: a healthy certificate renews with about a third of its life still left. If your alert appears earlier than that, it goes off on certificates that are doing nothing wrong, and soon everyone ignores it. As lifespans shrink, a fixed 30-day alert will start doing exactly that.

The fix is to set the alerts based on lateness, not on how close the expiry date is. Warn when a quarter of the lifetime is left, since a renewal is overdue by then, and escalate when a tenth is left. Because these are shares of the lifetime, they keep working, however short lifespans get.

#10393. Logging AI Prompts and Responses in Java Without Leaking Sensitive Data

Stay up to date with AI tools, model releases, and developer workflows that matter.

Picture this. A customer writes to your support chatbot: "Hi, I'm Asha, my card ending 4111 was charged twice, call me on 98400 12345." Your Java service wraps that message in a prompt, sends it to a model, and logs the whole thing so you can debug it later. Congratulations, you now have a customer's name, phone number and card details sitting in a plain text log file that half the engineering team can open.

This happens more often than people admit. Logging AI calls is genuinely useful, but prompts and responses are some of the most personal text your application ever touches. Here's how to keep the usefulness and drop the risk.

A regular web request is easy to log: URL, status code, time taken. AI calls are messier.

The output changes from run to run. If a user says "your bot gave me a wrong answer yesterday", the only proof of what happened is what you sent and what came back at that moment. You can't just replay it and expect the same result.

Prompts are also built, not typed. The final text is usually a template, a few retrieved document chunks, some chat history and the user's message stitched together. When something looks off, the bug could be in any of those pieces, and only the assembled prompt shows you which one.

Then there's cost. You pay by the token, so without per-call records you can't say which feature is burning money. And quality drifts over time as models get upgraded and templates get edited. Old logs are your only baseline.

So yes, you need these logs. The real question is what goes into them.

Before writing any masking code, agree on what counts as sensitive. In most business apps that means:

Names, emails, phone numbers and home addresses

Card numbers, bank details and government ID numbers

Health, legal or job-related details people mention in free text

Internal material like contract wording, pricing rules or source code

The first three groups follow patterns, so they're easy to catch. The last two don't, and that's where most teams get caught out. Keep that in mind, because it shapes the design below.

The safest sensitive value is the one that never reaches the log. So split what you record into two buckets.

The first is metadata: a request ID, a hashed user or tenant ID, model name, prompt template name and version, token counts, latency, retry count, error type and estimated cost. None of this is personal, and it answers most day-to-day questions.

The second is content, meaning the actual prompt and response text. You only need this when you're investigating quality, and even then you rarely need all of it. A sensible default is to log metadata for every call and masked content for a small sample, maybe five percent, plus every failed call.

Here's a mistake that's easy to make: letting the log appender clean things up afterwards. By then the raw text may already be in a buffer, an async queue or a crash dump. Mask first, then log.

The cleanest way is one small component that every AI log call has to pass through:

public interface PiiMasker {     String mask(String input); }

Nothing else is allowed to write raw prompts. One chokepoint is much easier to review and test than masking sprinkled across fifty classes.

For structured data like emails, cards and tokens, regular expressions do the job well:

public class RegexPiiMasker implements PiiMasker {     private static final Map RULES = new LinkedHashMap<>();     static {         RULES.put(Pattern.compile("[A-Za-z0-9.%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}"), "[EMAIL]");         RULES.put(Pattern.compile("\b(?:\d[ -]?){13,19}\b"), "[CARD]");         RULES.put(Pattern.compile("\b(?:\+?\d{1,3}[ -]?)?\d{10}\b"), "[PHONE]");         RULES.put(Pattern.compile("(?i)bearer\s+[A-Za-z0-9.~+/=-]+"), "Bearer [TOKEN]");     }     @Override     public String mask(String input) {         if (input == null || input.isBlank()) return input;         String result = input;         for (var rule : RULES.entrySet()) {             result = rule.getKey().matcher(result).replaceAll(rule.getValue());         }         return result;     } }

A few small choices matter here. The patterns are compiled once, not on every call. The order is fixed, because a card number can otherwise get half eaten by the phone rule. And the replacement labels such as [EMAIL] keep the sentence readable, so whoever debugs it later can still follow what the user was asking.

Regex won't catch a name like "Asha Raman" or an address buried mid-sentence. For those you have a few options, and they work best together.

You can run a named-entity recognition model that tags people, places and organisations, then mask anything above a confidence threshold. You can do exact replacement of values you already know, such as the customer's name from the current session. Or, best of all, you can mask at the field level while building the prompt. If your code knows that customer.getEmail() is going into the template, swap in a placeholder right there instead of trying to spot it afterwards. Knowing beats guessing every time.

Plain redaction can remove too much. If the same email shows up five times in a conversation, five identical [EMAIL] tags hide the fact that it was one person.

The fix is consistent pseudonyms. Turn each real value into a short token using a keyed hash, so the same email always becomes something like EMAIL_7f3a. You can still follow the thread, but nobody can read the original from the log. Use an HMAC with a secret from your secrets manager. A plain unkeyed hash of a phone number can be brute-forced in minutes, because there just aren't that many phone numbers.

One warning: if you also store a lookup table to reverse the tokens, that table is now sensitive data too. Most teams are better off with one-way tokens.

Free-text log lines are hard to search and easy to leak through. Write one JSON record per AI call with clearly separate fields:

log.info("ai_call",     kv("requestId", requestId),     kv("model", model),     kv("promptVersion", "support-reply-v4"),     kv("inputTokens", usage.inputTokens()),     kv("outputTokens", usage.outputTokens()),     kv("latencyMs", elapsed),     kv("promptMasked", masker.mask(prompt)),     kv("responseMasked", masker.mask(response)));

Now dashboards for cost and latency never need to touch the text fields at all. You can also keep the two kinds of data for different lengths of time: metadata for a year, masked content for a couple of weeks. Put the request ID into your logging framework's MDC so every line belonging to one call, including retries and tool calls, carries the same ID.

Streaming trips people up. Tokens arrive in tiny pieces, and a card number can be split across two chunks, which means masking each chunk on its own will miss it. Collect the full response in a buffer, mask it once the stream ends, and log that. If the stream dies halfway, run the partial buffer through the same masker.

Tool calls are the other trap. When the model calls one of your Java methods, the arguments and return values are often the most sensitive thing in the whole exchange: order details, account balances, addresses. Treat them as part of the prompt and response. Log the tool name, duration and outcome by default, and log arguments only after masking.

Masking lowers the risk but never removes it, so surround it with some ordinary discipline:

Give content fields a short retention period. Old prompt archives are liabilities.

Limit who can read AI logs. Debugging a model doesn't mean someone needs to read customer messages.

Encrypt log storage and the pipeline that feeds it.

Log the hashed user ID so you can find and delete one person's records when they ask.

Allow verbose logging in development with fake data, and enforce strict settings in production through configuration, not through people remembering.

A masker that quietly stops working is worse than having none, because everyone assumes the logs are clean. Write tests for it:

@Test void masksEmailAndCardNumber() {     String raw = "Contact me at asha@example.com, card 4111 1111 1111 1111";     String safe = new RegexPiiMasker().mask(raw);     assertFalse(safe.contains("asha@example.com"));     assertFalse(safe.contains("4111"));     assertTrue(safe.contains("[EMAIL]"));     assertTrue(safe.contains("[CARD]")); }

Build a small set of messy, realistic samples: numbers with odd spacing, mixed languages, addresses inside sentences, text pasted from spreadsheets. Run them in your CI pipeline, and add a new case every time a leak turns up. A scheduled job that scans stored logs for patterns that should never appear makes a good safety net too.

A few I'd watch for. Logging raw text at debug level and assuming production never enables it; debug flags get switched on during incidents, so mask at every level. Masking only the user's message while forgetting retrieved documents, system prompts and tool results. Letting SDK exceptions carry the full request body into the logs. Leaving wire-level HTTP logging on in production, which bypasses your masker completely. And treating masking as finished once it ships, when every new prompt template can bring new kinds of data.

Every AI call writes a structured metadata record with a request ID

All prompt and response text goes through a single masker first

Streams are masked after assembly, and tool arguments are masked too

Content logging is sampled, short-lived and access-controlled

Tests cover the masker, with a regression case for every past leak

Client libraries aren't dumping raw payloads into the logs

Good logs turn an AI feature from a black box into something you can actually debug, price and improve. The same logs can also expose the people who trusted you with their details. The way through is fairly plain: record metadata for every call, push all content through one well-tested masker, use pseudonyms when you need to follow a conversation, handle streams and tools carefully, and keep retention short. Set that up before launch, not after the first incident, and you get visibility without regret.

Most large-model training runs as Single Program, Multiple Data (SPMD) programs. Every accelerator runs the same program in lockstep and coordinates through collectives like AllReduce.

It works well when your job is the same program running on every device. It struggles when the job is no longer uniform, like a pipeline whose stages wait on each other or an RL loop where a sampler, a reward model, and a trainer are different programs that have to overlap.

Large runs also have to survive hardware failures, which interrupted Gemini 2.5 training multiple times per hour. In SPMD, one lost machine stops every process and sends the run back to its last checkpoint. In each case, the challenge is coordination. You have to decide what runs where and in what order, how tensors move between devices, and how the job keeps going when a machine drops out.

By the end, you'll know where SPMD is suboptimal, what single-controller execution changes, and how Pathways coordinates a whole training job across a cluster.

If you train PyTorch models, you almost certainly use Distributed Data Parallel (DDP) or Fully Sharded Data Parallel (FSDP). DDP runs a copy of your script on every accelerator and averages gradients with a collective operation such as AllReduce. FSDP shards parameters, gradients, and optimizer states across workers so that the model fits at all.

DDP and FSDP both follow the Single Program, Multiple Data (SPMD) execution model. Every process runs the same copy of your script, owns its accelerators for the whole run, and moves in lockstep with the others, because the only way they coordinate is through collectives like AllReduce. Inside one tightly connected group of accelerators those collectives run over a fast interconnect and are cheap. Scale the job across groups and the same collectives cross the datacenter network, which is far slower. On a TPU v5p, for example, each chip gets 1,200 GB/s of bidirectional chip-to-chip bandwidth inside its group, but only 50 Gb/s (gigabits, about 6 GB/s) to the datacenter network which is roughly two orders of magnitude less.

And because every step blocks on its collectives, that communication lands directly in step time. The more groups you span, the larger the share of each step spent moving data, so throughput grows slower than the number of accelerators you add.

As long as your training job is one program that fills the hardware you give it, this execution model fits well. You write your model as if there were one device, and the collectives do the rest. But fitting a model into memory is only part of the problem. Keeping every accelerator busy is the harder part, and this is where the SPMD model starts to show its limits.

Take pipeline parallelism as an example. You split a model into blocks across devices, and each device now runs different code over smaller micro-batches. Activations flow forward, activation gradients flow back, and while device 0 works on the first micro-batch, devices 1 and 2 wait. Apart from the idle accelerators you keep paying for, this drops utilization and throughput, even though every device has work in the steady state.

Another example is RL post-training for an LLM. You have a sampler that generates rollouts, a reward model that scores them, and a trainer that updates the policy and sends the new weights back to the sampler. These are three different programs that should overlap; otherwise the sampler is idle while the trainer runs, and the trainer is idle while the sampler generates.

In both scenarios, the job is now several different programs running on different devices, and their dependencies can no longer be managed through a single collective. You now have to coordinate which devices share which tensors, which processes run while others are still finishing, and how early to enqueue the next buffer so an accelerator never waits for input. Because each worker only has visibility into its local devices and data, no individual process can manage all of these dependencies itself. That has several consequences.

First, because each process owns its accelerators for the whole run and every collective blocks until all devices finish, one failed machine prevents the collective from completing and stops the entire job, forcing a restart from the last checkpoint. You cannot add devices mid-run, and you cannot give devices back.

Second, because each process holds its accelerators from start to finish, capacity can't move to where it's needed. Within one job, a stage that needs fewer chips than another still keeps the extra ones. They sit idle, you keep paying for them, and no other part of the job can use them until the run ends. Across a team, the same happens at cluster scale. Every job owns its accelerators for as long as it runs, so sharing a cluster means splitting it into per-job allocations, and each new job brings up its own processes on its own hosts.

Finally, the development process itself gets harder. On one host you iterate fast because you run the script, drop into a Python shell, set a breakpoint, and debug. This is not true once the job spans many hosts. You need a launcher to push your script to every host, you hit coordination bugs that never showed up on one machine, and there's no single process to break into. When something hangs, each worker is stuck at a collective waiting for the others, with no one place that shows the whole job.

So the common challenge here is the coordination itself. As soon as the job stops being one program in lockstep, you have to decide what runs where, in what order, and how tensors get from one device to the next.

One way to describe this is as a graph, where each block is a node, each tensor that moves between blocks is an edge, and the devices are where the nodes are placed. You can wire that graph up by hand in SPMD, one process at a time. But what if a single client declared that graph, including what each block does, what it needs, and where it runs, and a distributed runtime handled the transfers, dependencies, and ordering along its edges?

That is the idea behind Pathways, the distributed system Google built to train its own largest models, including Gemini. Pathways runs JAX programs on TPUs and it is available on Google Cloud.

With Pathways, you define the end-to-end computation from a single Python client, without writing custom coordination code, and a distributed runtime executes it. That client is decoupled from the hardware. It runs on an ordinary CPU machine and you write your program against virtual devices; a resource manager maps them onto real chips, and a worker on each accelerator host runs the compiled programs it receives.

Because your code refers to virtual devices rather than physical ones, the runtime is flexible to allow users to change the devices used for a given computation. This allows you to stay in control while the runtime handles the mapping to hardware. In an RL loop, for example, the trainer and the samplers rarely want the same number of chips, so you can give the sampler stage more chips by asking for more virtual devices.

Also, the same capability helps when a host fails or the hardware isn't ready yet. If a host dies, the resource manager remaps the work onto healthy chips and the run keeps going instead of relaunching the whole job, which is the basis for elastic training. And because the program targets virtual devices, compilation can start before the physical chips are provisioned, so setup overlaps with provisioning instead of waiting on it.

The resource manager owning the chips also means one Pathways cluster can serve several clients, so researchers on a team can share its capacity. With the Shared Pathways Service, the cluster stays up as a long running service, which lets you develop interactively on TPUs hosted on GKE. Each client connects on demand from a laptop or VM, gets its own slices (groups of tightly connected TPU chips) from the shared pool, and hands them back when it disconnects. When every chip is busy, the next workload waits until capacity frees up.

Take the three-block model from Figure 2. Block A runs on one group of devices, block B on a second, block C on a third. You declare what each block computes, its target devices, and where its outputs go. Pathways expresses those dependencies as a distributed dataflow graph, in which each block is a compiled SPMD program and each edge is a tensor the runtime has to deliver.

In a single SPMD program, the framework handles the collectives that keep the devices in sync within a group, with or without Pathways, and your code doesn't change. The difference shows up once the job runs several programs on different groups (Multiple Programs, Multiple Data, MPMD), like these three blocks or the sampler, reward model, and trainer of an RL loop. Then no single process sees both sides (the same limit from before, where each worker only knows its own devices), so getting a tensor from block A to block B is a hand-off you have to coordinate yourself.

Pathways closes that gap. You declare the dependency once, and the runtime moves and reshards the tensor for you, over the fast interconnect within a group and over the datacenter network between groups.

To keep the accelerators busy, Pathways prepares launches ahead of time with futures and parallel asynchronous dispatch. While block A is still computing, block B can't run yet, but its input shapes and dtypes are already known, so the runtime allocates B's buffers and schedules the transfer before A's output even exists. Host-side setup for every block happens up front, and each block launches when its inputs arrive.

This is also what keeps the single client from becoming a bottleneck. Because dispatch is asynchronous, the coordination work overlaps with the compute already running on the chips, so the client stays off the critical path instead of stalling the accelerators between steps.

In Pathways, the runtime decides execution order when a group has more than one operation ready. In pipelined training, B's devices often hold both the forward pass for an upcoming micro-batch and the backward pass for an earlier one. If each device picked on its own, their collectives would conflict and the group would stall.

Pathways has a central scheduler that puts every program's operations into one consistent order, so operations that must communicate start together instead of deadlocking.

And because it's still one client, the development loop we mentioned before comes back. It's the same single Python process whether you drive one host or thousands of hosts, so you can drop into a shell, set a breakpoint, and inspect the run as it goes. When something stalls, there's one place that knows what's queued on every device and which dependency hasn't been met, instead of a hang spread across separate processes.

Put together, Pathways separates model building from execution. You choose how the model partitions across hardware using the client. And the runtime handles the transfers, ordering, and scheduling that keep accelerators busy, across the whole cluster rather than just your slice of it.

Described this way, Pathways can start to sound like an orchestrator you already know. If scheduling work, moving tensors, and keeping a whole cluster busy brings Ray to mind, it should. But the two work at different layers.

Ray is an open-source framework for orchestrating Python-native AI workloads across large clusters. It provisions the cluster, schedules your Python code as tasks and actors, and launches your workload across hosts, holding data loading, training, serving, and tuning under one control plane. To Ray, an accelerator is a resource to schedule.

What Ray doesn't change is how your training runs on the chips. The job inside each worker still runs as SPMD. The framework inserts the collectives, and each process sees only its own devices. Ray places and starts that job but it doesn't turn it into a single program that drives the whole cluster.

That is the layer Pathways works at. It changes the execution model underneath, so one client coordinates every chip. Because they sit at different layers, the two are complementary. In principle, Ray can orchestrate the cluster and the pipeline while Pathways handles how the training step executes.

So concretely, Ray's job is about orchestration while Pathways' job is about execution. With Ray, you tie your data, training, serving, and tuning together and spread heterogeneous work across accelerators and clouds. With Pathways, you run one model across many groups of chips, express patterns beyond SPMD, and recover from a failed host instead of relaunching the whole job.

When a training job stops being one uniform program, the challenge becomes coordinating the dependencies between stages, the tensors that cross the network, and the ordering that keeps every accelerator fed.

SPMD requires you to address these dependencies. With Pathways, you describe the computation once, from a single client, as a graph of blocks and the tensors between them. And you have a runtime that places the blocks on virtual devices, moves and reshards the tensors, orders the work across the cluster, and remaps around a failed host.

With Pathways, model building and execution are separated and you reason about the whole cluster instead of one slice of it.

It is a workflow that converts inquiries from different channels into a shared data model, preserves their acquisition context, and connects them to business outcomes. Forms and calls keep their own interaction records, while contacts and opportunities provide the relationships needed for reporting.

Sometimes. Dynamic number insertion can provide a session or visitor association when the provider's mapping is available and valid. You can begin with PostgreSQL and an outbox worker if that setup meets your throughput and latency needs. #10363. Announcing Long-Context Training on TPUs with MaxText Context Parallelism

Long-context training — including pretraining and post-training, has become a foundation of frontier AI models. Longer native sequence lengths give large language models (LLMs) the working memory to read a whole code repository or ingest hours of video, and reason through multi-step agentic tasks. In three years, context windows have grown from 128K–200K tokens to 1M–2M, and models trained toward 10M tokens are arriving. Training at those lengths, not just serving them, is where the system limits show up.

In particular, efficient training at multi-million-token sequence lengths runs into the following bottlenecks:

Today, we are excited to announce long-context training support in MaxText, Google Cloud's open-source JAX training framework. MaxText enables this by supporting four context-parallel strategies on Cloud TPU: All-gather, A2A (DeepSpeed Ulysses), P2P (Ring Attention), and the A2A + P2P hybrid (Unified Sequence Parallelism, or USP), combined with load balancing and sequence packing. All four use the Tokamax Splash Attention kernel. Combined with the 3D inter-chip interconnect (ICI) ( supported on TPUs such as TPU 5p or TPU 7 (Ironwood) ), this lets one sequence span an entire slice while communication overlaps compute and memory per chip stays flat. In our benchmarks, Llama 3.1 8B (25 head dim, 16 query heads) demonstrates exceptional long-context efficiency, achieving 70% Model FLOPs Utilization (MFU) on TPU 5p for sequence lengths up to 4 million tokens. Across both TPU 5p and TPU 7, context can be seamlessly extended to 14 million tokens—with TPU 7 consistently maintaining 50% MFU across all sequence scales below 6 million tokens.

This functionality is available today in MaxText v0.2.4(doc).

Context parallelism splits a long sequence across chips, so no chip holds the activations of the whole sequence. Context parallelism can be combined with data and tensor parallelism, and the smallest context-parallel size that fits your sequence in HBM is usually the right one. This also holds for sparser attention variants which cut attention compute but not the activations of every other layer.

Attention is the one global operation where every token needs the keys and values of every preceding token, so each context parallel strategy has to bring those keys and values back together. Each makes a different tradeoff between memory (how much KV a chip holds), communication (how much moves per layer, and whether it overlaps compute), and model shape (how many attention heads to split).

All-gather: Each chip keeps its chunk of the sequence and, at every layer, gathers the keys and values from every other chip. It is the simplest option. However, because causal masking causes later tokens to attend to larger prefixes, All-gather requires balancing compute load across devices.

All-to-All (Ulysses): Gathering keys and values makes every chip hold the whole sequence, so attention memory never shrinks no matter how many chips you add. The ideal UI testing tool is the one that discovers what your users discover first: broken layouts, usability issues that no longer work, and new accessibility issues in all the browsers your users use before a change goes into the repository. Most "best UI testing tool" lists rank test runners and visual testing platforms against each other as if they were interchangeable. They aren't. UI testing covers four distinct jobs:

Functional testing: Does the UI respond correctly when a user clicks, types, or hovers?

Visual testing: Does the UI still look right across layout, color, typography, and spacing?

#10347. Build Live Video Chat With WebRTC: From First Call to Production Debugging

Stay up to date with AI tools, model releases, and developer workflows that matter.

Adding real-time video to a web app used to mean plugins, proprietary SDKs and a lot of money. Today every modern browser ships with WebRTC, a set of APIs that lets two browsers exchange audio, video and data directly. The catch is that WebRTC gives you building blocks, not a finished feature. This guide walks through those blocks in the order you actually need them, with the exact API calls you need, and then covers the production issues that tutorials usually skip.

A browser-to-browser call has four moving parts:

Start with the local preview. Browsers only allow camera access on HTTPS or localhost, so serve your page accordingly.

1.     Request a stream with navigator.mediaDevices.getUserMedia(), passing video constraints (an ideal width of 1280 and height of 720 is a sensible default) and audio constraints with echoCancellation and noiseSuppression enabled.

2.     Assign the returned MediaStream to the srcObject property of your local video element.

3.     Keep a reference to the stream, because you will add its tracks to the peer connection later.

Set the muted and playsinline attributes on the local video element. Without muted users hear themselves, and without playsinline iOS Safari opens the video full screen.

The peers need a way to find each other. A tiny Node.js server using the ws package is enough for development. Its whole job is to relay messages between the peers in a room:

1.     Create a WebSocket server (for example with the ws package) listening on its own port.

2.     Keep a map of room names to the set of sockets in each room.

3.     When a client sends a join message, store the room name on the socket and add it to that room's set.

4.     For every other message type, forward the raw message to the other sockets in the same room, and never echo it back to the sender.

5.     On disconnect, remove the socket from its room so stale peers do not receive messages.

In production you would add authentication, limit room size to two for one-to-one calls, and validate message types, but the shape stays the same.

Both sides create an RTCPeerConnection, add their local tracks and listen for the remote ones:

1.     Create a new RTCPeerConnection with an iceServers list that contains at least one STUN server.

2.     Loop over the local stream's tracks and call addTrack() for each one.

3.     In the ontrack handler, attach the first remote stream to your remote video element.

4.     In the onicecandidate handler, send every new candidate to the other peer through your signalling channel as a candidate message.

One peer creates an offer, the other answers, and both apply each other's descriptions. Candidates arrive asynchronously in the background.

1.     The caller runs createOffer(), applies it with setLocalDescription() and sends the description as an offer message.

2.     The callee applies the offer with setRemoteDescription(), runs createAnswer(), applies it locally and sends it back as an answer.

3.     The caller applies the answer with setRemoteDescription().

4.     Both sides pass every incoming candidate message to addIceCandidate().

If both peers might start a call at the same time, look up the "perfect negotiation" pattern on MDN. It assigns one side as polite and resolves offer collisions cleanly instead of leaving both peers stuck.

On a home network, STUN alone often works. On corporate Wi-Fi, mobile carriers and symmetric NATs it frequently does not, and the call silently fails to connect. A TURN server relays media when a direct path is impossible. The open-source coturn server is the usual choice.

In practice, your iceServers list should contain your own STUN URL plus a TURN URL with a username and credential, so the browser can fall back to the relay automatically when direct connectivity fails.

Generate short-lived TURN credentials on your backend rather than hard-coding them, and budget for bandwidth: relayed calls pass every frame through your server.

Users deny camera access, unplug headsets and switch from Wi-Fi to 4G mid-call. Catch NotAllowedError and show a clear explanation, listen for devicechange events, and use RTCRtpSender.replaceTrack() to swap cameras without renegotiating the whole call.

Listen to pc.onconnectionstatechange. When the state becomes disconnected, wait a few seconds before giving up, because it often recovers. On failed, call pc.restartIce() to try new network paths.

Use RTCRtpSender.setParameters() to cap the bitrate on weak connections, and read pc.getStats() to monitor packet loss and round-trip time. Showing a small "poor connection" indicator does more for perceived quality than any codec tweak.

Mesh calls, where every participant connects to every other, work for two or three people. Beyond that, upload bandwidth explodes. Group calls need a Selective Forwarding Unit (SFU) such as mediasoup, LiveKit or Janus, which receives each stream once and forwards it to the others.

Tutorials end at a working demo, but the fastest way to understand what production WebRTC looks like is to watch a real call from the inside. Chrome ships an internal diagnostics page that shows every peer connection the browser opens, and it works on any site that uses WebRTC.

1.     Open chrome://webrtc-internals in one tab and keep it open.

2.     In another tab, start a call on your own demo and find its RTCPeerConnection entry.

3.     Expand that entry and look at the ICE candidate pairs: you will see whether the call went direct (host or srflx) or through a TURN relay (relay).

4.     Open the stats graphs for the outbound video stream and watch the bitrate, frame rate and resolution adapt when you throttle the network in DevTools.

5.     Check the negotiated codec and how quickly the connection recovers when you switch Wi-Fi off and back on.

Once you can read your own call, repeat the exercise on a production service. Any browser-based product works, whether a meeting tool or a live video chat that pairs two visitors, because webrtc-internals shows the same data for every site. Expect differences from your demo: more candidate pairs, a relay candidate in the list and a bitrate that adapts faster. Seeing them makes the earlier sections concrete, from why TURN matters to how bandwidth estimation reacts to packet loss.

The one-to-one call above is the core of many products, from telehealth consultations and tutoring to customer support. The engineering challenges grow with the use case: random matching needs queueing and presence on the signalling server, public platforms need moderation and reporting, and global audiences need TURN servers in several regions.

Start with the minimal version, get it working across Chrome, Firefox and Safari on both desktop and mobile, and add TURN before real users arrive. Once the call is reliable, every other feature becomes a much easier problem.

#10313. How Agent Anomaly Detection scores on benchmarks we didn't write

AI agents now read email, book travel and move money for the people who use them. Every tool call also pulls in text that someone else wrote, and whoever controls that text can try to steer the agent. In September we announced Agent Anomaly Detection in Private Preview on Gemini Enterprise Agent Platform. It reads your agents' traces and logs asynchronously, without adding latency, and flags sessions where an agent acts outside its intended boundaries. We tested this feature against benchmarks for this top risk of agent goal hijack.

Security tools tend to look good on tests their own team wrote, so we ran five non-Google-written, public agent-security benchmarks through Agent Anomaly Detection without changing anything. In four of them, the harmful instruction hides in data that a tool returns. In the fifth, the user asks for harm directly.

The model itself didn't follow about half of the harmful instructions it read. It refused three in four direct requests for harm, and ignored or failed at about 30% of the instructions hidden in tool output. Of the ones that were executed, Agent Anomaly Detection flagged 87% for post-execution review. It raised false alarms on 2% to 16% of benign sessions, depending on the tools the agent uses. Poisoned memory is the clear gap: when instructions planted in the agent’s long-term memory made it act, Agent Anomaly Detection caught 4 of 18.

We ran each benchmark case through an agent built with the Agent Development Kit (ADK) using gemini-2.5-flash, on the benchmark's simulated apps. The agent sent its traces and logs to Agent Anomaly Detection, as a customer's agent would. Then the benchmark's own Python check read the final state of the apps, such as whether money left the account, and labeled the session. Deterministic code decides the label, not a model, so an injected instruction can't mislead the grader, and Agent Anomaly Detection cannot cheat the benchmark. #10295. Catch Go bugs that fuzzing misses with Gemini and a constraint solver

I help lead Google's agent skills program, currently with 175 agent skills that supplement community collections like go-skills. To keep that many skill files consistent, I wrote skill-lint, a standalone Go CLI that checks SKILL.md files and applies LLM-generated line edits before they ship. Even with skill-lint's own unit and fuzz test suite, a small slice or line-number mistake inside its Markdown parsers or edit applier can sit dormant until an unusual file or edit range triggers a runtime panic in the linter.

In Go, every slice or index operation that can panic at runtime compiles down to an explicit bounds-check trap in machine code, after the compiler's optimizer strips out the checks it can already rule out. To hunt for crashes, I compiled key functions from my code to see which panic traps survived optimization, and Gemini 4 Argon translated the path to each trap into rules for the Z3 constraint solver. An LLM-written solver model isn't a sound proof system, but it gives the agent an independent way to reason about control flow and synthesize concrete Go reproducers, and every crash it finds is real because go test runs the offending bytes directly. That workflow caught all three bugs I planted in test parsers and turned up three latent bugs in skill-lint.

In this post, I'll walk through how the Gemini and Z3 pipeline works, why go test -fuzz missed two of those crashes (and the one-line change that fixes it), and where this approach fits in a day-to-day Go workflow.

A recent post from Anthropic showed how formal verification catches latent bugs in C and C++ by having frontier AI models write machine-checked Rocq proofs across OSS-Fuzz libraries. Instead of sampling random inputs like a fuzzer, a formal tool works backward from each failure condition to solve for the exact input that triggers it. Full theorem proving is still too heavy for most day-to-day Go projects, so I wanted to see how much of that bug-hunting power an agent can get from an LLM and a constraint solver in about a minute per function.

In C and C++, reading or writing past the end of a buffer corrupts memory. Go catches out-of-bounds access at runtime instead, compiling every slice or index operation it can't prove safe into an explicit branch to runtime.panicBounds that panics, crashing the process unless recovered.

Before generating machine code, Go's SSA prove pass already eliminates most of those checks by tracking slice lengths and loop variables. That optimization pass leaves behind only the runtime.panicBounds traps the compiler couldn't rule out on its own, giving the solver a short list of candidate crash sites to target.

I compiled each target with GOOS=linux GOARCH=riscv64 go build -gcflags="-S -d=ssa/check_bce/debug=1" (-S prints the assembly listing and ssa/check_bce/debug=1 logs every surviving bounds check) and passed both the Go source and the disassembly to the model. Looking at Go source alone, you can't see which bounds checks the compiler already removed or where a register gets truncated to 8 bits; in the disassembly, both show up. I targeted RISC-V because it's the instruction set Anthropic's post targets for its Rocq proofs, and Go cross-compiles to it out of the box.

From there, Argon read the Go source and disassembly and returned a Z3 script modeling the path to each surviving trap, along with a patched function whenever it flagged a bug. Z3 then checked whether those constraints could be satisfied, and whenever it found a crashing input, go test replayed those bytes against the real function. Using an LLM saved me from translating assembly into solver constraints by hand. Argon's translation dominated the runtime, at about a minute per function, while Z3 itself finished in milliseconds.

Anthropic's approach relies on interactive theorem proving, where experts model machine semantics and Rocq checks LLM-generated proofs against those rules. In contrast, my workflow uses a constraint solver based on satisfiability modulo theories (SMT), relying on Argon to translate assembly directly into Z3 constraints. While a constraint solver doesn't provide a complete correctness proof without a semantic model, it is highly effective for finding bugs. Z3's check-sat command returns sat when input constraints can be satisfied and unsat when they cannot.

A sat answer ("definitely buggy") comes with concrete bytes aimed at the trap, and go test runs them against the real function. Once go test panics, you have a concrete bug reproducer regardless of whether Argon's model was sound. Like a Bloom filter for bugs, an unsat answer only means "maybe correct." Trading away a correctness proof is what makes the approach so practical: you get most of the bug-finding value of formal methods for a tiny fraction of the effort.

Anthropic's setup proved no-crash properties on whole binaries under a 64 MB budget; I checked individual functions on fresh 64-byte slices where cap(buf) == len(buf), so any slice past len(buf) panics. (If you want the full-binary Rocq setup for Go, theorem-labs/oss-verify includes a Go 1.27 runtime overlay that makes the runtime single-threaded and deterministic.)

For the fuzzing baseline, I ran unseeded go test -fuzz on Go 1.27.3 against each planted bug: one 3-second run and three 60-second runs, each with a fresh fuzz cache so a short time budget wouldn't explain a miss.

I started with three safe parsers to make sure the pipeline didn't flag clean code. The compiler's prove pass removed every bounds check in a TOML key parser on its own, and Z3 returned unsat on the remaining traps in an HTTP header scanner and a varint decoder.

A slot is one request that the server works on at the same time as others. llama-server sets the number of slots with -np (short for --parallel), and Ollama and LM Studio pass their own setting through to it.

Turning a design image into a working webpage can look simple.

You have a picture (a mockup, a screenshot, a Figma export), and your job is to turn it into working HTML in a browser.

But here is the catch. A design image is static, while a webpage is dynamic and responsive across different screen sizes and devices. A webpage needs to load quickly, adapt perfectly to different screen sizes, and allow touch interactions on mobile devices.

Most mistakes in this process happen when the conversion is treated as copying a picture instead of rebuilding it.

This section walks you through the mistakes developers often make, and more importantly, how to fix each of them.

Whether you are slicing a client mockup or converting a screenshot into code, avoiding these mistakes can save you from hours of rework. Let’s get into the details.

A screenshot reflects how a page appears at a particular display. But it doesn’t show how the layout will behave when the content changes or the screen gets smaller.

Developers sometimes try to copy the exact positions and dimensions of every element. To match the screenshot, they may use fixed widths, large margins, and absolute positioning.

This can work at one screen size, but the layout may break on smaller screens or when a heading wraps onto an extra line.

The better approach is identifying the layout rules behind the design. CSS Grid can arrange the cards in columns. Flexbox can help align elements within each card. And media queries can adjust the layout for smaller screens.

Pixel-level comparison can be useful in some cases, but it should not come at the cost of a flexible layout.

When developers recreate a design, it’s easier for them to focus on shapes and spacing rather than the purpose of each element. So, they may use generic elements for headings, buttons, navigation areas, and content sections instead of choosing elements that reflect each element's purpose.

This may produce the right appearance, but it often makes the code harder to maintain and understand. And when developers fail to use the right HTML elements, it can also create accessibility problems later.

So don’t put everything inside several unnamed containers. Instead, use a clear structure with appropriate headings, meaningful alt text for informative images, and real buttons for actions.

Semantic elements (e.g., header, nav, main, section, and footer) can also help organize a large page when they match the content’s purpose.

So, don’t treat the image like that. Instead, use the original image where appropriate and recreate the text and button in HTML. CSS can control their position, size, color, and spacing.

Make sure you distinguish between visual elements that should remain images and text that should be recreated as HTML.

Use automation where it saves time and your own judgement where it matters.
