AI coding agents -- Copilot, Cursor, Codex, Devin, and their successors -- are now standard tooling in many engineering teams. They generate production code, shifting the developer's role from writer to reviewer. That shift exposes a specific failure mode: natural-language prompt quality does not primarily determine agent output quality. The constraints a codebase enforces at compile time and CI time determine it.

Engineers who run AI coding agents in production, including Lauren Tan (@poteto), have argued publicly that traditional codebase hygiene is the highest-leverage investment for agent correctness. The core argument: making the correct path the easiest one, through types, invariants, and architectural boundaries, beats prompt engineering or post-hoc code review. When a compiler rejects invalid code before a pull request is even opened, no amount of conversational finesse matters.

This tutorial builds a minimal, runnable repository scaffold that demonstrates four complementary guardrails: branded types that enforce domain invariants at compile time, a custom ESLint rule that catches convention violations through static analysis, a GitHub Actions CI gate that prevents non-conforming code from merging, and an AGENTS.md guidance file that provides soft contextual nudges agents can read. These layers enforce constraints at four different points between code generation and merge, and each layer reinforces the others.

AI coding agents generate code that satisfies the immediate request. They lack whole-codebase awareness of unwritten conventions, team norms, or architectural decisions that exist only in developers' heads. Without machine-enforceable constraints, an agent defaults to the loosest valid pattern. Asked to fetch a user, it will accept a raw string parameter rather than seeking out a branded UserId type. It will import the database client directly rather than routing through a service layer. The agent is not being careless. It optimizes for the shortest path to syntactically valid code.

A useful way to organize guardrails is as a hierarchy ordered by enforcement strength and feedback speed:

Each layer compounds the effectiveness of the others. Types catch the majority of structural errors. Lint rules catch convention drift that types miss. CI gates catch anything that slips past local tooling. Documentation explains the why behind constraints, helping agents make better choices in ambiguous situations.

Consider a common function signature: function getUser(id: string). That parameter accepts any string. An email address, a raw UUID, an order ID, an empty string. An AI agent generating a call to getUser will happily pass whatever string-shaped value is closest at hand, with no compiler objection.

Branded types solve this by intersecting a base type with a unique symbol tag, creating a compile-time-only distinction between structurally identical types. A UserId and an OrderId are both strings at runtime, but the compiler treats them as incompatible types. The technique carries zero runtime overhead because the compiler erases the brand during compilation.

Important: Any direct cast such as "value" as UserId anywhere in the codebase bypasses the brand guarantee entirely. The TypeScript compiler will not prevent this. To enforce constructor-only creation, add an ESLint rule (e.g., @typescript-eslint/consistent-type-assertions) configured to ban as casts to branded types.

When an agent generates a call to getUser, the TypeScript compiler immediately rejects a raw string argument. The error message in the agent's context window points to the type mismatch, forcing the agent to locate or create a UserId through the createUserId constructor function, which automatically enforces format validation. The agent does not need to know the convention. The type system prevents the wrong path. Every domain identifier that uses a branded type becomes a self-documenting, self-enforcing contract that agents must satisfy to produce code that compiles.

Not every team convention belongs in a lint rule. Good candidates share a common trait: they can be detected via AST inspection and have a clear, unambiguous correct alternative. Banning direct imports from internal modules, enforcing barrel-file usage, and preventing any in specific directories are all strong fits. Rules that require judgment calls or contextual understanding are poor candidates.

This tutorial focuses on a rule that forbids importing from @/db outside the @/services directory, enforcing a service-layer boundary. Without this rule, an agent scaffolding a new HTTP handler would likely import the database client directly, bypassing the service layer and scattering data-access logic across the codebase.

When an agent's context window includes the test file, RuleTester fixtures serve as living documentation: the agent can see concrete examples of what is permitted and what is not. This doubles as both verification and guidance.

An agent scaffolding a new handler tries to query the database directly by importing from @/db. The lint step fails with: "Use a service function from @/services instead." That message points the agent toward the correct architectural pattern -- immediate, actionable, and unambiguous. The agent does not need to have read a wiki page or remembered a Slack conversation.

Agents frequently push code to feature branches and open pull requests automatically. CI must run before any human review to surface issues cheaply and quickly. The workflow follows a fail-early sequential ordering: type-check first, then lint, then test. If the type-check fails, there is no point running linting or tests on code that does not compile. Because steps in a single job are sequential, any failing step halts the job immediately.

The CI workflow alone is not sufficient. Without branch protection, a determined agent or developer can merge a pull request despite failures. In the GitHub repository settings under Branches, enable branch protection for main: require status checks to pass before merging, specifically require the guardrails job from the Agent Guardrails workflow, and disable bypass permissions for bot accounts. This combination ensures that no code reaches the default branch without satisfying every automated check. The workflow becomes a hard gate rather than an advisory signal.

Note: Some branch protection features (such as restricting bypass permissions) may require a paid GitHub plan for private repositories.

AGENTS.md is a convention for placing natural-language guidance at the repository root that agent frameworks can ingest as system-level context. Variations of this convention include CLAUDE.md for Claude Code and .cursorrules for Cursor. OpenAI Codex CLI also reads AGENTS.md from the repository root. The agents and tools that currently support reading repository-level guidance files include OpenAI Codex CLI, Claude Code, Cursor, and Windsurf. The agent framework loads the content into the agent's context window alongside the codebase when supported, making it available during code generation without requiring explicit prompting.

Agents may ignore, truncate, or misinterpret documentation. For example, Claude Code truncates files that exceed its context window limit, and instructions that work with one model version may produce different behavior after an update. AGENTS.md works best as a complement to compiler and linter enforcement, not a replacement. It fills gaps that hard enforcement cannot cover: explaining why a boundary exists, pointing to specific file paths, and providing checklists that aid both agents and human reviewers.

A practical maintenance habit: review and update AGENTS.md during sprint retrospectives. As new branded types, lint rules, or architectural boundaries are added, the guidance file must reflect them, or agents will lack the context to follow new conventions.

Hydration is the process where React, running in the browser, attaches event handlers to server-rendered HTML and reconciles that static markup with the virtual DOM tree the client would have produced. For hydration to succeed, the HTML generated on the server must match, node by node, what the client renders on its initial pass. Any divergence triggers a hydration mismatch error.

The window object does not exist in Node.js. Because localStorage is a property of window, any direct access during server-side rendering fails. Developers hit one of two failure modes. The first is a hard crash: ReferenceError: localStorage is not defined, which kills the server render entirely. In the App Router, 'use client' components still pre-render on the server during next build, so this error fires during server pre-rendering, not in the browser. The second failure mode is subtler and more common: a developer wraps the access in a typeof window !== 'undefined' guard, which avoids the crash but causes the server to render with a default value (say, 'light') while the client reads a stored value (say, 'dark') from localStorage. React detects the difference and throws a hydration mismatch warning. This exact scenario has been reported repeatedly on Stack Overflow, often confusing developers who believe the guard should be sufficient.

The root cause is straightforward but easy to overlook: the server and client disagree on initial state.

The goal here is to compare three patterns that resolve both failure modes, with honest analysis of their trade-offs.

During SSR, Next.js runs the React component tree in Node.js to produce an HTML string. Next.js sends that string to the browser, where React builds its own virtual DOM tree and diffs it against the existing server-rendered markup. If the two trees diverge in text content, attribute values, or tree structure, React logs a hydration error. In production, React 18 logs a console error and attempts DOM recovery, but visual glitches, lost state, or broken interactivity may still occur. Development mode adds additional checks and stack traces, making mismatches easier to diagnose.

Adding a typeof window !== 'undefined' guard prevents the crash, but it introduces an asymmetry. The server always falls back to 'light'. The client reads the user's stored preference, which might be 'dark'. React sees 'light' on the server and 'dark' on the client, and the mismatch fires. This is not a theoretical concern; it is the exact mechanism behind the majority of localStorage-related hydration errors in Next.js applications.

The simplest fix defers the localStorage read until after the component mounts. Server and client both render the same safe default. Once the component mounts in the browser, a useEffect reads the stored value and updates state, triggering a client-only re-render.

The server renders "Current theme: light". The client also renders "Current theme: light" during hydration, so the trees match. After mount, useEffect fires, reads 'dark' from localStorage if present, and updates the button text. Hydration succeeds.

This pattern requires zero dependencies and uses only useState and useEffect, both covered in the official React tutorial. However, it introduces a flash of the default state on first paint, typically lasting one to two frames (under 50 ms on modern hardware, but visible if it triggers a layout shift or color swap). If the user has stored 'dark', they see 'light' for that brief window before the effect runs and triggers a re-render. This FOUC is the primary downside. The pattern also causes two renders on mount: the initial hydration render and the state update from the effect.

This approach works for low-stakes preferences where a brief visual flash is acceptable, such as non-critical UI settings or feature flags that do not affect layout. It also suits prototypes and MVPs where simplicity matters more than polish.

Modern web forms often depend on JavaScript for validation, interaction, and submission. Although JavaScript makes it possible to build sophisticated interfaces, relying on it for every essential function can make a form less reliable when scripts fail, load slowly, or become unavailable.

Progressive enhancement offers a practical alternative. It starts with a functional HTML foundation, adds CSS for presentation, and introduces JavaScript to improve the user experience. This approach helps developers create interfaces that are easier to maintain, more accessible, and more resilient across different browsing conditions.

In this tutorial, we will build a simple contact form using semantic HTML, responsive CSS, and JavaScript. We will also explore how each layer contributes to a more reliable interface.

HTML should provide the essential structure and behavior of a web form before additional technologies are introduced.

Native HTML elements already support several useful features, including required fields, email validation, and keyboard interaction. Using these capabilities reduces the amount of custom code needed to build a functional interface.

Several details improve usability without requiring JavaScript.

First, every field has an associated label. This helps users understand the purpose of each input and allows assistive technologies to identify fields correctly.

Second, the required attribute prevents the browser from accepting empty fields during normal form submission. The type="email" attribute also enables basic browser-level email-format validation.

Finally, the autocomplete attributes help browsers populate familiar information, reducing repetitive typing.

The form uses a server endpoint at /contact. That endpoint must be implemented separately; the HTML alone does not process or store submissions.

A functional form should also be comfortable to use on different screen sizes. CSS can improve readability, spacing, and focus visibility without changing the underlying form behavior.

Because this demonstration uses preventDefault(), it also prevents the form's normal submission. Remove that behavior or implement the actual request before deploying the form.

Client-side validation improves convenience, but it is not a security boundary. Users can disable JavaScript, modify requests, or submit data without interacting with the form interface.

A production application should therefore validate incoming data on the server.

For example, a server handling contact requests should:

Confirm that required fields are present.

Check that field values have the expected types and formats.

Apply reasonable limits to message length and request size.

Apply appropriate spam prevention and rate limiting.

Validation should reflect the application's actual requirements. An email-format check, for example, cannot establish that an address exists or belongs to the person submitting the form.

Developers should also avoid displaying a success message before the request has completed. If the server rejects the submission or the network connection fails, the interface should communicate the problem and let the user retry without losing their input unnecessarily.

A form that works in one desktop browser is not necessarily ready for production. Testing should cover both normal interactions and failure conditions.

Keyboard navigation: Move through the fields using the keyboard and confirm that focus indicators remain visible.

Empty submissions: Leave required fields blank and verify that the browser identifies the missing information.

Invalid input: Enter an incorrectly formatted email address and check the validation response.

Small screens: Test the layout on narrow mobile viewports and confirm that controls remain readable and easy to operate.

JavaScript disabled: Confirm that the HTML form remains understandable and that native validation still works. Actual submission will require the server endpoint to support the normal HTML form request.

Server failures: Test what happens when the server returns an error or the connection is interrupted. Users should receive meaningful feedback rather than a misleading success message.

#11158. Vibe Coding to Production: A Developer’s Checklist for Building Reliable Web Apps

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

AI coding tools can turn a plain-English description into a working web application in minutes. They can generate interfaces, connect APIs, create database schemas, and help developers move from an idea to a functional prototype faster than traditional workflows often allow.

But getting an application to run is not the same as making it production-ready.

The security gap is measurable. In its 2025 GenAI Code Security Report, Veracode found that 45% of AI-generated code samples failed security tests by introducing vulnerabilities associated with the OWASP Top 10. The research evaluated generated code samples, not complete applications or confirmed cyberattacks. Nevertheless, it highlights an important risk: code that works can still be insecure.

Real-world investigations have raised similar concerns. A May 2026 WIRED investigation into exposed data in vibe-coded applications reported security and data-exposure problems in applications built using popular AI coding tools. These findings concern the applications examined, rather than every application developed with AI.

The lesson is not that vibe coding is inherently unsafe. It is that generating software quickly does not eliminate the engineering work required to protect data, verify behavior, and maintain reliability.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Consider a customer portal. An AI tool might generate a login page, a dashboard, and a database connection in a single session. The interface could look complete while the application still lacks proper authorization checks, reliable error handling, or protection against unauthorized data access.

These gaps become more consequential when an application stores personal information, processes payments, manages business records, or serves multiple customers.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Before generating substantial amounts of code, document:

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

A functional interface can conceal serious implementation problems.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Code review is therefore essential, even when an AI tool generates most of the implementation.

Start with the code responsible for important application behavior:

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

For JavaScript and TypeScript projects, automated linting and type checking can catch many common mistakes. However, these tools cannot prove that business logic is correct or that permissions are enforced properly.

When reviewing a change, ask the AI to explain its implementation and identify its assumptions. Then verify those explanations against the actual code and relevant documentation.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

Every sensitive operation should enforce the relevant permissions on the server or trusted backend.

For example, an application that allows users to view invoices should verify that the authenticated user is authorized to access the requested invoice. It should not rely solely on a user ID supplied by the browser.

Test both permitted and prohibited actions. A good security test confirms not only that the correct user can access a resource, but also that other users cannot.

For applications handling sensitive data, consider an independent security review before launch.

AI-generated applications often work well with expected inputs. Real users, however, submit incomplete forms, unexpected values, oversized files, malformed requests, and repeated actions.

Input validation and error handling help prevent these conditions from becoming application failures or security vulnerabilities.

Client-side validation improves the user experience, but it should not be the only line of defense. Requests can bypass browser validation entirely.

Validate incoming data on the server, using rules appropriate to each field and operation. Enforce database constraints where applicable, and use parameterized queries or safe ORM methods to prevent SQL injection.

For file uploads, validate file types, enforce size limits, and store files using a design that prevents unauthorized access. Do not assume a filename or content type supplied by the browser is trustworthy.

Users need understandable error messages. Developers need enough diagnostic information to investigate failures.

These requirements should be handled separately.

A user-facing response might say, "We couldn't save your changes. Please try again." An internal log can record a request identifier, the relevant operation, and a sanitized diagnostic message.

Avoid exposing stack traces, database credentials, internal configuration, access tokens, or sensitive records in production responses.

Also test what happens when external APIs time out, database connections fail, or required environment variables are missing.

A production-ready application should fail predictably, protect sensitive information, and provide a clear path to recovery.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.

Asking an AI tool to generate tests is useful, but those tests must be reviewed. A test suite can pass while validating incorrect assumptions or ignoring the application's most important failure cases.

Start with critical workflows rather than trying to test every minor interface detail.

For an e-commerce application, these workflows might include account creation, product selection, checkout, payment confirmation, and order retrieval. For a business dashboard, they might include importing records, updating a customer, assigning permissions, and generating a report.

Pay particular attention to boundary conditions.

What happens when a form is submitted twice? When an API returns an unexpected response? When a database operation fails halfway through a workflow? When two users update the same record simultaneously?

These scenarios often reveal problems that a successful demonstration will not.

For applications that process transactions, test idempotency where appropriate so that retries do not unintentionally create duplicate payments, orders, or records.

A web application can feel fast during development and become sluggish when it handles larger datasets, multiple concurrent users, or slower network connections.

AI-generated code should therefore be evaluated against realistic usage patterns.

Begin with the operations most likely to affect the user experience:

Use browser developer tools and server-side monitoring to identify actual bottlenecks before optimizing.

Database indexes can improve frequently used queries, while pagination can prevent interfaces from loading thousands of records at once. Caching can reduce repeated work when the data and consistency requirements allow it.

For public-facing websites, evaluate relevant Core Web Vitals and test performance on realistic devices and network conditions.

Avoid adding caching layers, complex abstractions, or performance libraries simply because an AI tool recommends them. Every additional component introduces maintenance costs and potential failure points.

Measure first, optimize the bottleneck, and measure again.

Generated applications frequently depend on third-party packages, API services, and environment-specific settings. Each dependency expands the application's maintenance and security responsibilities.

Before deployment, inspect the dependency manifest and lockfile. Remove unnecessary packages, verify that required packages exist, and review known vulnerabilities using appropriate dependency-scanning tools.

Keep frameworks and libraries updated according to a deliberate maintenance process rather than automatically accepting every suggested upgrade.

API keys, database passwords, signing secrets, and other credentials should not be embedded in client-side code or committed to a public repository.

Use environment variables or an appropriate secrets manager, depending on the deployment environment. Restrict credentials to the permissions they actually require, and rotate any secret that may have been exposed.

Remember that a variable included in a browser-delivered bundle is not secret simply because it was originally configured as an environment variable.

Also verify that development and production environments use the correct endpoints, database connections, authentication settings, and logging configuration.

A local application that works with unrestricted development credentials may behave very differently when deployed under production permissions.

Deployment should be a controlled process, not a final experiment performed after development is complete.

A repeatable deployment process reduces human error and helps teams identify which changes introduced a problem.

Before launch, verify that you can restore the application to a known-good state.

This includes maintaining version control, documenting deployment steps, backing up important data, and testing restoration procedures. A backup is only useful if it can be restored successfully.

Database schema changes deserve particular attention. An incompatible migration can make an otherwise successful deployment unusable. For important applications, plan migrations so that application versions can coexist safely during rollout and rollback.

Also check how the application behaves when a deployment fails, a service becomes unavailable, or a configuration change introduces a regression.

A reliable release process should make failures easier to detect, contain, and recover from.

Testing happens before release and in controlled environments. Monitoring helps developers understand how the application behaves after real users begin using it.

Without monitoring, a deployment can appear successful while users encounter failed requests, slow pages, broken integrations, or database errors.

Set alerts for failures that require action. Avoid collecting unnecessary personal data in logs, and define retention and access policies appropriate to the application.

For AI-powered features, monitor additional factors such as model response failures, latency, token usage, and output quality. An application that depends on an external AI service must account for rate limits, changing model behavior, and provider outages.

Monitoring does not prevent every failure. It makes failures visible enough to investigate and resolve.

Before releasing an AI-generated web application, use the following checklist to assess whether the essentials are in place.

Requirements: Core features, user roles, constraints, and acceptance criteria are documented.

Code quality: Important code paths have been reviewed, and unnecessary dependencies have been removed.

Authentication: Identity and session handling are implemented appropriately.

Authorization: Protected resources and operations enforce server-side permissions.

Input validation: Requests, uploads, and database operations are protected by appropriate validation and constraints.

Error handling: Failures are handled predictably without exposing sensitive information.

Testing: Critical workflows, negative cases, and regression scenarios have been tested.

Security: Dependencies, secrets, configuration, and common vulnerability risks have been reviewed.

Performance: Important queries, endpoints, and user journeys have been evaluated under realistic conditions.

Deployment: Builds and releases follow a repeatable process with appropriate quality gates.

Recovery: Backups, restoration procedures, and rollback options have been considered and tested where applicable.

Monitoring: Errors, availability, and performance can be observed after release.

Not every application needs the same level of testing or operational complexity. A personal prototype has different requirements from a financial application or a multi-tenant SaaS product.

The important thing is to identify the risks associated with the intended use and address them before exposing real users or sensitive data.

A developer does not necessarily need an external review for every small experiment. However, an independent review becomes increasingly valuable when the application handles sensitive information, processes payments, supports multiple customer organizations, or implements complex permissions.

It is also worth considering when the original developer cannot explain important parts of the generated code or when repeated AI-generated changes have made the architecture difficult to understand.

A useful review should examine more than formatting and syntax. It should evaluate application behavior, data access, authentication, security controls, error handling, deployment configuration, and maintainability.

For teams using AI to accelerate development, the goal is not to eliminate AI-generated code. It is to make sure that the resulting software meets the quality standards expected of any application entering production.

Vibe coding changes how quickly developers can move from an idea to working software. It does not remove the need to understand requirements, validate behavior, protect data, test failure scenarios, and maintain the application after release.

The most reliable approach is to treat AI as a development accelerator within a disciplined engineering process. Define the requirements, review generated code, test critical workflows, enforce security controls, automate deployment checks, and monitor the application after launch.

Start with the checklist in this article and prioritize the controls that matter most to your application's risk profile. For a deeper look at the development process, read this guide to production-ready vibe coding.

The goal is not simply to build an application quickly. It is to build one that users can trust, developers can maintain, and businesses can depend on.

Eight eMudhra intermediate Certificate Authority private keys are trivially recoverable from their public certificates. Any attacker can mint trusted TLS certificates for arbitrary domains. Browsers have already blocked these compromised intermediates through revocation mechanisms, but most non-browser runtimes — curl, Python, Node.js, Go, and Rust — still silently trust them. This affects any team operating server-side infrastructure, CI pipelines, or CLI tooling that makes outbound TLS connections. If your stack trusts the eMudhra chain, an attacker can forge certificates your code will accept without complaint.

This guide provides a diagnostic sequence: test every runtime in the stack against the compromised certificates, remediate by updating trust stores, and verify the fix sticks. The primary source for this disclosure is Scott Helme's detailed writeup.

In RSA key generation, you derive the private exponent d via the modular inverse of the public exponent e modulo λ(n) (the Carmichael totient of the modulus), where λ(n) depends on the prime factors of n. RSA's security depends entirely on d being large — typically hundreds of digits — making it computationally infeasible to derive from the public key alone.

eMudhra generated eight intermediate CA certificates with single-byte d values. Specific recovered values include d=4, d=56, and d=115, as documented in Scott Helme's disclosure post. These are not large numbers. They are recoverable from the public certificate in milliseconds. Anyone with access to the public certificate (which is, by definition, public) can reconstruct the private key and sign certificates that chain up to eMudhra's trusted root. That means arbitrary TLS certificates for any domain, indistinguishable from legitimate ones to any client that trusts the eMudhra chain.

An attacker holding one of these recovered keys can issue a certificate for any hostname, and any TLS client trusting the eMudhra intermediate will accept it without complaint.

Chrome pushed a CRLSet update blocking the intermediates the same evening, Mozilla blocked them in Firefox via OneCRL within hours, Apple applied its platform block on October 19, and Microsoft rolled out a disallowed-certificate CTL update. Current browser versions already reject the compromised intermediates.

The problem lies everywhere else. Non-browser TLS clients skip revocation checks by default. curl does not check CRLs or OCSP unless explicitly configured to do so. Python's requests and urllib3 libraries rely on the certifi bundle and perform no revocation checking. Python's standard library urllib.request module uses the system SSL store, not certifi. Node.js's https module uses either a compiled-in root store or the system store depending on build configuration, with no active revocation. Go's crypto/tls loads system roots but does not perform revocation checks. Rust's rustls paired with webpki-roots uses a bundled Mozilla root set, while native-tls defers to the system store; neither checks revocation by default.

This creates a trust store gap. The system CA bundle on a Linux server, the certifi bundle shipped with Python, and the compiled-in roots in Node.js might all still contain the eMudhra intermediates or trust the root that chains to them. Without manual intervention, these runtimes remain vulnerable.

Every frontend developer will eventually stare at a CORS error in the browser console, watching an API call fail for reasons that seem opaque. A CORS error fix requires understanding what the browser is actually telling you, matching that specific message to its root cause, and applying a targeted, security-conscious server configuration.

The scheme, host, and port together define an "origin." https://example.com and http://example.com are different origins (different schemes), as are https://example.com and https://api.example.com (different hosts). https://example.com and https://example.com:443 are the same origin because port 443 is the default for HTTPS, and browsers omit it in origin comparisons. The browser enforces the same-origin policy on client-side JavaScript reading responses, not on sending requests. This distinction trips up many developers: the server may still receive and fully process the request; the browser simply refuses to expose the response to the calling code. The request lands, the database row gets written, and the browser throws an error anyway. The policy exists to prevent a malicious page from silently reading sensitive data from another origin using the user's ambient credentials.

Cross-Origin Resource Sharing (CORS) is a controlled opt-in mechanism via HTTP response headers. The server signals to the browser that a specific foreign origin is permitted to read its responses. Four headers control the mechanism: Access-Control-Allow-Origin specifies which origin is allowed, and Access-Control-Allow-Methods declares which HTTP methods are permitted. Access-Control-Allow-Headers lists which custom or non-simple headers the client may send, while Access-Control-Allow-Credentials indicates whether the browser should expose the response to credentialed requests.

The browser does not treat all cross-origin requests equally. "Simple" requests use GET, HEAD, or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data, or text/plain, and no custom headers. A POST with Content-Type: application/json is not a simple request and triggers a preflight.

Simple requests go directly to the server, and the browser evaluates the CORS headers on the response. Anything else triggers a preflight request: an OPTIONS call the browser sends automatically before the actual request, asking the server whether the real request would be acceptable. If the OPTIONS response lacks the proper CORS headers, the browser never sends the real request at all.

A typical Chrome DevTools error reads: Access to fetch at 'https://api.example.com/data' from origin 'https://app.example.com' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two origins appear in this message. The URL after "fetch at" is the target server, the resource the code tried to reach. The value after "from origin" is the page's own origin, the one making the request. Chrome is stating that the target server's response did not include an Access-Control-Allow-Origin header that matches the requesting origin, so the browser blocked the response from reaching JavaScript.

The most common variant is the missing header: No 'Access-Control-Allow-Origin' header is present on the requested resource. The server simply did not include the header at all.

When the console says Response to preflight request doesn't pass access control check, the server either did not respond to the OPTIONS request correctly or returned a non-2xx status code for it.

Redirect variant: Redirect is not allowed for a preflight request. Developers commonly misdiagnose this one. It occurs when the URL triggers a redirect before reaching the application handler. Typical culprits include HTTP-to-HTTPS upgrades, trailing-slash normalization (e.g., /api/data redirecting to /api/data/), or a load balancer rewriting URLs. The browser's preflight OPTIONS request follows the redirect, and the Fetch specification (§4.8) forbids following redirects on preflight requests, so the entire flow fails. Fix the URL so no redirect occurs.

Credential variant: The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'. When fetch is called with credentials: 'include' or XMLHttpRequest sets withCredentials = true, the server must respond with the exact requesting origin, not *. The browser will block JavaScript access to the response if a wildcard is used with credentials.

Use an explicit origin allowlist. Avoid * when credentials are involved; the browser will block JavaScript access to the response if a wildcard is used with credentials: 'include'.

Restrict Access-Control-Allow-Methods to only the methods the API actually uses. Listing every HTTP method widens the attack surface unnecessarily.

Set Access-Control-Max-Age to cache preflight responses. Chrome caps this value at 7200 seconds (2 hours); Firefox honors up to 86400 (24 hours). Use 7200 as a safe cross-browser default, or 86400 if your users are primarily on Firefox and you want fewer preflight round-trips.

Include Vary: Origin on every response where Access-Control-Allow-Origin is set conditionally. Without it, CDN or proxy caches may serve a CORS response cached for one origin to a different origin, causing intermittent failures.

Never mirror the request Origin header back without validating it against an allowlist. This is an open CORS misconfiguration that effectively disables the same-origin policy for any attacker-controlled origin.

Do not install browser extensions that disable CORS either -- they mask the problem during development and expose you to real cross-origin attacks on every other site you visit.

Avoid adding CORS headers in both the application framework and Nginx simultaneously. Duplicate Access-Control-Allow-Origin headers cause the browser's CORS origin comparison to fail; the browser receives the response but blocks JavaScript from reading it, producing the same CORS error the fix was meant to resolve.

#11037. AI Agents Need Idempotency: The Distributed Systems Problem Hiding Inside Agentic AI

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

A customer wants a $480 refund for a faulty part of a shipment he received. After waiting for 30 seconds for the payment API to process the refund, the customer support AI sends another request. It ultimately is fulfilled. However, as it turns out, the first request had also been fulfilled. The only thing missing was the notification of the refund for the customer. So the customer received two refunds of $480 each instead of the one he was asking for.

The AI was acting appropriately within its given constraints; the surrounding system couldn’t tell if the initial action had already been taken and failed to deliver the result. A well-known problem in distributed systems is gaining more notoriety as AI-powered agents increasingly perform actions beyond simply generating text. Idempotence is the solution to this problem.

Idempotence means an action can be performed multiple times with the same result as performing it once. This concept is particularly important for an AI agent that issues refunds, creates tickets, sends emails, or updates business applications.

AI agents as distributed software components have simple processes.

Think → choose a tool → call an API → receive a result → decide what to do next.

As we have outlined, many of the agent actions will utilize services and networks that can have issues from time to time. Consider the simple action of asking a payment provider to issue a refund. There are three possible outcomes:

The payment service never gets the request.

The refund went through, and the agent got the answer.

The refund went through, but the agent never received it back.

The most severe case, however, is when the time to complete an operation exceeds the timeout, but the operation does complete successfully. Since there is no answer, the software agent never learns of the operation's successful completion and must attempt to complete the operation again.

Distributed systems have dealt with the issues of unreliable networks for a long time already (retries, duplicate requests, etc.). By introducing agents, we give the software more freedom to choose when and how to proceed.

Consider an agent with these tools: search_customer(), check_inventory(), refund_payment(), send_email(), create_order(), delete_account()

Calling search_customer() twice will usually not cause much trouble.

In other words, an agent runtime should be able to tell if a tool only gets data or makes changes to the outside world. In the second group are things like sending money, getting money back, placing orders, writing messages, making accounts, and changing infrastructure.

There are side effects to these treatments. It's risky to think that agents can just retry every failed tool call as they get access to more business systems.

One common way to handle the duplicate requests issue is to implement idempotency keys.

Idempotency-Key: refund-order-123-run-842

The service stores the idempotency key and the result of processing the associated request.

It allows the refund to be processed the first time the idempotency key is sent to the service by the agent. Thereafter, if the response to the refund is lost and the agent attempts to resubmit the refund with the same idempotency key, the service will recognize that the refund has already been processed and return the previous result to the agent instead of processing another refund.

Many of the world’s leading payment companies, including Stripe, PayPal, and Square, use idempotency keys to allow their customers to safely retry requests.

However, one important rule for agents is that the agent software or workflow system—not the AI model—creates the idempotency key, and it is up to date.

By the time the model retries the same step, the Operation ID will have remained the same. This means the system can recognize the request as another attempt to execute the same action as before and not a new action.

Things could be easy if we could tell the model to ‘remember if it has already issued one of these before issuing another.' But even in the production environment, this approach is not sufficient. The agent could crash. The context could go away. The workflow could be taken off to be executed on another machine. The problem is that the model lacks sufficient information about what has or has not happened in external systems. Instead, the system should keep a record of the execution state outside of the model. The model determines what should happen. The runtime determines safe execution.

Modern agent tools include a name, description, and input parameters for the production system. More importantly, the agent runtime also needs to know about the behavior of the individual tool. For example, ‘refund_order’ modifies the application outside this tool, so the operation must be re-executed with the same actionID used for the initial failure. Also, as an example, refunds larger than $5,000 require manual approval. On the other hand, a ‘search_customer’ action is only a read, so re-execution can occur without human intervention. Based on this information, the OS makes decisions about the danger of the individual tool call. Automatic re-execution is still possible, even if the search fails. However, refunds require a bit more caution to avoid double posting of money. Thus, in addition to the input models for the AI tools used in real life, so-called “execution rules” are also required. These rules state when re-execution, increased security, or human intervention is required.

Suppose an AI agent were to perform the following three actions: 1) Make whole the customer, 2) Send a confirmation email with the order update and a proof, and 3) Check the status of the order in process. We had described how stopping the AI from paying out twice was only half the problem; the system also needed to know where the work had stopped. To that end, we’d like to introduce the concept of durable execution. For durable execution, the agent must do more than simply remember the actions it has taken. We need to keep track of the progress of the actions of the AI. The refund action was marked complete, but the email action was not sent yet. Thus, when the agent is restarted, it continues from where it left off rather than starting over. To create reliable AI agents, we need a few things: stable operation IDs, irrevocable actions, durable state, controlled retries, and logging. There are also cases where one wants to perform a recovery or compensating action (e.g., the agent makes a reservation but then fails to perform the subsequent action). The recovery action would be to cancel the reservation that had been made.

While controls with a person in the loop are mostly suitable for fine-grained actions that cannot be undone, idempotence ensures that an action is not accidentally executed more than once, and human approval is required to decide whether the action should be executed in the first place. This point is illustrated by an example: An employee correctly approves a $10,000 refund. However, the payment request somehow times out and is automatically re-executed several times. Without adequate idempotency security, the customer might end up with even more refunds than intended. Note, however, that a person’s approval cannot prevent double killing in such high-risk agent processes. Therefore, additional decision controls and corresponding execution controls are usually required to ensure that all actions are executed safely and correctly.

There are 5 simple questions that need to be answered before allowing an AI agent to take real-world actions.

Improving the model alone will not make the agent reliable unless we can answer all of these questions.

Much work in AI today focuses on making agents smarter, better at planning, and better to use as tools. But running agents in production has its own problems. API calls time out, processes crash, networks fail, and responses get lost, and the smartest agent can try again and again until it works. These are not new problems. Engineers working on distributed systems have been struggling with these same issues for decades. So long as the AI agent is confined to a simple test environment, of course it can query payment systems, customer information, and corporate tools. But when it is turned loose on the production corporation’s infrastructure (with all the payment systems, customer information, and corporate tools that entails), it must also be reliable. A smart model can figure out that a customer is due a refund. But a strong system can only give that customer a refund once. So the important question to ask of an AI agent before turning loose on it is, "Some powerful new tool: what happens if the action worked?" The answer will tell you whether or not the AI agent is currently able to operate reliably in production.

#11025. Web-Ready AI Images: Formats, Sizes, and srcset Done Right

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

AI image generation has become a normal part of many web projects. However, the image a model produces is rarely the image a browser should receive. A single large PNG straight from a generator can weigh several megabytes, ignore the visitor's screen size, and slow down your Largest Contentful Paint (LCP) before the page has a chance to impress anyone.

The good news is that the fix is not complicated. If you treat the generated image as a high-quality master file and run it through a small, repeatable pipeline, you can ship images that look sharp on every device and load quickly on slow connections.

This tutorial walks through that pipeline from start to finish: generating at the right size and aspect ratio, choosing modern formats, creating responsive variants with Node.js, writing srcset and sizes correctly, and avoiding the performance mistakes that show up most often in audits.

Image generators are built to produce visually impressive results, not optimized web assets. Their output is usually a single file at one resolution, often in PNG format, and sometimes with an aspect ratio that does not match your layout.

Sending that file directly to the browser creates three problems. First, mobile visitors download far more pixels than their screens can display. Second, PNG is a poor choice for photographic images because its lossless compression produces large files. Third, without width and height information, the browser cannot reserve space for the image, which causes layout shifts as the page loads.

A web pipeline solves all three. You generate one master image, export multiple sizes in modern formats, and let the browser choose the best version for each visitor.

Optimization starts before you export anything. The most efficient pipeline begins with an image that already fits your layout.

Look at where the image will appear and note its aspect ratio at each breakpoint. A full-width hero might use 16:9 on desktop, while a blog thumbnail might use 4:3 or 1:1. Then identify the largest size the image will ever display. For a full-width hero, that could be 1920 pixels wide on large screens, or more if you support high-density displays at wide viewports.

Your master image should be at least as large as that maximum rendered width. Upscaling a small image later almost always introduces blurriness or artifacts.

Modern image-generation models can follow detailed instructions, so describe the technical requirements in your prompt, not just the subject. Specify the aspect ratio, intended display size, visual style, and any areas that need to remain clear for HTML text. The exact controls available will depend on the tool you use, so check its official documentation before building a workflow around a particular feature.

A practical web-focused prompt might read: "hero image of a modern home office at sunrise, soft natural light, calm blue and warm wood tones, clear empty space on the left third for headline text, no text or logos in the image."

That last instruction matters. Avoid baking headlines or buttons into images. Text inside an image cannot be translated, resized for accessibility, or indexed reliably, and it often becomes unreadable at small sizes. Keep text in HTML and use the image for visuals only.

Once you have a master file, decide which formats to serve. For most photographic and illustrative AI images, a combination of AVIF, WebP, and JPEG covers every modern browser while keeping file sizes small.

AVIF typically offers the strongest compression for photographic content and is supported by all major modern browsers, including Safari 16 and later. WebP is slightly less efficient but encodes faster and has near-universal support. JPEG remains a reliable fallback for older browsers and email clients.

Use PNG only when you specifically need lossless quality, such as for sharp-edged graphics or screenshots. Both AVIF and WebP support transparency, so you rarely need PNG for images with transparent backgrounds anymore.

Creating a dozen versions of every image by hand is tedious and error-prone. Instead, script the process. The Sharp documentation explains how to resize images and export them in different formats.

Then create a script that exports several widths in each format:

const widths = [480, 768, 1080, 1440, 1920];

{ ext: 'avif', format: 'avif', options: { quality: 50 } },

{ ext: 'webp', format: 'webp', options: { quality: 75 } },

{ ext: 'jpg', format: 'jpeg', options: { quality: 80, mozjpeg: true } },

for (const { ext, format, options } of formats) {

.resize({ width, withoutEnlargement: true })

Save the file as an ES module, such as build-images.mjs, and run it with Node. The withoutEnlargement option prevents sharp from upscaling the master when a target width is larger than the original.

The quality values above are reasonable starting points, not universal rules. AVIF and WebP quality scales do not map directly to JPEG quality, so compare outputs visually at the sizes your users will actually see. Smooth gradients, which are common in AI-generated skies and backgrounds, are especially prone to banding at aggressive settings.

The MDN responsive images guide explains how srcset and sizes work. The srcset attribute lists available image files and their intrinsic widths. The sizes attribute tells the browser how wide the image will be displayed in the layout. With both pieces of information, the browser can choose the smallest file that still looks sharp on the visitor's screen, including high-density displays.

Here is an example for an image inside an article column that is 720 pixels wide on larger screens and nearly full width on smaller ones:

alt="A modern home office at sunrise with a wooden desk and soft natural light"

The most common mistake is omitting sizes or leaving it at 100vw for images that are not full width. When that happens, the browser assumes the image fills the entire viewport and downloads a much larger file than necessary. Always match sizes to your actual CSS layout.

To offer AVIF and WebP with a JPEG fallback, wrap your image in a picture element. The browser checks each source in order and uses the first format it supports. See the MDN documentation for the picture element for the full syntax.

srcset="dist/hero-768.avif 768w, dist/hero-1440.avif 1440w, dist/hero-1920.avif 1920w"

srcset="dist/hero-768.webp 768w, dist/hero-1440.webp 1440w, dist/hero-1920.webp 1920w"

srcset="dist/hero-768.jpg 768w, dist/hero-1440.jpg 1440w, dist/hero-1920.jpg 1920w"

alt="A modern home office at sunrise with a wooden desk and soft natural light"

The img element is still required. It holds the fallback file, the dimensions, the alt text, and the loading attributes, while the source elements simply provide alternative formats.

If you need a different crop on mobile, such as a square version of a wide hero, add media attributes to your source elements. This technique is called art direction, and it is a good reason to generate or crop a separate master image for small screens rather than relying on CSS to hide important parts of a wide composition.

Always include width and height attributes on your img element. Modern browsers use them to calculate the image's aspect ratio and reserve the correct space before the file downloads, which helps prevent Cumulative Layout Shift. In CSS, set the image to width: 100% and height: auto so it scales responsively while keeping its proportions.

Use loading="lazy" for images below the fold, but never on your hero or other LCP image. Lazy loading your most important image delays it unnecessarily. Instead, add fetchpriority="high" to the LCP image so the browser downloads it early.

Write alt text that describes the image's purpose in context. If an image is purely decorative, use an empty alt attribute so screen readers skip it. Generated images do not come with meaningful descriptions, so this step always requires human judgment.

Use descriptive file names, such as home-office-sunrise-1440.avif, instead of generic names like image-final-v3.png. Clear names make assets easier to manage and give search engines a small amount of extra context.

Be aware of metadata. Some AI image providers, including OpenAI, embed C2PA provenance data that identifies an image as AI-generated. sharp strips most metadata by default, which reduces file size but also removes that provenance information. If transparency matters to your project or your client, recent versions of sharp offer a keepMetadata() method, and you can also disclose AI-generated imagery in captions or credits.

In Chrome DevTools, open the Network panel, filter by images, and resize the viewport or switch to device emulation. Reload the page and confirm that smaller files load on smaller screens. You can also select the image in the Elements panel and check its currentSrc property in the console to see which file the browser actually chose.

Then run Lighthouse or PageSpeed Insights. Look for warnings about properly sized images, modern image formats, and LCP.
