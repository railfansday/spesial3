The line between Astro and Next.js has blurred considerably. Astro added SSR, server endpoints, and hybrid rendering modes. Next.js introduced partial prerendering and static exports. Both frameworks now cover a wide enough surface area that choosing between Astro and Next.js requires more than a vague sense of which one "feels right" for a project. The wrong call early on locks a team into performance ceilings and hosting costs that are expensive to reverse — migrating routing, data-fetching patterns, and deployment pipelines typically means rewriting, not refactoring.

This guide replaces gut instinct with a structured decision matrix and side-by-side implementation patterns. The goal is to expose where each architecture genuinely excels, where it breaks down, and how to map project requirements to the right default.

Astro pages render as static HTML by default. Zero JavaScript ships to the browser unless a developer explicitly opts in. The mechanism for opting in is Astro's client:* directive system, which controls exactly when and how individual UI components hydrate. The available directives include client:load (hydrate immediately on page load), client:idle (hydrate once the browser is idle), client:visible (hydrate when the component scrolls into view), client:media (hydrate when a CSS media query matches), and client:only="react" (skip server rendering entirely; the framework name is a required argument, e.g., "react", "svelte"). Every piece of surrounding markup stays as static HTML. Critically, Astro is framework-agnostic: islands can be built in React, Svelte, Vue, Solid, or Preact, and multiple frameworks can coexist within the same project.

In the App Router, Next.js components are server-rendered by default. Client components are opted into with the "use client" directive at the top of a file. The server/client boundary is per-component, but unlike Astro's isolated islands, the entire page participates in React's unified component tree and streaming pipeline. This tight coupling to the React ecosystem means Next.js benefits from React's concurrent features, including Suspense boundaries and transitions, but it also means the framework is bound to React as the sole UI layer.

Astro treats a page as a static document with interactive widgets bolted on. The mental model is HTML-first. Next.js treats a page as a unified React component tree where the server/client split is a rendering concern. The mental model is app-first. This distinction shapes everything from default payload size to how teams reason about state, data fetching, and hydration boundaries.

Client-side routing with optimistic UI updates across multiple nested segments — think multi-step wizards with shared state spanning three or more route levels — pushes against the islands model. Next.js becomes overhead when the site is predominantly static content and the React runtime (~80-90 KB gzipped for React + ReactDOM + framework code) ships for no user-facing benefit. If the team does not use React and would need to adopt it solely for the framework, the learning curve and ecosystem lock-in are hard to justify. Additionally, Vercel-specific features such as built-in analytics and globally distributed ISR edge caching may be important, but ISR itself works on any Node.js server via next start. Next.js supports static generation, server-side rendering, ISR (Incremental Static Regeneration), partial prerendering (experimental as of Next.js 14; check release notes for current status), and an edge runtime option for middleware and select routes.

For a blog, both Astro SSG and Next.js SSG work well, but Astro ships less JavaScript. E-commerce product pages with frequently changing data pair well with Next.js ISR or Astro SSR backed by a CDN. Documentation sites get a strong out-of-the-box experience from Astro's purpose-built Starlight tool, while Next.js SSG is equally capable if the team already works in the React ecosystem.

SSR adds compute costs that static deployments avoid entirely.

If the site is content-first and interactivity is sporadic, choose Astro. If the product is an interactive web application built in React, choose Next.js. Projects that blend content with a few deeply interactive sections — search, comments, or embedded tools — can go either way: Astro with React islands or Next.js with disciplined RSC boundaries. The tiebreaker is team expertise and hosting preference.

The question is not which framework is "better." It is which default — zero JavaScript or a React component tree — matches where the project concentrates its complexity. That concentration can shift as requirements evolve. The decision matrix above is worth revisiting whenever project scope changes, a new feature pushes the interactivity ratio, or hosting constraints shift. The framework that aligns with the project's natural shape will demand the least friction over time.

Two levels of structured output support differ in what they guarantee. JSON mode, available in providers like OpenAI and Gemini, guarantees that the model emits syntactically valid JSON. It does not guarantee any particular shape. The model might return {"foo": 42} when the application expected {"sentiment": "positive", "rating": 5}. Valid JSON is not the same as correct JSON.

Schema-constrained mode goes further. It enforces a declared JSON Schema at the token-generation level: the provider guides token decoding to produce output conforming to a specific structure. Function calling (also referred to as tool calling) provides an alternative path to structured output. Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Adding an event listener to window, document, or any DOM node outside the component's own render tree requires manual cleanup. Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. Declare the handler as a named function (or a variable holding the function) inside the effect, then pass that same variable to both addEventListener and removeEventListener.

If the handler depends on a prop or state value and is defined outside the effect (for example, with useCallback), that handler must appear in the dependency array. When the reference changes, React cleans up the old listener and attaches the new one. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

Consider a search component where the user types quickly. Each keystroke triggers a new fetch. The request for "rea" might take 300ms while the request for "react" takes 50ms. The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Note that the effect function itself is not async. An inner async function is declared and called immediately. This matters because useEffect expects its return value to be either undefined or a cleanup function. React ignores a returned promise and never registers a cleanup function from it.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. AI coding agents -- Copilot, Cursor, Codex, Devin, and their successors -- are now standard tooling in many engineering teams. They generate production code, shifting the developer's role from writer to reviewer. That shift exposes a specific failure mode: natural-language prompt quality does not primarily determine agent output quality. The constraints a codebase enforces at compile time and CI time determine it.

Engineers who run AI coding agents in production, including Lauren Tan (@poteto), have argued publicly that traditional codebase hygiene is the highest-leverage investment for agent correctness. The core argument: making the correct path the easiest one, through types, invariants, and architectural boundaries, beats prompt engineering or post-hoc code review. When a compiler rejects invalid code before a pull request is even opened, no amount of conversational finesse matters.

This tutorial builds a minimal, runnable repository scaffold that demonstrates four complementary guardrails: branded types that enforce domain invariants at compile time, a custom ESLint rule that catches convention violations through static analysis, a GitHub Actions CI gate that prevents non-conforming code from merging, and an AGENTS.md guidance file that provides soft contextual nudges agents can read. These layers enforce constraints at four different points between code generation and merge, and each layer reinforces the others.

AI coding agents generate code that satisfies the immediate request. They lack whole-codebase awareness of unwritten conventions, team norms, or architectural decisions that exist only in developers' heads. Without machine-enforceable constraints, an agent defaults to the loosest valid pattern. Asked to fetch a user, it will accept a raw string parameter rather than seeking out a branded UserId type. It will import the database client directly rather than routing through a service layer. The agent is not being careless. It optimizes for the shortest path to syntactically valid code.

Each layer compounds the effectiveness of the others. Types catch the majority of structural errors. Lint rules catch convention drift that types miss. CI gates catch anything that slips past local tooling. Documentation explains the why behind constraints, helping agents make better choices in ambiguous situations.

Consider a common function signature: function getUser(id: string). That parameter accepts any string. An email address, a raw UUID, an order ID, an empty string. An AI agent generating a call to getUser will happily pass whatever string-shaped value is closest at hand, with no compiler objection.

Branded types solve this by intersecting a base type with a unique symbol tag, creating a compile-time-only distinction between structurally identical types. A UserId and an OrderId are both strings at runtime, but the compiler treats them as incompatible types. The technique carries zero runtime overhead because the compiler erases the brand during compilation.

Important: Any direct cast such as "value" as UserId anywhere in the codebase bypasses the brand guarantee entirely. The TypeScript compiler will not prevent this. To enforce constructor-only creation, add an ESLint rule (e.g., @typescript-eslint/consistent-type-assertions) configured to ban as casts to branded types.

When an agent generates a call to getUser, the TypeScript compiler immediately rejects a raw string argument. The error message in the agent's context window points to the type mismatch, forcing the agent to locate or create a UserId through the createUserId constructor function, which automatically enforces format validation. The agent does not need to know the convention. The type system prevents the wrong path. Every domain identifier that uses a branded type becomes a self-documenting, self-enforcing contract that agents must satisfy to produce code that compiles.

Not every team convention belongs in a lint rule. Good candidates share a common trait: they can be detected via AST inspection and have a clear, unambiguous correct alternative. Banning direct imports from internal modules, enforcing barrel-file usage, and preventing any in specific directories are all strong fits. Rules that require judgment calls or contextual understanding are poor candidates.

This tutorial focuses on a rule that forbids importing from @/db outside the @/services directory, enforcing a service-layer boundary. Without this rule, an agent scaffolding a new HTTP handler would likely import the database client directly, bypassing the service layer and scattering data-access logic across the codebase.

When an agent's context window includes the test file, RuleTester fixtures serve as living documentation: the agent can see concrete examples of what is permitted and what is not. This doubles as both verification and guidance.

An agent scaffolding a new handler tries to query the database directly by importing from @/db. The lint step fails with: "Use a service function from @/services instead." That message points the agent toward the correct architectural pattern -- immediate, actionable, and unambiguous. The agent does not need to have read a wiki page or remembered a Slack conversation.

Agents frequently push code to feature branches and open pull requests automatically. CI must run before any human review to surface issues cheaply and quickly. The workflow follows a fail-early sequential ordering: type-check first, then lint, then test. If the type-check fails, there is no point running linting or tests on code that does not compile. Because steps in a single job are sequential, any failing step halts the job immediately.

The CI workflow alone is not sufficient. Without branch protection, a determined agent or developer can merge a pull request despite failures. In the GitHub repository settings under Branches, enable branch protection for main: require status checks to pass before merging, specifically require the guardrails job from the Agent Guardrails workflow, and disable bypass permissions for bot accounts. This combination ensures that no code reaches the default branch without satisfying every automated check. The workflow becomes a hard gate rather than an advisory signal.

Note: Some branch protection features (such as restricting bypass permissions) may require a paid GitHub plan for private repositories.

AGENTS.md is a convention for placing natural-language guidance at the repository root that agent frameworks can ingest as system-level context. Variations of this convention include CLAUDE.md for Claude Code and .cursorrules for Cursor. OpenAI Codex CLI also reads AGENTS.md from the repository root. The agents and tools that currently support reading repository-level guidance files include OpenAI Codex CLI, Claude Code, Cursor, and Windsurf. The agent framework loads the content into the agent's context window alongside the codebase when supported, making it available during code generation without requiring explicit prompting.

Agents may ignore, truncate, or misinterpret documentation. For example, Claude Code truncates files that exceed its context window limit, and instructions that work with one model version may produce different behavior after an update. AGENTS.md works best as a complement to compiler and linter enforcement, not a replacement. It fills gaps that hard enforcement cannot cover: explaining why a boundary exists, pointing to specific file paths, and providing checklists that aid both agents and human reviewers.

A practical maintenance habit: review and update AGENTS.md during sprint retrospectives. As new branded types, lint rules, or architectural boundaries are added, the guidance file must reflect them, or agents will lack the context to follow new conventions.
