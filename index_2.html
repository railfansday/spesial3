Duplicated validation logic is one of the most persistent sources of bugs in React applications. A client-side rule changes, the server-side copy stays the same, and invalid data slips through the gap. React form validation that relies on a single Zod schema, shared between React Hook Form on the client and a Next.js Server Action on the server, eliminates that drift entirely. This tutorial walks through building that pattern from scratch: a contact form with client-side validation via zodResolver, server-side re-validation with safeParse, accessible error rendering following ARIA authoring practices, and a Vitest test suite that locks down the schema's correctness.

The result is a Next.js App Router contact form where every validation rule lives in one file. When the server rejects a submission, field-level errors map back to individual inputs using setError, and screen readers announce them through aria-describedby associations.

Prerequisites: you should know React, TypeScript, and the Next.js App Router. You will also need Node 20.9 or later, which is the minimum for current Next.js releases. The code below was type-checked with TypeScript 5.9.3 and 7.0.2 and the tests were run with Vitest 5.0.5, React Hook Form 7.90.0, @hookform/resolvers 5.9.1 and Zod 4.6.7.

The schema lives in its own file so both the client component and the Server Action can import it without pulling in unnecessary dependencies.

Each field carries a custom error message. This tutorial uses Zod 4, where z.email() replaces the deprecated z.string().email(); on Zod 3 keep the older form. The ContactFormData type is inferred directly from the schema with z.infer, so the TypeScript type and the runtime validation rules can never diverge.

Both the client component and the Server Action import contactSchema from this one module. On the client, zodResolver wraps the schema so React Hook Form can evaluate it during its validation cycle. On the server, safeParse() runs the same rules against raw input and returns structured errors without throwing. You author the schema once, but it executes in two runtimes. The useForm hook accepts a resolver option that delegates validation to Zod. Setting mode to 'onTouched' means fields validate on blur and re-validate on subsequent changes, giving users immediate feedback without triggering errors before they interact with a field.

The register function connects inputs to React Hook Form's internal state. errors provides per-field error objects, and isSubmitting tracks whether an async submission is in flight.

Every input receives aria-invalid when its corresponding error exists and aria-describedby pointing to a that holds the error message. The aria-describedby attribute is always present (pointing to a consistently rendered ) so that screen readers maintain the association even when errors are cleared. This follows the ARIA authoring practices for inline error messages: aria-describedby links the error to its input, and aria-invalid signals the error state, so screen readers announce the error when the user focuses the field.

The noValidate attribute on the

element turns off built-in browser validation so Zod's rules run instead. The submit button disables itself during submission to prevent duplicate requests. The aria-busy attribute on the form communicates the loading state to assistive technology.

When React Hook Form's client-side validation passes, onSubmit fires. It calls the Server Action, inspects the response for field errors, and maps any server-returned errors back to individual inputs using the applyServerErrors helper (defined in the "Mapping Server Errors" section below). A try/catch block wraps the handler so that network failures or unexpected Server Action crashes surface as a root-level form error instead of leaving the form stuck in a submitting state.

The type: 'server' string used inside applyServerErrors is a convention, not a React Hook Form requirement. It makes it possible to distinguish server-originated errors from client-originated ones when logging, styling, or routing analytics events.

The Server Action imports the same contactSchema and runs safeParse against the incoming data. If parsing fails, the flattened field errors return to the client. If it succeeds, business logic executes inside a try/catch block to ensure unexpected errors come back as structured responses rather than crashing the action. In a real application, the success branch would perform a concrete operation like inserting a row into a contacts table via Prisma or dispatching a transactional email.

The parameter is typed unknown deliberately. Typing it ContactFormData would let TypeScript accept the data without re-parsing, defeating server-side re-validation.

The z.flattenError() helper turns a ZodError into a flat { formErrors: string[], fieldErrors: { name: string[], email: string[] } } shape, which maps directly to the setError loop on the client. (Zod 3 and 4 also have an error.flatten() method, deprecated in Zod 4.) Zod types each field value as optional via a partial record, so the filtering step above narrows out undefined entries and the returned fieldErrors object is a safe Record.

Client-side validation runs in the browser. A user can bypass it entirely by disabling JavaScript, manipulating form data through DevTools, or submitting requests directly via cURL or an automated bot. The applyServerErrors helper (used in the onSubmit handler above) takes each key from the server's fieldErrors object and injects it into React Hook Form's error state. Because the error spans in the JSX read from formState.errors.fieldName, the correct re-renders automatically and aria-invalid toggles to true on the corresponding input. The accessible error contract stays intact without adding manual DOM queries or event listeners.

For unexpected errors that do not map to a specific field, React Hook Form supports root-level errors via setError('root.serverError', { message: '...' }) (requires react-hook-form >=7.34.0; alternatively use setError('root', ...) on earlier versions). This is useful for handling cases like network failures or internal server errors where no individual field is at fault.

Alt text is the written description a screen reader reads out loud in place of an image. Without it, a screen reader either skips the image entirely or announces the file name, which tells a user nothing about the image.

For example, if it's a product photo, a chart, or an icon that functions as a button, missing alt text means a screen reader user has no idea what they're looking at, what it does, or what happens when they click it.

The Fix: Describe what the image actually shows instead of just saying it's an image. If it's purely decorative and adds nothing a screen reader user needs, use an empty alt attribute (alt="") instead of leaving it off. That tells the screen reader to skip it cleanly.

A popular r/Frontend post captured this precisely. The developer reported that Claude Code wrote roughly 1,000 lines of code for a simple helper function that already existed in a project dependency. The root cause is structural, not incidental. Prompt-based instructions are probabilistic. They work well in short sessions, but as the context window fills during extended agentic loops, earlier instructions degrade in influence. Tool outputs, file contents, and intermediate reasoning bury the initial convention reminders. A long enough session means the agent effectively forgets what it was told. Any enforcement mechanism that relies solely on prompt text will exhibit this degradation pattern.

Claude Code hooks offer an alternative enforcement mechanism: shell scripts that bind to lifecycle events inside the agent loop. These scripts use exit codes to enforce rules. Exit 0 means proceed. Exit 2 blocks the action, and the script's stderr is surfaced to Claude as feedback. Any other non-zero exit code is a non-blocking error. This is deterministic. No matter how full the context window gets, an exit code of 2 stops the action every time.

By the end of this article, you will have two working hooks: a pre-write gate that forces Claude to verify whether an implementation already exists before writing new code, and a post-edit lint and format pipeline that runs Prettier and ESLint on every changed file. Together, these hooks catch duplicated or unnecessary code before it lands and enforce style rules automatically.

Prerequisites: Claude Code installed and functional; a Node.js project with Prettier and ESLint already configured; jq installed (brew install jq / apt install jq); Prettier and ESLint must be installed as local node_modules dependencies (not relied upon via npx remote fetch); and basic familiarity with Bash scripting.

Hooks operate on an event-driven model. They fire at specific points in Claude Code's agent loop, intercepting actions before or after they occur. Four lifecycle events are relevant:

PreToolUse fires before any tool call executes. This is the interception point for blocking actions. For file-write gating, the tool names to match are Write, Edit, and MultiEdit. You can also match against Bash for command-level gating.

After a tool call completes, PostToolUse runs. This is the point for validation: linters, formatters, or test suites check the result of an edit. Because the tool has already executed, an exit code of 2 from a PostToolUse hook does not block the original action. Instead, it surfaces the script's stderr as feedback to Claude, which can then issue a follow-up edit to correct the issues.

When the user submits a new prompt, UserPromptSubmit fires. This is useful for resetting state between conversational turns.

Notification fires when Claude sends a notification. Non-zero exit codes from Notification hooks do not block any action. (The documentation does not specify any exit-code effect for this event type.) This makes it useful only for logging or side effects.

The contract is simple. When a hook script exits with code 0, the action proceeds normally. Exit code 2 is the blocking signal. For PreToolUse, exit 2 blocks the tool call and the script's stderr is fed to Claude as feedback. For PostToolUse, the tool has already completed, but exit 2 surfaces the script's stderr to Claude, which can take corrective action. The stderr content becomes part of the agent's reasoning context, which is what makes hooks corrective rather than merely restrictive. Any other non-zero exit code counts as a non-blocking error, not a block.

Configure hooks in the hooks object within .claude/settings.json for project-level scope or ~/.claude/settings.json for user-level scope. Each entry is keyed by event name and contains an array of matcher groups. Each group pairs an optional matcher (a pattern matching specific tool names) with a hooks array of one or more handlers, and each handler declares a type (command for a shell command) plus the command to execute.

This skeleton shows the structural pattern. The matcher field accepts pipe-delimited tool names. When a PreToolUse event fires for a Write tool call, Claude Code checks whether any hook entry matches, then executes the command, piping a JSON payload to its stdin containing the tool name and parameters.

The following configuration wires together all three lifecycle events. The PreToolUse entry fires before Write, Edit, or MultiEdit tool calls and blocks the first write attempt per prompt, printing a checklist for Claude to verify before proceeding. The PostToolUse entry fires after those same tool calls complete and runs Prettier (auto-fix) then ESLint (check) on the changed file. The wrong call early on locks a team into performance ceilings and hosting costs that are expensive to reverse — migrating routing, data-fetching patterns, and deployment pipelines typically means rewriting, not refactoring.

This guide replaces gut instinct with a structured decision matrix and side-by-side implementation patterns. The goal is to expose where each architecture genuinely excels, where it breaks down, and how to map project requirements to the right default.

Astro pages render as static HTML by default. Zero JavaScript ships to the browser unless a developer explicitly opts in. The mechanism for opting in is Astro's client:* directive system, which controls exactly when and how individual UI components hydrate. The available directives include client:load (hydrate immediately on page load), client:idle (hydrate once the browser is idle), client:visible (hydrate when the component scrolls into view), client:media (hydrate when a CSS media query matches), and client:only="react" (skip server rendering entirely; the framework name is a required argument, e.g., "react", "svelte"). Every piece of surrounding markup stays as static HTML. Critically, Astro is framework-agnostic: islands can be built in React, Svelte, Vue, Solid, or Preact, and multiple frameworks can coexist within the same project.

In the App Router, Next.js components are server-rendered by default. Client components are opted into with the "use client" directive at the top of a file. The server/client boundary is per-component, but unlike Astro's isolated islands, the entire page participates in React's unified component tree and streaming pipeline. This tight coupling to the React ecosystem means Next.js benefits from React's concurrent features, including Suspense boundaries and transitions, but it also means the framework is bound to React as the sole UI layer.

Astro treats a page as a static document with interactive widgets bolted on. The mental model is HTML-first.
