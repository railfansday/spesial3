Forms are among the most important components of modern websites. They allow users to register accounts, submit contact requests, search for information, complete purchases, and interact with web applications.

Despite their apparent simplicity, forms can introduce significant usability and development challenges. Poorly labeled fields, unclear validation messages, inaccessible controls, and unreliable submission behavior can prevent users from completing even basic tasks.

Modern HTML provides many built-in features that help developers create more reliable forms with less JavaScript. When combined with semantic markup, thoughtful CSS, and carefully designed validation, these features can improve both usability and maintainability.

This article explores practical techniques for building modern web forms that are accessible, responsive, and easier to maintain.

A well-structured form begins with the correct HTML elements. Native controls provide built-in browser behavior and communicate their purpose to assistive technologies.

Each control has an explicitly associated label. The name attributes identify the fields when form data is submitted, while autocomplete helps browsers recognize common information types.

The required attribute indicates that a field must be completed before a normal browser submission can proceed.

These native features reduce the need for custom code and provide a more consistent starting point across browsers.

HTML provides several input types designed for specific kinds of information.

For example, type="email" enables browser validation for email-shaped input, while type="tel" identifies a telephone number field and can prompt mobile browsers to display a suitable keyboard.

Selecting appropriate input types improves the user experience, especially on mobile devices.

However, native validation has limits. An email input does not establish that an address exists or belongs to the person entering it. Similarly, a URL input does not guarantee that a submitted address is safe to access.

Client-side validation should therefore be treated as a usability feature, not as a substitute for server-side validation.

Browser controls can look different across platforms. A small set of reusable CSS rules can make a form feel more consistent while preserving native functionality.

The box-sizing: border-box declaration makes width calculations more predictable because padding and borders are included in the declared width.

Using font: inherit helps form controls remain consistent with the surrounding typography.

The visible focus outline is equally important. Keyboard users need to identify which control currently receives focus, so removing browser outlines without an accessible replacement should be avoided.

For operations that must not be repeated, server-side idempotency controls may be necessary. Disabling a button alone cannot guarantee that a request is processed only once.

Forms frequently collect personal or business information, so security must be part of their design.

Validate all submitted data on the server.

Apply appropriate authorization checks to sensitive operations.

Use CSRF protection where required by the application's authentication architecture.

Escape or safely render user-provided content to reduce injection risks.

Avoid placing passwords, tokens, or sensitive personal information in URLs.

Apply appropriate rate limits to public-facing endpoints.

HTML validation helps users correct mistakes, but it does not establish trust in submitted data.

For example, a hidden input containing a user's role must never be treated as authoritative proof of that role. A malicious client can change the value before submission.

Security decisions belong on the server, where the application can verify permissions and enforce its rules.

Forms should remain usable on mobile devices without forcing users to zoom, scroll horizontally, or interact with cramped controls.

Developers should test forms at narrow widths and with browser zoom enabled. Long labels, validation messages, and translated content should be allowed to wrap naturally.

It is also worth checking that touch targets are comfortable to use and that the form does not depend on hover effects to communicate important information.

A form that works when every field contains valid data may still fail under realistic conditions.

Automated browser tests can cover common validation and submission scenarios. Manual testing remains valuable for checking whether error messages are understandable and whether the form feels usable to people with different accessibility needs.

The most reliable forms are designed to handle failure clearly, not just to demonstrate a successful submission.

Modern HTML provides a strong foundation for building accessible and maintainable forms. Semantic elements, appropriate input types, native validation, and reusable CSS can reduce unnecessary JavaScript while improving the user experience.

When custom validation or asynchronous submission is required, developers should add it carefully and preserve clear feedback, keyboard support, and server-side security controls.

A well-designed form does more than collect information. It guides users through a task, helps them recover from mistakes, and communicates what happens next. By treating usability, accessibility, and security as connected parts of the same design process, developers can build forms that are more reliable and easier to maintain.

A design file shows what an interface should look like in a particular state. A browser reveals what happens when the headline doubles in length, a request fails, someone uses a keyboard, or a device struggles to render an animation.

That gap explains many frustrating handoffs. A developer believes the implementation matches the design, while a designer notices behavior that was never discussed. Both can be right about the evidence they have.

A more useful review combines the rendered interface with repeatable browser checks. Each check should produce a small, actionable finding: the conditions, the observed behavior, and the expected result.

The nine checks below use browser tools to turn visual opinions into implementation decisions. Chrome DevTools provides the main examples; tool names and locations can vary between versions.

When a component looks wrong, first identify which rule actually controls it. The value in a stylesheet may be overridden, inherited, or constrained by its parent.

Select the element in DevTools and inspect its computed width, spacing, typography, and box model. Toggle a suspected declaration to see whether it explains the problem. Chrome’s CSS inspection guide covers this workflow.

Suppose a card heading overflows. Reducing its font size might hide the symptom while damaging the visual hierarchy. Instead, investigate whether the text container can shrink:

This is a targeted pattern, not a universal fix. Check the actual layout before applying it.

Record the finding: “At a narrow width, the flex child’s minimum size prevents the heading from wrapping.” Include the selector and the source change needed. Temporary DevTools edits are experiments; commit the fix in the project.

General technical documentation should capture the reasoning behind reusable layout rules. For this card, explain why the text container must be allowed to shrink and which long-content cases should be checked after future changes.

Testing only a desktop and a mobile preset can miss awkward layouts between them. Navigation may wrap at one width, while a toolbar collides at another.

Use Device Mode to resize the viewport gradually. Try long labels, empty content, and a larger number of cards. Watch for clipping, unnecessary horizontal scrolling, and controls that become difficult to reach.

Choose breakpoints based on the point where the content stops working. A device name does not explain why a layout should change.

Record the viewport width in CSS pixels and the content that triggered the failure. “Broken on mobile” is much less actionable than “At 390 CSS pixels, a two-line product name pushes the action button outside its container.”

Device emulation does not reproduce every hardware, operating-system, or browser behavior. Confirm critical flows on real devices and the browsers your audience uses. SitePoint’s cross-browser responsive testing guide provides additional background.

Record the finding: The failing width, the content variant, and the intended reflow behavior.

A control can be visually obvious while exposing an unclear name to assistive technology. This often happens with icon-only buttons.

Inspect the computed role and accessible name using DevTools’ accessibility features. Check that the name describes the action and that the element has appropriate semantics.

If a button already has clear visible text, an extra ARIA label may be unnecessary. Keep visible and accessible naming aligned rather than adding ARIA everywhere.

Loading states are part of the interface, even when they are absent from the mockup.

Use the Network panel to inspect the requests made by a user action. Check the status, timing, and response. Apply network throttling to observe loading behavior that disappears on a fast connection.

A network error, an HTTP error, and an empty successful response are different conditions. Exercise each through controlled development fixtures or mocks rather than assuming that one failure test covers everything.

Record the finding: The action, request outcome, UI state, and recovery path. A screenshot of a spinner alone does not explain whether the application can recover.

A page may load promptly but become sluggish when a user filters a large list or opens a complex menu.

Record a short session with the Performance panel. Start recording, perform the problem interaction once, and stop. Inspect the period surrounding the delay for scripting, layout, and rendering work.

Keep the investigation narrow. A recording containing several unrelated actions is harder to interpret.

For example, if typing into a filter causes repeated expensive updates, investigate the work triggered by each keystroke before adding an animation to disguise the delay. The appropriate fix might involve reducing rendered content, avoiding repeated calculations, or changing when work runs.

Compare before and after using the same content, browser, and throttling settings. A local trace is diagnostic evidence, not proof of the experience of every user.

Confirm any removal or loading change against the supported routes and states. Coverage can suggest a question; it cannot establish the answer by itself.

Choose a finding, reproduce it, make a targeted change, and rerun the audit. If results vary, investigate the test environment before concluding that the code improved or regressed.

Browser evidence becomes more useful when another person can reproduce it without attending the original review.

Technical references can include setup guidance, component specifications, and troubleshooting procedures. For a web interface, connect those references to specific browser observations so the documentation describes behavior that the team can verify.

This structure separates observation from proposed implementation. A screenshot can show the clipping, but it does not establish the underlying cause.

Keep documentation beside the component or in a place linked from the relevant issue. Update it when behavior changes, and give examples a clear connection to a build or release.

Record the finding: Enough context for another developer or designer to reproduce, assess, and verify it.

You do not need to run every tool against every component. Match the check to the risk: network inspection for asynchronous flows, keyboard checks for interactive controls, and performance recordings for expensive interactions.

The useful outcome is a shared explanation of how the interface behaves under real conditions. Designers gain evidence about the implemented experience, and developers gain clearer acceptance criteria.

Start with one important flow. Inspect it together, document the failures precisely, and turn the agreed behavior into repeatable checks. That makes the next handoff easier to implement—and easier to review.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

AI coding agents -- Copilot, Cursor, Codex, Devin, and their successors -- are now standard tooling in many engineering teams. They generate production code, shifting the developer's role from writer to reviewer. That shift exposes a specific failure mode: natural-language prompt quality does not primarily determine agent output quality. The constraints a codebase enforces at compile time and CI time determine it.

Engineers who run AI coding agents in production, including Lauren Tan (@poteto), have argued publicly that traditional codebase hygiene is the highest-leverage investment for agent correctness. The core argument: making the correct path the easiest one, through types, invariants, and architectural boundaries, beats prompt engineering or post-hoc code review. This tutorial builds a minimal, runnable repository scaffold that demonstrates four complementary guardrails: branded types that enforce domain invariants at compile time, a custom ESLint rule that catches convention violations through static analysis, a GitHub Actions CI gate that prevents non-conforming code from merging, and an AGENTS.md guidance file that provides soft contextual nudges agents can read. These layers enforce constraints at four different points between code generation and merge, and each layer reinforces the others.

AI coding agents generate code that satisfies the immediate request. They lack whole-codebase awareness of unwritten conventions, team norms, or architectural decisions that exist only in developers' heads. Without machine-enforceable constraints, an agent defaults to the loosest valid pattern. Asked to fetch a user, it will accept a raw string parameter rather than seeking out a branded UserId type. It will import the database client directly rather than routing through a service layer. The agent is not being careless. It optimizes for the shortest path to syntactically valid code.

AI coding tools can turn a plain-English description into a working web application in minutes. They can generate interfaces, connect APIs, create database schemas, and help developers move from an idea to a functional prototype faster than traditional workflows often allow.

But getting an application to run is not the same as making it production-ready.

The security gap is measurable. In its 2025 GenAI Code Security Report, Veracode found that 45% of AI-generated code samples failed security tests by introducing vulnerabilities associated with the OWASP Top 10. The research evaluated generated code samples, not complete applications or confirmed cyberattacks. Nevertheless, it highlights an important risk: code that works can still be insecure.

Real-world investigations have raised similar concerns. A May 2026 WIRED investigation into exposed data in vibe-coded applications reported security and data-exposure problems in applications built using popular AI coding tools. These findings concern the applications examined, rather than every application developed with AI.

The lesson is not that vibe coding is inherently unsafe. It is that generating software quickly does not eliminate the engineering work required to protect data, verify behavior, and maintain reliability.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Consider a customer portal. An AI tool might generate a login page, a dashboard, and a database connection in a single session. The interface could look complete while the application still lacks proper authorization checks, reliable error handling, or protection against unauthorized data access.

These gaps become more consequential when an application stores personal information, processes payments, manages business records, or serves multiple customers.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Before generating substantial amounts of code, document:

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

A functional interface can conceal serious implementation problems.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Code review is therefore essential, even when an AI tool generates most of the implementation.

Start with the code responsible for important application behavior:

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

For JavaScript and TypeScript projects, automated linting and type checking can catch many common mistakes. However, these tools cannot prove that business logic is correct or that permissions are enforced properly.

When reviewing a change, ask the AI to explain its implementation and identify its assumptions. Then verify those explanations against the actual code and relevant documentation.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

Every sensitive operation should enforce the relevant permissions on the server or trusted backend.

For example, an application that allows users to view invoices should verify that the authenticated user is authorized to access the requested invoice. It should not rely solely on a user ID supplied by the browser.

Test both permitted and prohibited actions. A good security test confirms not only that the correct user can access a resource, but also that other users cannot.

For applications handling sensitive data, consider an independent security review before launch.

AI-generated applications often work well with expected inputs. Real users, however, submit incomplete forms, unexpected values, oversized files, malformed requests, and repeated actions.

Input validation and error handling help prevent these conditions from becoming application failures or security vulnerabilities.

Client-side validation improves the user experience, but it should not be the only line of defense. Requests can bypass browser validation entirely.

Validate incoming data on the server, using rules appropriate to each field and operation. Enforce database constraints where applicable, and use parameterized queries or safe ORM methods to prevent SQL injection.

For file uploads, validate file types, enforce size limits, and store files using a design that prevents unauthorized access. Do not assume a filename or content type supplied by the browser is trustworthy.

Users need understandable error messages. Developers need enough diagnostic information to investigate failures.

These requirements should be handled separately.

A user-facing response might say, "We couldn't save your changes. Please try again." An internal log can record a request identifier, the relevant operation, and a sanitized diagnostic message.

Avoid exposing stack traces, database credentials, internal configuration, access tokens, or sensitive records in production responses.

Also test what happens when external APIs time out, database connections fail, or required environment variables are missing.

A production-ready application should fail predictably, protect sensitive information, and provide a clear path to recovery.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.

Asking an AI tool to generate tests is useful, but those tests must be reviewed. A test suite can pass while validating incorrect assumptions or ignoring the application's most important failure cases.

Start with critical workflows rather than trying to test every minor interface detail.

For an e-commerce application, these workflows might include account creation, product selection, checkout, payment confirmation, and order retrieval. For a business dashboard, they might include importing records, updating a customer, assigning permissions, and generating a report.

Pay particular attention to boundary conditions.

What happens when a form is submitted twice? When an API returns an unexpected response? When a database operation fails halfway through a workflow? When two users update the same record simultaneously?

These scenarios often reveal problems that a successful demonstration will not.

For applications that process transactions, test idempotency where appropriate so that retries do not unintentionally create duplicate payments, orders, or records.

Database indexes can improve frequently used queries, while pagination can prevent interfaces from loading thousands of records at once. Caching can reduce repeated work when the data and consistency requirements allow it.

For public-facing websites, evaluate relevant Core Web Vitals and test performance on realistic devices and network conditions.

Avoid adding caching layers, complex abstractions, or performance libraries simply because an AI tool recommends them. Every additional component introduces maintenance costs and potential failure points.

Measure first, optimize the bottleneck, and measure again.

Generated applications frequently depend on third-party packages, API services, and environment-specific settings. Each dependency expands the application's maintenance and security responsibilities.

Before deployment, inspect the dependency manifest and lockfile. Remove unnecessary packages, verify that required packages exist, and review known vulnerabilities using appropriate dependency-scanning tools.

Use environment variables or an appropriate secrets manager, depending on the deployment environment. Restrict credentials to the permissions they actually require, and rotate any secret that may have been exposed.

Also check how the application behaves when a deployment fails, a service becomes unavailable, or a configuration change introduces a regression.

A reliable release process should make failures easier to detect, contain, and recover from.

Testing happens before release and in controlled environments. Monitoring helps developers understand how the application behaves after real users begin using it.

Without monitoring, a deployment can appear successful while users encounter failed requests, slow pages, broken integrations, or database errors.

Set alerts for failures that require action. Avoid collecting unnecessary personal data in logs, and define retention and access policies appropriate to the application.

For AI-powered features, monitor additional factors such as model response failures, latency, token usage, and output quality. An application that depends on an external AI service must account for rate limits, changing model behavior, and provider outages.

Monitoring does not prevent every failure. It makes failures visible enough to investigate and resolve.

Eight eMudhra intermediate Certificate Authority private keys are trivially recoverable from their public certificates. Any attacker can mint trusted TLS certificates for arbitrary domains. Browsers have already blocked these compromised intermediates through revocation mechanisms, but most non-browser runtimes — curl, Python, Node.js, Go, and Rust — still silently trust them. This affects any team operating server-side infrastructure, CI pipelines, or CLI tooling that makes outbound TLS connections. If your stack trusts the eMudhra chain, an attacker can forge certificates your code will accept without complaint.

This guide provides a diagnostic sequence: test every runtime in the stack against the compromised certificates, remediate by updating trust stores, and verify the fix sticks. The primary source for this disclosure is Scott Helme's detailed writeup.

In RSA key generation, you derive the private exponent d via the modular inverse of the public exponent e modulo λ(n) (the Carmichael totient of the modulus), where λ(n) depends on the prime factors of n. RSA's security depends entirely on d being large — typically hundreds of digits — making it computationally infeasible to derive from the public key alone.

eMudhra generated eight intermediate CA certificates with single-byte d values. Specific recovered values include d=4, d=56, and d=115, as documented in Scott Helme's disclosure post. These are not large numbers. They are recoverable from the public certificate in milliseconds. Anyone with access to the public certificate (which is, by definition, public) can reconstruct the private key and sign certificates that chain up to eMudhra's trusted root. That means arbitrary TLS certificates for any domain, indistinguishable from legitimate ones to any client that trusts the eMudhra chain.

An attacker holding one of these recovered keys can issue a certificate for any hostname, and any TLS client trusting the eMudhra intermediate will accept it without complaint.

Current browser versions already reject the compromised intermediates.

The problem lies everywhere else. Non-browser TLS clients skip revocation checks by default. curl does not check CRLs or OCSP unless explicitly configured to do so. Python's requests and urllib3 libraries rely on the certifi bundle and perform no revocation checking. Python's standard library urllib.request module uses the system SSL store, not certifi. Node.js's https module uses either a compiled-in root store or the system store depending on build configuration, with no active revocation. Go's crypto/tls loads system roots but does not perform revocation checks. Rust's rustls paired with webpki-roots uses a bundled Mozilla root set, while native-tls defers to the system store; neither checks revocation by default.

This creates a trust store gap. The system CA bundle on a Linux server, the certifi bundle shipped with Python, and the compiled-in roots in Node.js might all still contain the eMudhra intermediates or trust the root that chains to them. Without manual intervention, these runtimes remain vulnerable.

Every frontend developer will eventually stare at a CORS error in the browser console, watching an API call fail for reasons that seem opaque. A CORS error fix requires understanding what the browser is actually telling you, matching that specific message to its root cause, and applying a targeted, security-conscious server configuration.

The scheme, host, and port together define an "origin." https://example.com and http://example.com are different origins (different schemes), as are https://example.com and https://api.example.com (different hosts). https://example.com and https://example.com:443 are the same origin because port 443 is the default for HTTPS, and browsers omit it in origin comparisons. The browser enforces the same-origin policy on client-side JavaScript reading responses, not on sending requests. This distinction trips up many developers: the server may still receive and fully process the request; the browser simply refuses to expose the response to the calling code. The request lands, the database row gets written, and the browser throws an error anyway. The policy exists to prevent a malicious page from silently reading sensitive data from another origin using the user's ambient credentials.

Cross-Origin Resource Sharing (CORS) is a controlled opt-in mechanism via HTTP response headers. The server signals to the browser that a specific foreign origin is permitted to read its responses. Four headers control the mechanism: Access-Control-Allow-Origin specifies which origin is allowed, and Access-Control-Allow-Methods declares which HTTP methods are permitted. Access-Control-Allow-Headers lists which custom or non-simple headers the client may send, while Access-Control-Allow-Credentials indicates whether the browser should expose the response to credentialed requests.

The browser does not treat all cross-origin requests equally. "Simple" requests use GET, HEAD, or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data, or text/plain, and no custom headers. A POST with Content-Type: application/json is not a simple request and triggers a preflight.

Simple requests go directly to the server, and the browser evaluates the CORS headers on the response. Anything else triggers a preflight request: an OPTIONS call the browser sends automatically before the actual request, asking the server whether the real request would be acceptable. If the OPTIONS response lacks the proper CORS headers, the browser never sends the real request at all.

A typical Chrome DevTools error reads: Access to fetch at 'https://api.example.com/data' from origin 'https://app.example.com' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two origins appear in this message. The URL after "fetch at" is the target server, the resource the code tried to reach. The value after "from origin" is the page's own origin, the one making the request. Chrome is stating that the target server's response did not include an Access-Control-Allow-Origin header that matches the requesting origin, so the browser blocked the response from reaching JavaScript.

The most common variant is the missing header: No 'Access-Control-Allow-Origin' header is present on the requested resource. The server simply did not include the header at all.

When the console says Response to preflight request doesn't pass access control check, the server either did not respond to the OPTIONS request correctly or returned a non-2xx status code for it.

Redirect variant: Redirect is not allowed for a preflight request. Developers commonly misdiagnose this one. It occurs when the URL triggers a redirect before reaching the application handler. Typical culprits include HTTP-to-HTTPS upgrades, trailing-slash normalization (e.g., /api/data redirecting to /api/data/), or a load balancer rewriting URLs. The browser's preflight OPTIONS request follows the redirect, and the Fetch specification (§4.8) forbids following redirects on preflight requests, so the entire flow fails. Fix the URL so no redirect occurs.

Credential variant: The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'. When fetch is called with credentials: 'include' or XMLHttpRequest sets withCredentials = true, the server must respond with the exact requesting origin, not *. The browser will block JavaScript access to the response if a wildcard is used with credentials.

#11046. “Existential risk” – Why scientists are racing to define consciousness

As artificial intelligence continues to advance and ethical concerns grow alongside it, scientists say the need to understand consciousness has reached a critical point.

In a new review published in Frontiers in Science, researchers warn that progress in AI and neurotechnology is moving faster than scientific understanding of consciousness. This gap, they argue, could lead to serious ethical problems if it is not addressed.

The authors say explaining how consciousness emerges is now an urgent scientific and moral priority. A clearer understanding could eventually make it possible to develop scientific methods for detecting consciousness. That breakthrough would have far-reaching consequences for AI development, prenatal policy, animal welfare, medicine, mental health care, law, and emerging technologies such as brain-computer interfaces.

"Consciousness science is no longer a purely philosophical pursuit. It has real implications for every facet of society -- and for understanding what it means to be human," said lead author Prof Axel Cleeremans from Université Libre de Bruxelles. "Understanding consciousness is one of the most substantial challenges of 21st-century science -- and it's now urgent due to advances in AI and other technologies.

"If we become able to create consciousness -- even accidentally -- it would raise immense ethical challenges and even existential risk," added Cleeremans, a European Research Council (ERC) grantee.

Consciousness, commonly described as awareness of both the world around us and ourselves, remains one of science's most difficult puzzles. Despite decades of research, scientists still lack agreement on how subjective experience emerges from biological processes.

Researchers have identified brain regions and neural activity linked to conscious experience, but major disagreements remain. Scientists continue to debate which brain systems are truly necessary for consciousness and how they interact to produce awareness. Some researchers even question whether this approach captures the problem correctly.

The new review examines the current state of consciousness science, future directions for the field, and the possible consequences if humans succeed in fully explaining or even creating consciousness. This includes the possibility of consciousness emerging in machines or in lab-grown brain-like systems known as "brain organoids."

The authors argue that developing evidence-based tests for consciousness could transform how awareness is identified across many contexts. Such tools could help detect consciousness in patients with brain injuries or dementia and determine when awareness arises in fetuses, animals, brain organoids, or even AI systems.

While this would represent a major scientific advance, the researchers caution that it would also create difficult ethical and legal questions. Determining that a system is conscious would force society to reconsider how that system should be treated.

"Progress in consciousness science will reshape how we see ourselves and our relationship to both artificial intelligence and the natural world," said co-author Prof Anil Seth from the University of Sussex and ERC grantee. "The question of consciousness is ancient -- but it's never been more urgent than now."

A deeper understanding of consciousness could have wide-ranging effects across society.

In medicine, it could improve care for patients who are unresponsive and assumed to be unconscious. Measurements inspired by integrated information theory and global workspace theory[1] have already detected signs of awareness in some individuals diagnosed with unresponsive wakefulness syndrome. Further progress could refine these tools to better assess consciousness in coma, advanced dementia, and anesthesia, and influence treatment decisions and end-of-life care.

Mental health treatment could also benefit. Understanding the biological basis of subjective experience may help researchers develop better therapies for conditions such as depression, anxiety, and schizophrenia by narrowing the gap between animal studies and human emotional experience.

Greater insight into consciousness could reshape how humans think about their moral responsibilities toward animals. Identifying which animals and systems are sentient could influence animal research practices, farming, food consumption, and conservation strategies. "Understanding the nature of consciousness in particular animals would transform how we treat them and emerging biological systems that are being synthetically generated by scientists," said co-author Prof Liad Mudrik from Tel Aviv University and ERC grantee.

Consciousness research could also affect how the legal system understands responsibility. New findings may challenge traditional legal concepts such as mens rea, the "guilty mind" required to establish intent. As neuroscience reveals how much behavior arises from unconscious processes, courts may need to reconsider where responsibility begins and ends.

At the same time, advances in AI, brain organoids, and brain-computer interfaces raise the possibility of creating or altering awareness beyond natural biological limits. While some researchers believe consciousness might arise through computation alone, others argue that biological factors play an essential role. "Even if 'conscious AI' is impossible using standard digital computers, AI that gives the impression of being conscious raises many societal and ethical challenges," said Seth.

The authors emphasize the need for a coordinated, evidence-based approach to studying consciousness. One proposed strategy involves adversarial collaborations, in which competing theories are tested against each other through experiments designed jointly by their supporters. "We need more team science to break theoretical silos and overcome existing biases and assumptions," said Mudrik. "This step has the potential to move the field forward."

The researchers also argue that scientific work should place greater emphasis on phenomenology (what consciousness feels like) alongside studies of function (what consciousness does).

"Cooperative efforts are essential to make progress -- and to ensure society is prepared for the ethical, medical, and technological consequences of understanding, and perhaps creating, consciousness," said Cleeremans.

#11041. A tiny light trap could unlock million qubit quantum computers

After years of slow progress, researchers may finally be seeing a clear path forward in the quest to build powerful quantum computers. These machines are expected to dramatically shorten the time required for certain calculations, turning problems that would take classical computers thousands of years into tasks that could be completed in hours.

A team led by physicists at Stanford University has developed a new kind of optical cavity that can efficiently capture single photons, the basic particles of light, emitted by individual atoms. Those atoms serve as the core components of a quantum computer because they store qubits, which are the quantum equivalent of the zeros and ones used in traditional computing. For the first time, this approach allows information to be collected from all qubits at once.

Optical Cavities Enable Faster Qubit Readout

In research published in Nature, the team describes a system made up of 40 optical cavities, each holding a single atom qubit, along with a larger prototype that contains more than 500 cavities. The results point to a realistic route toward building quantum computing networks that could one day include as many as a million qubits.

"If we want to make a quantum computer, we need to be able to read information out of the quantum bits very quickly," said Jon Simon, the study's senior author and associate professor of physics and of applied physics in Stanford's School of Humanities and Sciences. "Until now, there hasn't been a practical way to do that at scale because atoms just don't emit light fast enough, and on top of that, they spew it out in all directions. An optical cavity can efficiently guide emitted light toward a particular direction, and now we've found a way to equip each atom in a quantum computer within its own individual cavity."

An optical cavity works by trapping light between two or more reflective surfaces, causing it to bounce back and forth. The effect can be compared to standing between mirrors in a fun house, where reflections seem to stretch endlessly into the distance. In scientific settings, these cavities are far smaller and use repeated passes of a laser beam to extract information from atoms.

Although optical cavities have been studied for decades, they have been difficult to use with atoms because atoms are extremely small and nearly transparent. Getting light to interact with them strongly enough has been a persistent challenge.

Rather than relying on many repeated reflections, the Stanford team introduced microlenses inside each cavity to tightly focus light onto a single atom. Even with fewer light bounces, this method proved more effective at pulling quantum information from the atom.

"We have developed a new type of cavity architecture; it's not just two mirrors anymore," said Adam Shaw, a Stanford Science Fellow and first author on the study. "We hope this will enable us to build dramatically faster, distributed quantum computers that can talk to each other with much faster data rates."

Beyond the Binary Limits of Classical Computing

Conventional computers process information using bits that represent either zero or one. Quantum computers operate using qubits, which are based on the quantum states of tiny particles. A qubit can represent zero, one, or both states at the same time, allowing quantum systems to handle certain calculations far more efficiently than classical machines.

"A classical computer has to churn through possibilities one by one, looking for the correct answer," said Simon. "But a quantum computer acts like noise-canceling headphones that compare combinations of answers, amplifying the right ones while muffling the wrong ones."

Scientists estimate that quantum computers will need millions of qubits to outperform today's most powerful supercomputers. According to Simon, reaching that level will likely require connecting many quantum computers into large networks. The parallel light-based interface demonstrated in this study provides an efficient foundation for scaling up to those sizes.

The researchers showed a working 40-cavity array in the current study, along with a proof-of-concept system containing more than 500 cavities. Their next goal is to expand to tens of thousands. Looking further ahead, the team envisions quantum data centers in which individual quantum computers are linked through cavity-based network interfaces to form full-scale quantum supercomputers.

Broader Scientific and Technological Impact

Significant engineering hurdles remain, but the researchers believe the potential benefits are substantial. Large-scale quantum computers could lead to breakthroughs in materials design and chemical synthesis, including applications related to drug discovery, as well as advances in code breaking.

The ability to efficiently collect light also has implications beyond computing. Cavity arrays could improve biosensing and microscopy, supporting progress in medical and biological research. Quantum networks may even contribute to astronomy by enabling optical telescopes with enhanced resolution, potentially allowing scientists to directly observe planets orbiting stars beyond our solar system.

"As we understand more about how to manipulate light at a single particle level, I think it will transform our ability to see the world," Shaw said.
