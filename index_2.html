A design file shows what an interface should look like in a particular state. A browser reveals what happens when the headline doubles in length, a request fails, someone uses a keyboard, or a device struggles to render an animation.

That gap explains many frustrating handoffs. A developer believes the implementation matches the design, while a designer notices behavior that was never discussed. Both can be right about the evidence they have.

A more useful review combines the rendered interface with repeatable browser checks. Each check should produce a small, actionable finding: the conditions, the observed behavior, and the expected result.

The nine checks below use browser tools to turn visual opinions into implementation decisions. Chrome DevTools provides the main examples; tool names and locations can vary between versions.

When a component looks wrong, first identify which rule actually controls it. The value in a stylesheet may be overridden, inherited, or constrained by its parent.

Select the element in DevTools and inspect its computed width, spacing, typography, and box model. Toggle a suspected declaration to see whether it explains the problem. Chrome’s CSS inspection guide covers this workflow.

General technical documentation should capture the reasoning behind reusable layout rules. For this card, explain why the text container must be allowed to shrink and which long-content cases should be checked after future changes.

Testing only a desktop and a mobile preset can miss awkward layouts between them. Navigation may wrap at one width, while a toolbar collides at another.

Use Device Mode to resize the viewport gradually. Try long labels, empty content, and a larger number of cards. Watch for clipping, unnecessary horizontal scrolling, and controls that become difficult to reach.

Choose breakpoints based on the point where the content stops working. A device name does not explain why a layout should change.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

AI coding agents -- Copilot, Cursor, Codex, Devin, and their successors -- are now standard tooling in many engineering teams. They generate production code, shifting the developer's role from writer to reviewer. That shift exposes a specific failure mode: natural-language prompt quality does not primarily determine agent output quality. The constraints a codebase enforces at compile time and CI time determine it.

Engineers who run AI coding agents in production, including Lauren Tan (@poteto), have argued publicly that traditional codebase hygiene is the highest-leverage investment for agent correctness. The core argument: making the correct path the easiest one, through types, invariants, and architectural boundaries, beats prompt engineering or post-hoc code review. When a compiler rejects invalid code before a pull request is even opened, no amount of conversational finesse matters.

This tutorial builds a minimal, runnable repository scaffold that demonstrates four complementary guardrails: branded types that enforce domain invariants at compile time, a custom ESLint rule that catches convention violations through static analysis, a GitHub Actions CI gate that prevents non-conforming code from merging, and an AGENTS.md guidance file that provides soft contextual nudges agents can read. These layers enforce constraints at four different points between code generation and merge, and each layer reinforces the others.

AI coding agents generate code that satisfies the immediate request. They lack whole-codebase awareness of unwritten conventions, team norms, or architectural decisions that exist only in developers' heads. Without machine-enforceable constraints, an agent defaults to the loosest valid pattern. Asked to fetch a user, it will accept a raw string parameter rather than seeking out a branded UserId type. It will import the database client directly rather than routing through a service layer. The agent is not being careless. It optimizes for the shortest path to syntactically valid code.

Each layer compounds the effectiveness of the others. Types catch the majority of structural errors. Lint rules catch convention drift that types miss. CI gates catch anything that slips past local tooling. Documentation explains the why behind constraints, helping agents make better choices in ambiguous situations.

Consider a common function signature: function getUser(id: string). That parameter accepts any string. An email address, a raw UUID, an order ID, an empty string. An AI agent generating a call to getUser will happily pass whatever string-shaped value is closest at hand, with no compiler objection.

Branded types solve this by intersecting a base type with a unique symbol tag, creating a compile-time-only distinction between structurally identical types. A UserId and an OrderId are both strings at runtime, but the compiler treats them as incompatible types. The technique carries zero runtime overhead because the compiler erases the brand during compilation.

Hydration is the process where React, running in the browser, attaches event handlers to server-rendered HTML and reconciles that static markup with the virtual DOM tree the client would have produced. For hydration to succeed, the HTML generated on the server must match, node by node, what the client renders on its initial pass. Any divergence triggers a hydration mismatch error.

The window object does not exist in Node.js. Because localStorage is a property of window, any direct access during server-side rendering fails. Developers hit one of two failure modes. The first is a hard crash: ReferenceError: localStorage is not defined, which kills the server render entirely. In the App Router, 'use client' components still pre-render on the server during next build, so this error fires during server pre-rendering, not in the browser. The second failure mode is subtler and more common: a developer wraps the access in a typeof window !== 'undefined' guard, which avoids the crash but causes the server to render with a default value (say, 'light') while the client reads a stored value (say, 'dark') from localStorage. React detects the difference and throws a hydration mismatch warning. This exact scenario has been reported repeatedly on Stack Overflow, often confusing developers who believe the guard should be sufficient.

The root cause is straightforward but easy to overlook: the server and client disagree on initial state.

The goal here is to compare three patterns that resolve both failure modes, with honest analysis of their trade-offs.

Eight eMudhra intermediate Certificate Authority private keys are trivially recoverable from their public certificates. Any attacker can mint trusted TLS certificates for arbitrary domains. Browsers have already blocked these compromised intermediates through revocation mechanisms, but most non-browser runtimes — curl, Python, Node.js, Go, and Rust — still silently trust them. This affects any team operating server-side infrastructure, CI pipelines, or CLI tooling that makes outbound TLS connections. If your stack trusts the eMudhra chain, an attacker can forge certificates your code will accept without complaint.

This guide provides a diagnostic sequence: test every runtime in the stack against the compromised certificates, remediate by updating trust stores, and verify the fix sticks. The primary source for this disclosure is Scott Helme's detailed writeup.

In RSA key generation, you derive the private exponent d via the modular inverse of the public exponent e modulo λ(n) (the Carmichael totient of the modulus), where λ(n) depends on the prime factors of n. RSA's security depends entirely on d being large — typically hundreds of digits — making it computationally infeasible to derive from the public key alone.

eMudhra generated eight intermediate CA certificates with single-byte d values. Specific recovered values include d=4, d=56, and d=115, as documented in Scott Helme's disclosure post. These are not large numbers. They are recoverable from the public certificate in milliseconds. Anyone with access to the public certificate (which is, by definition, public) can reconstruct the private key and sign certificates that chain up to eMudhra's trusted root. That means arbitrary TLS certificates for any domain, indistinguishable from legitimate ones to any client that trusts the eMudhra chain.

An attacker holding one of these recovered keys can issue a certificate for any hostname, and any TLS client trusting the eMudhra intermediate will accept it without complaint.

Chrome pushed a CRLSet update blocking the intermediates the same evening, Mozilla blocked them in Firefox via OneCRL within hours, Apple applied its platform block on October 19, and Microsoft rolled out a disallowed-certificate CTL update. Current browser versions already reject the compromised intermediates.

The problem lies everywhere else. Non-browser TLS clients skip revocation checks by default. curl does not check CRLs or OCSP unless explicitly configured to do so. Python's requests and urllib3 libraries rely on the certifi bundle and perform no revocation checking. Python's standard library urllib.request module uses the system SSL store, not certifi. Node.js's https module uses either a compiled-in root store or the system store depending on build configuration, with no active revocation. Go's crypto/tls loads system roots but does not perform revocation checks. Rust's rustls paired with webpki-roots uses a bundled Mozilla root set, while native-tls defers to the system store; neither checks revocation by default.

This creates a trust store gap. The system CA bundle on a Linux server, the certifi bundle shipped with Python, and the compiled-in roots in Node.js might all still contain the eMudhra intermediates or trust the root that chains to them. Without manual intervention, these runtimes remain vulnerable.

Every frontend developer will eventually stare at a CORS error in the browser console, watching an API call fail for reasons that seem opaque. A CORS error fix requires understanding what the browser is actually telling you, matching that specific message to its root cause, and applying a targeted, security-conscious server configuration.

The scheme, host, and port together define an "origin." https://example.com and http://example.com are different origins (different schemes), as are https://example.com and https://api.example.com (different hosts). https://example.com and https://example.com:443 are the same origin because port 443 is the default for HTTPS, and browsers omit it in origin comparisons. The browser enforces the same-origin policy on client-side JavaScript reading responses, not on sending requests. This distinction trips up many developers: the server may still receive and fully process the request; the browser simply refuses to expose the response to the calling code. The request lands, the database row gets written, and the browser throws an error anyway. The policy exists to prevent a malicious page from silently reading sensitive data from another origin using the user's ambient credentials.

Cross-Origin Resource Sharing (CORS) is a controlled opt-in mechanism via HTTP response headers. The server signals to the browser that a specific foreign origin is permitted to read its responses. Four headers control the mechanism: Access-Control-Allow-Origin specifies which origin is allowed, and Access-Control-Allow-Methods declares which HTTP methods are permitted. Access-Control-Allow-Headers lists which custom or non-simple headers the client may send, while Access-Control-Allow-Credentials indicates whether the browser should expose the response to credentialed requests.

The browser does not treat all cross-origin requests equally. "Simple" requests use GET, HEAD, or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data, or text/plain, and no custom headers. A POST with Content-Type: application/json is not a simple request and triggers a preflight.

Simple requests go directly to the server, and the browser evaluates the CORS headers on the response. Anything else triggers a preflight request: an OPTIONS call the browser sends automatically before the actual request, asking the server whether the real request would be acceptable. If the OPTIONS response lacks the proper CORS headers, the browser never sends the real request at all.

A typical Chrome DevTools error reads: Access to fetch at 'https://api.example.com/data' from origin 'https://app.example.com' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two origins appear in this message. The URL after "fetch at" is the target server, the resource the code tried to reach. The value after "from origin" is the page's own origin, the one making the request. Chrome is stating that the target server's response did not include an Access-Control-Allow-Origin header that matches the requesting origin, so the browser blocked the response from reaching JavaScript.

The most common variant is the missing header: No 'Access-Control-Allow-Origin' header is present on the requested resource. The server simply did not include the header at all.

When the console says Response to preflight request doesn't pass access control check, the server either did not respond to the OPTIONS request correctly or returned a non-2xx status code for it.

Redirect variant: Redirect is not allowed for a preflight request. Developers commonly misdiagnose this one. It occurs when the URL triggers a redirect before reaching the application handler. Typical culprits include HTTP-to-HTTPS upgrades, trailing-slash normalization (e.g., /api/data redirecting to /api/data/), or a load balancer rewriting URLs. The browser's preflight OPTIONS request follows the redirect, and the Fetch specification (§4.8) forbids following redirects on preflight requests, so the entire flow fails. Fix the URL so no redirect occurs.

Credential variant: The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'. When fetch is called with credentials: 'include' or XMLHttpRequest sets withCredentials = true, the server must respond with the exact requesting origin, not *. The browser will block JavaScript access to the response if a wildcard is used with credentials.

Nginx's if directive creates a new configuration context. Any add_header inside an if block discards all add_header directives from the enclosing scope.

Why the if block contains all headers and return 204: By placing return 204 inside the if block, the OPTIONS request is fully handled there and never reaches the outer add_header directives or proxy_pass. Use an explicit origin allowlist. Avoid * when credentials are involved; the browser will block JavaScript access to the response if a wildcard is used with credentials: 'include'.

Restrict Access-Control-Allow-Methods to only the methods the API actually uses. Listing every HTTP method widens the attack surface unnecessarily.

The application cleared the fields, but an asynchronous request still held the old values and updated the screen when it finished. Similar problems occur when drafts remain in browser storage, validation messages retain personal details, or a component’s internal state survives a visual reset.

A customer wants a $480 refund for a faulty part of a shipment he received. After waiting for 30 seconds for the payment API to process the refund, the customer support AI sends another request. It ultimately is fulfilled. However, as it turns out, the first request had also been fulfilled. The only thing missing was the notification of the refund for the customer. So the customer received two refunds of $480 each instead of the one he was asking for.

The AI was acting appropriately within its given constraints; the surrounding system couldn’t tell if the initial action had already been taken and failed to deliver the result. A well-known problem in distributed systems is gaining more notoriety as AI-powered agents increasingly perform actions beyond simply generating text. Idempotence is the solution to this problem.

Idempotence means an action can be performed multiple times with the same result as performing it once. This concept is particularly important for an AI agent that issues refunds, creates tickets, sends emails, or updates business applications.

AI agents as distributed software components have simple processes.

Think → choose a tool → call an API → receive a result → decide what to do next.

As we have outlined, many of the agent actions will utilize services and networks that can have issues from time to time. Consider the simple action of asking a payment provider to issue a refund. There are three possible outcomes:

The payment service never gets the request.

The refund went through, and the agent got the answer.

The refund went through, but the agent never received it back.

The most severe case, however, is when the time to complete an operation exceeds the timeout, but the operation does complete successfully. Since there is no answer, the software agent never learns of the operation's successful completion and must attempt to complete the operation again.

Distributed systems have dealt with the issues of unreliable networks for a long time already (retries, duplicate requests, etc.). By introducing agents, we give the software more freedom to choose when and how to proceed.

Consider an agent with these tools: search_customer(), check_inventory(), refund_payment(), send_email(), create_order(), delete_account()

Calling search_customer() twice will usually not cause much trouble.

In other words, an agent runtime should be able to tell if a tool only gets data or makes changes to the outside world. In the second group are things like sending money, getting money back, placing orders, writing messages, making accounts, and changing infrastructure.

There are side effects to these treatments. It's risky to think that agents can just retry every failed tool call as they get access to more business systems.

One common way to handle the duplicate requests issue is to implement idempotency keys.

Idempotency-Key: refund-order-123-run-842

The service stores the idempotency key and the result of processing the associated request.

It allows the refund to be processed the first time the idempotency key is sent to the service by the agent. Thereafter, if the response to the refund is lost and the agent attempts to resubmit the refund with the same idempotency key, the service will recognize that the refund has already been processed and return the previous result to the agent instead of processing another refund.

Many of the world’s leading payment companies, including Stripe, PayPal, and Square, use idempotency keys to allow their customers to safely retry requests.

However, one important rule for agents is that the agent software or workflow system—not the AI model—creates the idempotency key, and it is up to date.

By the time the model retries the same step, the Operation ID will have remained the same. This means the system can recognize the request as another attempt to execute the same action as before and not a new action.

Things could be easy if we could tell the model to ‘remember if it has already issued one of these before issuing another.' But even in the production environment, this approach is not sufficient. The agent could crash. The context could go away. The workflow could be taken off to be executed on another machine. The problem is that the model lacks sufficient information about what has or has not happened in external systems. Instead, the system should keep a record of the execution state outside of the model. The model determines what should happen. The runtime determines safe execution.

Modern agent tools include a name, description, and input parameters for the production system. More importantly, the agent runtime also needs to know about the behavior of the individual tool. For example, ‘refund_order’ modifies the application outside this tool, so the operation must be re-executed with the same actionID used for the initial failure. Also, as an example, refunds larger than $5,000 require manual approval. On the other hand, a ‘search_customer’ action is only a read, so re-execution can occur without human intervention. Based on this information, the OS makes decisions about the danger of the individual tool call. Automatic re-execution is still possible, even if the search fails. However, refunds require a bit more caution to avoid double posting of money. Thus, in addition to the input models for the AI tools used in real life, so-called “execution rules” are also required. These rules state when re-execution, increased security, or human intervention is required.

Suppose an AI agent were to perform the following three actions: 1) Make whole the customer, 2) Send a confirmation email with the order update and a proof, and 3) Check the status of the order in process. We had described how stopping the AI from paying out twice was only half the problem; the system also needed to know where the work had stopped. To that end, we’d like to introduce the concept of durable execution. For durable execution, the agent must do more than simply remember the actions it has taken. We need to keep track of the progress of the actions of the AI. The refund action was marked complete, but the email action was not sent yet. Thus, when the agent is restarted, it continues from where it left off rather than starting over. To create reliable AI agents, we need a few things: stable operation IDs, irrevocable actions, durable state, controlled retries, and logging. There are also cases where one wants to perform a recovery or compensating action (e.g., the agent makes a reservation but then fails to perform the subsequent action). The recovery action would be to cancel the reservation that had been made.

While controls with a person in the loop are mostly suitable for fine-grained actions that cannot be undone, idempotence ensures that an action is not accidentally executed more than once, and human approval is required to decide whether the action should be executed in the first place. This point is illustrated by an example: An employee correctly approves a $10,000 refund. However, the payment request somehow times out and is automatically re-executed several times. Without adequate idempotency security, the customer might end up with even more refunds than intended. Note, however, that a person’s approval cannot prevent double killing in such high-risk agent processes. Therefore, additional decision controls and corresponding execution controls are usually required to ensure that all actions are executed safely and correctly.

There are 5 simple questions that need to be answered before allowing an AI agent to take real-world actions.

Improving the model alone will not make the agent reliable unless we can answer all of these questions.

Much work in AI today focuses on making agents smarter, better at planning, and better to use as tools. But running agents in production has its own problems. API calls time out, processes crash, networks fail, and responses get lost, and the smartest agent can try again and again until it works. These are not new problems. Engineers working on distributed systems have been struggling with these same issues for decades. So long as the AI agent is confined to a simple test environment, of course it can query payment systems, customer information, and corporate tools. But when it is turned loose on the production corporation’s infrastructure (with all the payment systems, customer information, and corporate tools that entails), it must also be reliable. A smart model can figure out that a customer is due a refund. But a strong system can only give that customer a refund once. So the important question to ask of an AI agent before turning loose on it is, "Some powerful new tool: what happens if the action worked?" The answer will tell you whether or not the AI agent is currently able to operate reliably in production.

AI image generation has become a normal part of many web projects. However, the image a model produces is rarely the image a browser should receive. A single large PNG straight from a generator can weigh several megabytes, ignore the visitor's screen size, and slow down your Largest Contentful Paint (LCP) before the page has a chance to impress anyone.

The good news is that the fix is not complicated. If you treat the generated image as a high-quality master file and run it through a small, repeatable pipeline, you can ship images that look sharp on every device and load quickly on slow connections.

This tutorial walks through that pipeline from start to finish: generating at the right size and aspect ratio, choosing modern formats, creating responsive variants with Node.js, writing srcset and sizes correctly, and avoiding the performance mistakes that show up most often in audits.

Image generators are built to produce visually impressive results, not optimized web assets. Their output is usually a single file at one resolution, often in PNG format, and sometimes with an aspect ratio that does not match your layout.

Sending that file directly to the browser creates three problems. First, mobile visitors download far more pixels than their screens can display. Second, PNG is a poor choice for photographic images because its lossless compression produces large files. Third, without width and height information, the browser cannot reserve space for the image, which causes layout shifts as the page loads.

A web pipeline solves all three. You generate one master image, export multiple sizes in modern formats, and let the browser choose the best version for each visitor.

Optimization starts before you export anything. The most efficient pipeline begins with an image that already fits your layout.

Look at where the image will appear and note its aspect ratio at each breakpoint. A full-width hero might use 16:9 on desktop, while a blog thumbnail might use 4:3 or 1:1. Then identify the largest size the image will ever display. For a full-width hero, that could be 1920 pixels wide on large screens, or more if you support high-density displays at wide viewports.

Your master image should be at least as large as that maximum rendered width. Upscaling a small image later almost always introduces blurriness or artifacts.

Modern image-generation models can follow detailed instructions, so describe the technical requirements in your prompt, not just the subject. Specify the aspect ratio, intended display size, visual style, and any areas that need to remain clear for HTML text. The exact controls available will depend on the tool you use, so check its official documentation before building a workflow around a particular feature.

A practical web-focused prompt might read: "hero image of a modern home office at sunrise, soft natural light, calm blue and warm wood tones, clear empty space on the left third for headline text, no text or logos in the image."

That last instruction matters. Avoid baking headlines or buttons into images. Text inside an image cannot be translated, resized for accessibility, or indexed reliably, and it often becomes unreadable at small sizes. Keep text in HTML and use the image for visuals only.

Once you have a master file, decide which formats to serve. For most photographic and illustrative AI images, a combination of AVIF, WebP, and JPEG covers every modern browser while keeping file sizes small.

AVIF typically offers the strongest compression for photographic content and is supported by all major modern browsers, including Safari 16 and later. WebP is slightly less efficient but encodes faster and has near-universal support. JPEG remains a reliable fallback for older browsers and email clients.

Use PNG only when you specifically need lossless quality, such as for sharp-edged graphics or screenshots. Both AVIF and WebP support transparency, so you rarely need PNG for images with transparent backgrounds anymore.

AVIF and WebP quality scales do not map directly to JPEG quality, so compare outputs visually at the sizes your users will actually see. Smooth gradients, which are common in AI-generated skies and backgrounds, are especially prone to banding at aggressive settings.

The MDN responsive images guide explains how srcset and sizes work. The srcset attribute lists available image files and their intrinsic widths. The sizes attribute tells the browser how wide the image will be displayed in the layout. With both pieces of information, the browser can choose the smallest file that still looks sharp on the visitor's screen, including high-density displays.

The most common mistake is omitting sizes or leaving it at 100vw for images that are not full width. When that happens, the browser assumes the image fills the entire viewport and downloads a much larger file than necessary. Always match sizes to your actual CSS layout.

srcset="dist/hero-768.webp 768w, dist/hero-1440.webp 1440w, dist/hero-1920.webp 1920w"

srcset="dist/hero-768.jpg 768w, dist/hero-1440.jpg 1440w, dist/hero-1920.jpg 1920w"

alt="A modern home office at sunrise with a wooden desk and soft natural light"

Always include width and height attributes on your img element. Modern browsers use them to calculate the image's aspect ratio and reserve the correct space before the file downloads, which helps prevent Cumulative Layout Shift. In CSS, set the image to width: 100% and height: auto so it scales responsively while keeping its proportions.

Use descriptive file names, such as home-office-sunrise-1440.avif, instead of generic names like image-final-v3.png. Clear names make assets easier to manage and give search engines a small amount of extra context.

Catch coordinate-order bugs, distance mistakes, boundary cases, and bad spatial assumptions before they reach production.

A location endpoint can return HTTP 200 and still be wrong by kilometers. That is the uncomfortable part of testing geospatial APIs: ordinary API checks tell you whether the request worked, not whether the geography is correct.

Spatial bugs can look harmless in code review. Latitude and longitude get reversed. A radius value is treated as degrees instead of meters. A query works near one city but behaves differently elsewhere because the geometry column uses the wrong type. The JSON is valid, the tests are green, and the map is still wrong.

In this tutorial, you will build a small FastAPI endpoint backed by PostGIS and then test the spatial behavior directly. The examples use deterministic fixtures positioned at known distances, so the tests verify geography rather than only response structure.

The API exposes one endpoint: GET /places/nearby. A client sends longitude, latitude, and a radius in meters. The service returns nearby places as GeoJSON features, ordered by distance.

The useful part is not the endpoint itself. The useful part is the test strategy. We will check coordinate validation, exact distance boundaries, GeoJSON coordinate order, and the database query that turns a radius into a spatial filter.

Use a geography column when the API is answering human-scale distance questions in meters. PostGIS can then calculate on the ellipsoid instead of treating longitude and latitude as flat Cartesian coordinates.

The endpoint below validates longitude, latitude, and radius with Pydantic, then sends a parameterized query to PostgreSQL. The SQL uses ST_DWithin to filter candidates and ST_Distance to return the measured distance.

The API accepts lon and lat as separate named parameters. That removes ambiguity at the HTTP boundary. GeoJSON still uses [longitude, latitude] when the response is created.

Hard-coding two real businesses and hoping their distance is approximately right makes a fragile test. A better approach is to create test points at exact distances from a fixed origin.

PostGIS can generate those fixtures with ST_Project. In the test database, create one point 500 meters away, one 950 meters away, and one 1,500 meters away. Now a 1,000-meter query has an unambiguous expected result: the first two belong in the response and the third does not.

This is the first test that actually proves something spatial. It is not checking that the endpoint returns a list. It is checking that the 1-kilometer contract means what the API says it means.

GeoJSON coordinates are longitude first, latitude second. Many developers naturally think latitude first because that is how coordinates are commonly spoken. A validation layer can catch the most obvious reversal before the database ever sees it.

Longitude must be between -180 and 180. Latitude must be between -90 and 90. That will not catch every reversal, because both numbers may sometimes fall inside both ranges, but it catches a large class of failures and gives clients a useful error instead of a misleading map.

A response can be syntactically valid JSON and still violate the GeoJSON contract. Assert the geometry type and the coordinate order. For a known query point, longitude should appear in element zero and latitude in element one.

Spatial boundaries deserve their own tests. A place at 999 meters should be included in a 1,000-meter search. A place at 1,001 meters should not. A place exactly at the boundary should behave consistently with the predicate you chose.

ST_DWithin includes features whose distance is less than or equal to the supplied threshold, so document that behavior and test it explicitly.

Unit tests are useful for request validation, but mocking the repository layer removes the most important part of this API: PostGIS itself. Keep a small integration-test database and run at least a few tests against the real extension.

That catches mistakes that mocks cannot: geography versus geometry behavior, SRID mismatches, spatial indexes, units, and changes to SQL functions. A location API is one of the cases where a cheap database integration test buys a lot of confidence.

Correctness is only half the story. A radius endpoint that scans every feature will work in development and become painful at production scale. Add a GiST index and inspect the query plan.

The exact plan depends on your data and PostgreSQL version, but you should see the spatial index participating in candidate filtering. Treat an accidental sequential scan on a large production table as a regression worth investigating.

For a real project, I would split the tests into two groups. Fast validation tests run on every commit. PostGIS integration tests run in CI with a temporary PostgreSQL/PostGIS service.

The CI gate should cover invalid coordinates, zero or negative radius values, known-distance fixtures, boundary behavior, GeoJSON output, and at least one query-plan or performance sanity check for larger datasets.

This is more work than asserting status_code == 200, but it tests the thing users actually care about: whether the API's answer is geographically true.

Location APIs fail in ways ordinary web tests are not designed to notice. The response can have the right schema, the database call can succeed, and every field can look reasonable while the location itself is wrong.

The fix is not a giant testing framework. Start with a few spatial invariants you can prove: known distances, valid coordinate ranges, correct GeoJSON order, deterministic boundary behavior, and real PostGIS integration tests. Those checks turn geography from an assumption into something your CI pipeline can verify.

Most identity theft online starts with a password. Someone reuses one, a site gets breached, a fake login page collects a few more, and suddenly a stranger is inside an email account resetting everything else.

Passkeys are the industry’s attempt to remove that weak link. Apple, Google, and Microsoft all support them now, and plenty of big sites already offer them at sign-in. But do they actually make identity theft harder, or do they just move the problem somewhere else?

The honest answer is a bit of both. This article looks at how passkeys work under the hood, which attacks they shut down, which ones they don’t touch, and what you need to get right if you’re adding them to your own site.

Passwords have one basic flaw. They’re a shared secret. You know it, the server knows it (or a hash of it), and anyone who gets a copy can use it from anywhere.

That one flaw feeds most of the account takeover attacks you hear about:

Two-factor authentication helps, but not as much as people think. SMS codes can be intercepted or stolen through SIM swaps. One-time codes from an app can still be phished, because a fake site can simply ask for the code and pass it along in real time.

A passkey is a pair of cryptographic keys made for one specific website. It’s built on the WebAuthn standard from the W3C and the FIDO Alliance.

Here’s the short version of what happens:

Nothing secret ever crosses the network, and nothing secret is stored on the server. That small change has big consequences.

This is the biggest win. Every passkey is tied to the domain it was created for. Your browser won’t use a passkey for example.com on examp1e-login.com, no matter how real the page looks. That protection only holds if the attacker can’t fall back to a password or a weak recovery path, which is why the rollout advice later in this article matters.

With a password, the user is the one who has to spot the fake. With a passkey, the browser checks the domain for them. People get tired and click bad links. The browser doesn’t.

Each passkey is unique to one site, so there’s nothing to reuse. An attacker can’t take a passkey from one breach and try it somewhere else, because there’s no shared value to try.

If an attacker dumps a site’s database, they get public keys. A public key can check a signature, but it can’t make one. So the stolen data can’t be used to sign in as anyone.

This doesn’t make a breach harmless (more on that below), but it does remove the part that usually leads straight to account takeovers.

This is where a lot of articles get too optimistic. Passkeys protect the login step. Identity theft is a much bigger problem than that.

Every site needs a way back in for people who lose their phone. If that recovery path is an SMS code, an email link, or a support agent who can be talked into resetting things, attackers will go after that instead.

A site with passkeys and a weak recovery flow is only as strong as the recovery flow. This is the part developers most often underestimate. The OWASP Forgot Password Cheat Sheet is a good checklist for hardening it.

A breach that exposes names, addresses, birth dates, or government ID numbers is still a breach. Criminals don’t need to log in to your accounts to open new ones in your name. They can apply for credit, file fake tax returns, or run scams with that data alone.

Passkeys do nothing about this kind of identity theft. It’s why credit monitoring, freezes, and alert services are still worth knowing about even when your logins are locked down. If you want a broader look at how those tools compare, these theft protection insights from Cybernews cover what different services actually monitor.

Someone can still call a person, pretend to be their bank, and talk them into approving something. Passkeys make that harder because there’s no code to read out loud, but scammers adapt. User education still matters.

The good news is that the browser side is fairly small. Most of the real work happens on the server. The MDN guide to the Web Authentication API covers every option in detail, and the Passkeys Developer Resources site is a good source for implementation guidance.

Passkeys feel best when they show up right in the username field’s autofill menu. This is called conditional UI, and it lets you add passkeys without changing your login form much.

Users who have a passkey see it in the dropdown. Users who don’t can keep typing a password like before. That makes a gradual rollout much easier.

Verifying WebAuthn responses means checking the challenge, the origin, the relying party ID, and the signature. It’s very easy to get one of those subtly wrong. Use a well-maintained library instead of writing it yourself. SimpleWebAuthn is a popular choice for Node.js, and most major languages have solid options.

One thing that trips people up: signature counters. Older hardware keys increment a counter on every use, and some guides tell you to reject sign-ins if it goes backward. Synced passkeys often just report zero, so a strict counter check can lock out real users.

Password managers like 1Password and Bitwarden now store and sync them across platforms, and the FIDO Alliance has published specifications for moving passkeys and other credentials between providers, the Credential Exchange Format and its companion protocol. Passkeys close off phishing, credential stuffing, and password database leaks, which are the most common ways criminals take over accounts. That alone makes them one of the most meaningful security upgrades the web has seen in years.

But identity theft is bigger than logins. Weak recovery flows, stolen sessions, and leaked personal data all still lead to real harm, and passkeys don’t fix any of them on their own.

If you’re building for the web, treat passkeys as a strong foundation, not the whole house. Add them, make recovery just as solid, keep your sessions protected, and collect as little personal data as you can. That combination does far more for your users than any single feature.

The extension a developer installed three years ago can probably read everything they do in the browser today.

General online security advice from VPNpro and similar guides cover the network side of staying safe, but they cannot see what an extension does inside the browser. That layer is more the developer's responsibility. The risk is complicated, but the fix is simple: request fewer permissions, narrower host access, and less data, and review every update. Here is a walkthrough of each.

Think about what a developer has open on a normal day: a cloud console, a staging dashboard, a private repo, maybe webmail. One over-permissioned extension sees all of it.

The most common mistake is asking for broad access early and planning to trim it later. Later rarely arrives.

This also helps adoption. People hesitate when an extension asks to read every site they visit. A narrow request looks, and is, more trustworthy.

Analytics and error logging are where good intentions leak. A crash report that includes the full page URL may contain a session token in the query string. A “usage event” may capture page titles from internal tools.

The most secure approach is to collect only the data a feature needs and to process the data locally if possible. When data has to be sent, it should be stripped down to the absolute minimum. Avoid sending query strings, and truncate URLs to the domain name where possible. Never send page content if it is not absolutely necessary.

Remote code is another trap. Manifest V3 restricts remotely hosted code for a good reason. A script fetched at runtime can modify its behavior after the fact, and one can’t audit what it will do in the future. Bundle everything and the code that is reviewed will be identical to the code that is run.

A good extension today can become a risky one next year. Two patterns keep repeating.

Ownership changes. Popular extensions get sold, and the new owner ships an update with tracking or worse. The Great Suspender, a widely used tab tool, ended up flagged as malware after a change of hands.

Compromised publisher accounts. If an attacker phishes the developer account, they can push a malicious update to every existing user. Cyberhaven’s extension was hit by a phished administrator account in late December 2024.

The defenses are mostly boring, which is a good sign. Hardware-key two-factor authentication on the publisher account, a short list of people allowed to publish, and a review step before each release stops most of it. Lockfiles, pinned versions and regular dependency audits cover the code side.

Teams that only install extensions can apply the same thinking. Keep an approved list, review updates that change permissions, and remove anything nobody uses. Following security news is worthwhile too, since incidents involving popular extensions tend to be reported publicly.

It is only one layer, though. A VPN protects traffic in transit. It does nothing about an add-on that reads page content inside the browser, so it never replaces a proper permission review.

Simpler habits do more here. A separate browser profile for development keeps test extensions away from personal accounts. Fake or low-privilege accounts for testing avoid exposing real credentials. And installers for any tool, VPN clients included, should come from the official site or store, never from a mirror.

Safe extensions come down to restraint. Ask for less access, collect less data, send less off the device, and explain more to the user. Developers who treat every permission as a liability end up with extensions people can trust, and teams that review what they install avoid the worst surprises.

Most articles on this topic stop at the scary part. This one is written for people who build websites, so we’ll go a bit further: what goes into a fingerprint, what the collection code actually looks like, and what you can change in your own projects.

Think of a fingerprint as a stack of clues rather than a single value. Your time zone is shared by millions of people. So is your screen resolution. Put twenty clues like that together, though, and the crowd shrinks fast.

Here’s roughly where the clues come from.

HTTP headers. Before any JavaScript runs, every request already tells the server a lot. The User-Agent string and the Accept-Language header give away your browser, its version, your OS, and your languages. Chromium browsers also send Client Hints.

JavaScript APIs. Plenty of everyday APIs leak device details. screen.width and screen.height, navigator.hardwareConcurrency (your CPU core count), navigator.deviceMemory (Chromium only), navigator.platform, and your time zone all add something. Plugin lists used to be a goldmine, but modern browsers now return a fixed, generic list, so that one’s mostly dead.

Rendering. This is the clever bit. Ask two computers to draw the exact same text, and the pixels won’t match perfectly. Fonts, graphics drivers, and the GPU itself all nudge the output slightly. Same browser, same version, different hardware, different result.

Network details. Your IP address, connection type, and even the way your browser sets up a TLS connection can help. IPs change, so these clues are less reliable. Trackers mostly use them to back up a match they already suspect.

How unique does this make you? Back in 2010, the EFF’s Panopticlick study tested around 470,000 browsers and found that about 84% of them had a unique fingerprint. (The project still exists, now called Cover Your Tracks.) Later studies with bigger samples found lower numbers, especially on phones, since a lot of phones share near-identical hardware. The percentages move around, but the basic idea hasn’t changed.

Audio fingerprinting is sneakier. The script generates a sound, runs it through an AudioContext, and hashes the result. Different audio stacks produce slightly different numbers.

It’s worth remembering that the Canvas API, WebGL, and the Web Audio API were built for charts, games, and music apps. Tracking is a side effect of how much they expose. The W3C’s guidance on mitigating fingerprinting in web specifications covers how standards authors try to avoid adding new signals.

You might not write a single line of fingerprinting code yourself and still end up involved. There are three common ways that happens.

Your third-party scripts can do it without asking you. Analytics tags, ad scripts, chat widgets, social buttons. Each of them can call the same APIs your own code can. If your page loads fifteen of them, that’s fifteen possible fingerprinters. Checking what each script does has quietly become part of the job.

Browsers are closing the door. Chrome froze most of the User-Agent string and moved detailed info into Client Hints. Safari has Advanced Fingerprinting Protection. Firefox blocks known fingerprinting scripts, and Brave randomizes values returned by fingerprintable APIs. If your site depends on the old, wide-open APIs, you’re building on ground that’s shrinking every release.

Most of this comes down to one rule: collect less, and know why you’re collecting what’s left.

Search your codebase for the high-entropy stuff: canvas exports, WebGL renderer lookups, font detection, and calls to navigator.userAgentData.getHighEntropyValues(). If a feature still works without them, take them out.

In many teams, the biggest win is boring. Someone added a fingerprinting library years ago for one fraud check, nobody reviewed it since, and it’s still loading on every page. Deleting it helps more than any clever fix.

The classic User-Agent string packs browser, exact version, OS, and CPU architecture into one header. Client Hints break that apart so you only get what you ask for.

By default, Chromium browsers already send three basic hints: Sec-CH-UA, Sec-CH-UA-Mobile, and Sec-CH-UA-Platform. For most sites, that’s plenty, and you don’t need to request anything extra. If a feature really does need more detail, ask for that one hint with Accept-CH:

Skip full version numbers, architecture, and device model unless you have a real reason. Each extra hint makes your visitors a little easier to tell apart.

Keep in mind that only Chromium-based browsers support User-Agent Client Hints. Firefox and Safari won’t send them, so you’ll need a fallback. Where you can, feature detection beats browser detection anyway.

Here’s an uncomfortable truth: once a script runs on your page, it can call canvas, WebGL, and audio APIs, and there’s no header that switches those off. What you can control is which scripts run and how close they get to your page.

None of these is a silver bullet. Together, they cut down how much code gets the chance to fingerprint your users at all.

If your app draws on canvas (dashboards, editors, browser games), that output can be fingerprinted too. Try not to hand raw canvas data to third-party scripts.

Fonts count as well. Load fifteen unusual web fonts and you’ve given every script on the page an easy font fingerprint. A system font stack blends in better, and for interface text, most users won’t notice the difference.

Sometimes you’ll want to keep a fingerprint, for example to flag logins from a device you haven’t seen before. That’s fine, as long as you treat it with care:

Fix the feature. Don’t ask users to turn their protection down. Browsers are only going to get stricter from here.

What works better is a browser with fingerprinting protection built in, such as Brave, Firefox on strict settings, Safari, or Tor Browser. These either add noise to the signals or make everyone look the same. Extensions that block canvas and font reads can help too. So can simply updating your browser, since each release tends to remove a few more leaky details.

No single tool will stop fingerprinting completely. The good news is that it doesn’t have to. Fingerprinting works on probabilities, so making the signals noisier is often enough to break the match.
