Accessibility is an essential part of modern web development. A website may look polished and function correctly with a mouse, yet remain difficult to use for people who rely on keyboards, screen readers, magnification, or other assistive technologies.

Building accessible interfaces does not necessarily require complicated frameworks or extensive JavaScript. Many improvements begin with choosing the right HTML elements, providing clear labels, maintaining visible focus indicators, and using CSS that accommodates different user needs.

For developers, the goal is to create interfaces that remain understandable and usable across different devices, input methods, and accessibility requirements.

This article explores practical HTML and CSS techniques that can help make web interfaces more inclusive without adding unnecessary complexity.

Semantic HTML gives elements a meaningful purpose. Browsers and assistive technologies can use this information to communicate the structure of a page to users.

For example, a clickable div might appear to be a button, but it does not automatically provide the keyboard behavior and accessibility semantics of a native button.

It may look like a button after styling, but keyboard support and button semantics must be implemented separately.

A native button is generally a better choice:

Native buttons support keyboard interaction and communicate their role to assistive technologies without requiring custom ARIA attributes.

The same principle applies to navigation links, headings, lists, and form controls. Use elements according to their intended meaning rather than choosing them solely for their default appearance.

Not everyone uses a mouse or touchscreen to navigate a website. Some users rely entirely on a keyboard or an alternative input device that simulates keyboard interactions.

Interactive elements should therefore have a logical focus order and a visible focus indicator.

A simple CSS rule can improve focus visibility:

The :focus-visible pseudo-class allows browsers to display focus indicators when they determine that the indication is appropriate, commonly during keyboard navigation.

Developers should avoid removing outlines without providing an effective alternative. A link or button that receives focus but gives no visual indication can make navigation confusing.

For larger applications, keyboard testing should cover menus, dialogs, dropdowns, forms, and any custom interactive components.

A useful test is to navigate the page using only the Tab, Shift+Tab, Enter, Space, and arrow keys where appropriate. Users should be able to identify their current position and operate the interface without becoming trapped in an unexpected focus sequence.

Forms are a common source of accessibility problems. Placeholder text alone is not a reliable replacement for a persistent label because it disappears or becomes less visible when users enter information.

An explicitly associated label provides a more dependable structure:

The for attribute on the label matches the input's id, creating an explicit association.

The autocomplete attribute can help browsers recognize the type of information being requested. The required attribute also communicates that the field must be completed.

However, browser validation alone does not guarantee accessible error handling. When validation fails, applications should explain the problem clearly and help users identify the field that needs attention.

For more complex forms, developers can associate additional instructions with controls using aria-describedby and provide appropriate error messages.

Accessible interfaces should accommodate different viewport sizes, text preferences, and reading needs.

Fixed dimensions can cause problems when text becomes larger or content changes length. A card with a fixed height, for example, may clip a heading when users zoom in.

Instead of forcing content into a rigid box, allow the layout to grow:

The clamp() function allows the heading size to scale within a defined range. The line-height gives body text room to breathe, while overflow-wrap helps prevent unusually long strings from overflowing their container.

These settings are starting points rather than universal requirements. Developers should test the actual content, fonts, languages, and supported zoom levels.

Text needs sufficient contrast against its background to remain readable for users with low vision or reduced contrast sensitivity.

A color combination that looks attractive in a design mockup may be difficult to read when displayed on a real device.

For example, consider a secondary label on a white background:

This darker gray generally provides stronger contrast than a very pale gray on white.

Developers should measure actual color combinations rather than relying on visual judgment alone. Under WCAG 2.2, the usual minimum contrast ratio is 4.5:1 for normal text and 3:1 for large text at Level AA.

Contrast requirements also apply to relevant graphical elements and user interface components. A contrast checker can help identify combinations that need improvement.

Color should not be the only way information is communicated. For example, an invalid field should have a clear error message or another suitable indicator rather than relying solely on a red border.

Animations can improve feedback and communicate changes, but excessive motion may cause discomfort for some users.

CSS media queries allow developers to respect a user's reduced-motion preference:

This example removes the transition and hover movement when reduced motion is requested.

The appropriate response depends on the interface. Some animations communicate important information, so developers should ensure that removing decorative movement does not remove essential feedback or functionality.

Reduced-motion support should be part of the initial design process rather than an afterthought.

Images often communicate information that is not available in surrounding text. Users who cannot see an image need an appropriate text alternative when that information matters.

The alternative text describes the image's relevant purpose rather than listing every visual detail.

Decorative images should generally use an empty alternative:

This allows assistive technologies to skip an image that does not contribute meaningful information.

Complex images, such as detailed charts, may require a longer explanation elsewhere on the page. The alternative text should be based on what users need to understand, not simply on the image filename.

Automated accessibility tools can identify many common problems, including missing labels, some contrast failures, and certain structural issues. However, automated checks cannot determine whether every interaction makes sense to a real user.

A practical testing process should include:

Navigating the interface with a keyboard.

Checking focus order and focus visibility.

Testing forms with missing or invalid information.

Zooming in and checking for clipped content.

Testing meaningful content with a screen reader.

Running an automated accessibility audit and investigating its findings.

The W3C Web Accessibility Initiative provides standards and educational resources for understanding accessibility requirements. WCAG is a useful reference for evaluating web content, but meeting individual technical checks does not automatically guarantee a usable experience.

For important applications, testing with people who use assistive technologies can reveal problems that automated tools and developer assumptions may miss.

Accessible web development begins with thoughtful implementation choices. Semantic HTML, clear form labels, visible keyboard focus, readable typography, sufficient contrast, and reduced-motion support can significantly improve how people interact with a website.

These practices also help create more consistent and maintainable code. Native browser behavior often eliminates the need for custom interaction logic, while clear markup makes interfaces easier to understand and test.

Accessibility should not be treated as a final checklist applied after development. By considering different user needs from the beginning, developers can build web interfaces that are more inclusive, robust, and practical for everyone.

Creating responsive website layouts is a fundamental part of modern front-end development. Developers need interfaces that work across mobile phones, tablets, laptops, and large desktop displays without requiring separate markup for every screen size.

CSS Grid provides a powerful way to organize content into rows and columns. Unlike older layout techniques that often require additional wrappers or complicated positioning, Grid allows developers to define two-dimensional layouts directly in CSS.

When combined with flexible sizing functions, intrinsic layout techniques, and a small number of carefully chosen media queries, CSS Grid can make responsive interfaces easier to build and maintain.

This article explores practical CSS Grid techniques for creating flexible layouts, avoiding common mistakes, and writing cleaner responsive stylesheets.

CSS Grid begins by defining a grid container. Its direct children become grid items, which can be positioned within the resulting layout.

The layout can be defined with a few CSS declarations:

The display: grid declaration establishes the grid formatting context. The grid-template-columns property creates three equal-width columns, while gap controls the spacing between grid items.

This works well when the available space can accommodate three columns. On a narrow screen, however, the columns may become too small. Responsive sizing can solve this without requiring a separate rule for every device.

One useful CSS Grid technique is combining repeat(), auto-fit, and minmax().

This declaration allows the browser to create as many columns as comfortably fit within the available space.

The expression has three important parts:

auto-fit fits available tracks into the grid and collapses empty repeated tracks when appropriate.

minmax() establishes a flexible range for each column.

The nested min(100%, 16rem) also helps prevent the minimum column size from exceeding the container's available width on narrow screens.

As the container grows, more columns can fit. As it shrinks, items naturally move onto additional rows.

This technique is especially useful for product listings, article cards, image galleries, and resource directories.

It does not eliminate the need for testing. Content length, available space, and the desired visual hierarchy may still require additional layout rules.

The auto-fit and auto-fill keywords look similar, but they handle empty repeated grid tracks differently.

With auto-fill, the browser preserves the space for tracks that can fit within the grid, even when there are not enough items to occupy them.

With auto-fit, empty repeated tracks collapse after placement, allowing occupied tracks to expand into the available space.

This can be a good choice for a gallery where a small number of images should expand to fill the available row.

If the design needs to preserve the expected track arrangement even when some positions are empty, auto-fill may be more appropriate.

Neither option is universally better. The choice depends on whether the layout should expand existing items or preserve space for potential additional items.

One common CSS Grid problem occurs when content forces a column to become wider than expected.

Grid items can have automatic minimum sizes influenced by their content. Long URLs, unbroken strings, wide images, and large code examples may therefore cause overflow.

The zero minimum in minmax(0, ...) gives the tracks more flexibility, while min-width: 0 helps individual grid items shrink when their content would otherwise create an unwanted minimum width.

For code blocks, horizontal scrolling may be preferable to forcing long lines to wrap and changing their formatting.

These techniques address common overflow problems, but the best solution depends on the type of content and how users are expected to interact with it.

Responsive layouts do not always need explicit breakpoints. CSS Grid can often determine a suitable arrangement from the available space and the intrinsic dimensions of its content.

This creates flexible columns with a preferred minimum size of approximately 20rem, unless the container is narrower.

For a card collection, this may be enough to provide a responsive layout without a collection of device-specific media queries.

However, some designs require more deliberate changes. A navigation bar might need to become a menu button, or a sidebar may need to move below the primary content. These are behavioral or structural decisions that intrinsic sizing alone cannot make.

A useful approach is to let Grid handle flexible dimensions and use media queries when the design genuinely needs a different arrangement.

CSS Grid is powerful, but it is not always the simplest tool for the job.

Flexbox is often a better fit for a one-dimensional layout, such as aligning a group of buttons in a row or arranging an icon beside a label.

Grid is generally useful when relationships between rows and columns matter, while Flexbox is particularly effective when content flows primarily along one axis.

Both systems can work together. A page can use Grid for its overall structure and Flexbox for individual components.

The best layout method is the one that expresses the design clearly without introducing unnecessary rules.

A grid that works with three short placeholder headings may behave differently when real content is introduced.

Before shipping a responsive layout, developers should test:

Empty or partially populated card collections.

Intermediate widths where columns begin to feel cramped.

Browser developer tools make it easy to inspect grid tracks and experiment with container dimensions.

It is also useful to test the actual content rather than relying exclusively on idealized examples. Realistic content exposes sizing problems that placeholder text often hides.

CSS Grid provides a flexible foundation for responsive web layouts. Features such as minmax(), auto-fit, named grid areas, and intrinsic sizing allow developers to create adaptable interfaces with relatively little CSS.

The most effective layouts combine these features thoughtfully. Let Grid manage two-dimensional structure, use Flexbox for simpler one-dimensional arrangements, and introduce media queries when the design requires a meaningful change.

By accounting for intrinsic content sizes, preventing overflow, and testing realistic scenarios, developers can build responsive interfaces that are easier to understand and maintain.

Claude Code hooks solve a problem that every developer running agentic coding sessions eventually hits: the AI drifts from project conventions, and soft instructions in the prompt cannot prevent it. A popular r/Frontend post captured this precisely. The developer reported that Claude Code wrote roughly 1,000 lines of code for a simple helper function that already existed in a project dependency. The prompt stated the project conventions. Claude ignored them anyway. The result was duplicated logic, bloated output, and wasted review time.

The root cause is structural, not incidental. Prompt-based instructions are probabilistic. They work well in short sessions, but as the context window fills during extended agentic loops, earlier instructions degrade in influence. Tool outputs, file contents, and intermediate reasoning bury the initial convention reminders. A long enough session means the agent effectively forgets what it was told. Any enforcement mechanism that relies solely on prompt text will exhibit this degradation pattern.

Claude Code hooks offer an alternative enforcement mechanism: shell scripts that bind to lifecycle events inside the agent loop. These scripts use exit codes to enforce rules. Exit 0 means proceed. Exit 2 blocks the action, and the script's stderr is surfaced to Claude as feedback. Any other non-zero exit code is a non-blocking error. This is deterministic. No matter how full the context window gets, an exit code of 2 stops the action every time.

By the end of this article, you will have two working hooks: a pre-write gate that forces Claude to verify whether an implementation already exists before writing new code, and a post-edit lint and format pipeline that runs Prettier and ESLint on every changed file. Together, these hooks catch duplicated or unnecessary code before it lands and enforce style rules automatically.

Prerequisites: Claude Code installed and functional; a Node.js project with Prettier and ESLint already configured; jq installed (brew install jq / apt install jq); Prettier and ESLint must be installed as local node_modules dependencies (not relied upon via npx remote fetch); and basic familiarity with Bash scripting.

Hooks operate on an event-driven model. They fire at specific points in Claude Code's agent loop, intercepting actions before or after they occur. Four lifecycle events are relevant:

PreToolUse fires before any tool call executes. This is the interception point for blocking actions. For file-write gating, the tool names to match are Write, Edit, and MultiEdit. You can also match against Bash for command-level gating.

After a tool call completes, PostToolUse runs. This is the point for validation: linters, formatters, or test suites check the result of an edit. Because the tool has already executed, an exit code of 2 from a PostToolUse hook does not block the original action. Instead, it surfaces the script's stderr as feedback to Claude, which can then issue a follow-up edit to correct the issues.

When the user submits a new prompt, UserPromptSubmit fires. This is useful for resetting state between conversational turns.

Notification fires when Claude sends a notification. Non-zero exit codes from Notification hooks do not block any action. (The documentation does not specify any exit-code effect for this event type.) This makes it useful only for logging or side effects.

The contract is simple. When a hook script exits with code 0, the action proceeds normally. Exit code 2 is the blocking signal. For PreToolUse, exit 2 blocks the tool call and the script's stderr is fed to Claude as feedback. For PostToolUse, the tool has already completed, but exit 2 surfaces the script's stderr to Claude, which can take corrective action. The stderr content becomes part of the agent's reasoning context, which is what makes hooks corrective rather than merely restrictive. Any other non-zero exit code counts as a non-blocking error, not a block.

Configure hooks in the hooks object within .claude/settings.json for project-level scope or ~/.claude/settings.json for user-level scope. Each entry is keyed by event name and contains an array of matcher groups. Each group pairs an optional matcher (a pattern matching specific tool names) with a hooks array of one or more handlers, and each handler declares a type (command for a shell command) plus the command to execute.

This skeleton shows the structural pattern. The matcher field accepts pipe-delimited tool names. When a PreToolUse event fires for a Write tool call, Claude Code checks whether any hook entry matches, then executes the command, piping a JSON payload to its stdin containing the tool name and parameters.

The following configuration wires together all three lifecycle events. The PreToolUse entry fires before Write, Edit, or MultiEdit tool calls and blocks the first write attempt per prompt, printing a checklist for Claude to verify before proceeding. The PostToolUse entry fires after those same tool calls complete and runs Prettier (auto-fix) then ESLint (check) on the changed file. If ESLint finds issues, it exits 2 and prints them to stderr, surfacing the lint errors as feedback for Claude to self-correct. The UserPromptSubmit entry resets the pre-write gate so it re-arms on every new user prompt. No matcher is needed for UserPromptSubmit because this event has no associated tool. The reset is delegated to a dedicated script to ensure $PPID is evaluated consistently.

Important: Before relying on the UserPromptSubmit reset, verify that $PPID expands to the same value in this context as it does inside the hook scripts. You can add a temporary diagnostic command — echo "PPID=$PPID" >> /tmp/hook-ppid.log — to both reset-gate.sh and pre-write-gate.sh and compare the logged values. If they differ, the gate reset will not function correctly.

All three lifecycle events work together as a system: UserPromptSubmit resets state, PreToolUse enforces the gate, and PostToolUse validates output.

On the first file-write attempt after each new user prompt, the hook exits with code 2 and prints a checklist to stderr, which Claude Code feeds to Claude as the reason for the block. The checklist asks Claude to verify three things before writing new code: Does an implementation already exist in the project? Is there a standard-library equivalent? Is there a well-maintained dependency that handles this? This directly addresses the r/Frontend scenario where Claude wrote 1,000 lines duplicating existing functionality.

After Claude acknowledges the checklist (by seeing the stderr feedback, adjusting its plan, and attempting the write again), subsequent writes within the same prompt pass through. The gate opens for the duration of that conversational turn and re-arms when the user submits a new prompt.

The stateful pattern uses a temp file to track whether the gate has been opened. The file path follows the pattern /tmp/claude-hook-gate-$PPID. When the file exists, the gate is open and writes proceed. When it does not exist, the gate is closed and writes are blocked.

The UserPromptSubmit hook entry in settings.json handles the reset by running scripts/reset-gate.sh, which deletes this temp file, so every new user prompt re-arms the gate automatically.

Note on shared systems: The temp file path is predictable and based on a process ID, which can be a symlink attack surface on multi-user systems. On shared machines, consider using mktemp -d to create a session-specific directory and store the gate file there, or ensure /tmp permissions are appropriately restricted.

Each hook invocation spawns a new child process, so $PID (or $$) changes on every run. $PPID refers to the parent of the hook script. In the expected case, this is the Claude Code session process, which ties the gate state to the session rather than to the ephemeral script invocation.

However, this assumption should be verified in your environment. If Claude Code launches hooks through an intermediate shell (e.g., sh -c "bash scripts/..."), $PPID may point to that intermediate shell rather than the Claude Code session, and the value may change between invocations. Before relying on this mechanism, add a diagnostic hook that logs echo "PPID=$PPID" >> /tmp/hook-debug.log and confirm that the value is stable across multiple hook calls within a single session. If it varies, replace $PPID with a fixed session identifier.

This script reads the JSON payload from stdin, extracts the tool name and file path with jq in a single invocation (avoiding double-fork and potential echo mangling), checks for the gate file, and either allows or blocks the action. On the first blocked attempt, it prints the checklist and creates the gate file so the immediate retry succeeds. The UserPromptSubmit hook runs scripts/reset-gate.sh to delete the gate file and re-arm everything for the next prompt.

Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Website performance is an essential part of modern web development. A visually attractive website may still frustrate users if its pages load slowly, interactions feel delayed, or content shifts unexpectedly during loading. These problems can affect usability, accessibility, and business outcomes.

Improving performance does not always require a complete redesign or a complicated optimization framework. Many improvements come from understanding how browsers load resources, reducing unnecessary work, optimizing images, and delivering only the code a page actually needs.

For developers, the challenge is to identify which changes will make the biggest difference without introducing unnecessary complexity.

This article explores practical techniques for improving website performance using modern HTML, CSS, JavaScript, and browser development tools.

The first step in performance optimization is understanding how a website behaves under real conditions.

A page may feel fast on a powerful development computer but perform poorly on a mobile device or a slower network. Measuring performance helps developers identify the actual source of the problem instead of making changes based on assumptions.

Three important Core Web Vitals help evaluate the user experience:

Largest Contentful Paint (LCP): Measures when the largest relevant content element becomes visible.

Interaction to Next Paint (INP): Measures responsiveness across user interactions.

Cumulative Layout Shift (CLS): Measures unexpected visual movement during page loading and use.

Current good-target thresholds are an LCP of 2.5 seconds or less, an INP of 200 milliseconds or less, and a CLS of 0.1 or less, assessed at the 75th percentile of page visits.

Developers can investigate performance using Chrome DevTools, Lighthouse, and PageSpeed Insights.

Lab tests are useful during development, while real-user data can reveal problems that synthetic tests may not capture. Whenever possible, examine both.
