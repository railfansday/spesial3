Every frontend developer will eventually stare at a CORS error in the browser console, watching an API call fail for reasons that seem opaque. A CORS error fix requires understanding what the browser is actually telling you, matching that specific message to its root cause, and applying a targeted, security-conscious server configuration.

The scheme, host, and port together define an "origin." https://example.com and http://example.com are different origins (different schemes), as are https://example.com and https://api.example.com (different hosts). https://example.com and https://example.com:443 are the same origin because port 443 is the default for HTTPS, and browsers omit it in origin comparisons. The browser enforces the same-origin policy on client-side JavaScript reading responses, not on sending requests. This distinction trips up many developers: the server may still receive and fully process the request; the browser simply refuses to expose the response to the calling code. The request lands, the database row gets written, and the browser throws an error anyway. The policy exists to prevent a malicious page from silently reading sensitive data from another origin using the user's ambient credentials.

Cross-Origin Resource Sharing (CORS) is a controlled opt-in mechanism via HTTP response headers. The server signals to the browser that a specific foreign origin is permitted to read its responses. Four headers control the mechanism: Access-Control-Allow-Origin specifies which origin is allowed, and Access-Control-Allow-Methods declares which HTTP methods are permitted. Access-Control-Allow-Headers lists which custom or non-simple headers the client may send, while Access-Control-Allow-Credentials indicates whether the browser should expose the response to credentialed requests.

The browser does not treat all cross-origin requests equally. "Simple" requests use GET, HEAD, or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data, or text/plain, and no custom headers. A POST with Content-Type: application/json is not a simple request and triggers a preflight.

Simple requests go directly to the server, and the browser evaluates the CORS headers on the response. Anything else triggers a preflight request: an OPTIONS call the browser sends automatically before the actual request, asking the server whether the real request would be acceptable. If the OPTIONS response lacks the proper CORS headers, the browser never sends the real request at all.

A typical Chrome DevTools error reads: Access to fetch at 'https://api.example.com/data' from origin 'https://app.example.com' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two origins appear in this message. The URL after "fetch at" is the target server, the resource the code tried to reach. The value after "from origin" is the page's own origin, the one making the request. Chrome is stating that the target server's response did not include an Access-Control-Allow-Origin header that matches the requesting origin, so the browser blocked the response from reaching JavaScript.

The most common variant is the missing header: No 'Access-Control-Allow-Origin' header is present on the requested resource. The server simply did not include the header at all.

When the console says Response to preflight request doesn't pass access control check, the server either did not respond to the OPTIONS request correctly or returned a non-2xx status code for it.

Redirect variant: Redirect is not allowed for a preflight request. Developers commonly misdiagnose this one. It occurs when the URL triggers a redirect before reaching the application handler. Typical culprits include HTTP-to-HTTPS upgrades, trailing-slash normalization (e.g., /api/data redirecting to /api/data/), or a load balancer rewriting URLs. The browser's preflight OPTIONS request follows the redirect, and the Fetch specification (§4.8) forbids following redirects on preflight requests, so the entire flow fails. Fix the URL so no redirect occurs.

Credential variant: The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'. When fetch is called with credentials: 'include' or XMLHttpRequest sets withCredentials = true, the server must respond with the exact requesting origin, not *. The browser will block JavaScript access to the response if a wildcard is used with credentials.

Before modifying any server code, verify what the server actually returns by simulating a preflight request from the command line:

The -i flag prints response headers. -X OPTIONS sets the HTTP method to OPTIONS, mimicking the browser's preflight. The Origin header declares the requesting origin. Access-Control-Request-Method tells the server which method the real request would use. Access-Control-Request-Headers lists the custom headers the real request would include.

If these are absent, the server is not configured for CORS. If the response is a 301 or 302 redirect, the redirect variant is the culprit.

During local development, the least-configuration way to eliminate cross-origin issues is to proxy API requests through the dev server so the browser sees all traffic as same-origin.

With this configuration, a fetch('/api/users') call from the frontend at http://localhost:5173 is forwarded to http://localhost:3001/users. The browser never sees a cross-origin request. Without changeOrigin: true, the Host header sent upstream retains the dev server's hostname, which may cause backend rejections if the target validates the Host header. This is strictly a development-only solution. Production builds served from a static host will not have this proxy, so proper server-side CORS headers remain necessary.

When Nginx sits in front of a backend, it is often the right place to manage CORS centrally. Important: Do not use if with add_header inside a location block -- Nginx's if block causes all parent-scope add_header directives to be silently ignored, breaking CORS headers on actual (non-OPTIONS) API responses.

The map directive builds an allowlist: if $http_origin matches a listed value, $cors_origin is set to that value; otherwise it remains empty. The always parameter ensures headers are added even on error responses (4xx, 5xx), which is critical because Nginx's add_header without always silently drops headers on non-2xx responses.

Nginx's if directive creates a new configuration context. Any add_header inside an if block discards all add_header directives from the enclosing scope.

Why the if block contains all headers and return 204: By placing return 204 inside the if block, the OPTIONS request is fully handled there and never reaches the outer add_header directives or proxy_pass. Non-OPTIONS requests skip the if block entirely and the outer scope's add_header directives and proxy_pass handle them. This separation avoids the inheritance pitfall: each request path (OPTIONS vs. non-OPTIONS) has its own complete, self-contained set of headers.

Note on empty $cors_origin: When the allowlist excludes the origin, $cors_origin resolves to an empty string, and Nginx emits Access-Control-Allow-Origin: (a blank header). Browsers will reject CORS for the request, which is the correct security outcome. However, emitting a blank header is technically non-conformant with RFC 6454. The most robust production solution is to handle CORS in the application layer (Express/Next.js) and have Nginx proxy transparently, or to use OpenResty/Lua for conditional header suppression.

After deploying, verify that both curl -X OPTIONS and curl -X GET against the same URL return the expected CORS headers.

A frequent source of the redirect CORS variant is a proxy_pass trailing-slash mismatch. If the location block is location /api but proxy_pass is http://127.0.0.1:3001 (no trailing slash), Nginx may issue a redirect for /api/ normalization before the request reaches the handler. Similarly, a return 301 https://... rule placed before the CORS location block can redirect the OPTIONS preflight. The fix is straightforward: ensure trailing slashes match between location and proxy_pass, and place any redirect rules after or outside the API location block so they do not intercept OPTIONS requests.

Use an explicit origin allowlist. Avoid * when credentials are involved; the browser will block JavaScript access to the response if a wildcard is used with credentials: 'include'.

Restrict Access-Control-Allow-Methods to only the methods the API actually uses. Listing every HTTP method widens the attack surface unnecessarily.

Set Access-Control-Max-Age to cache preflight responses. Chrome caps this value at 7200 seconds (2 hours); Firefox honors up to 86400 (24 hours). Use 7200 as a safe cross-browser default, or 86400 if your users are primarily on Firefox and you want fewer preflight round-trips.

Include Vary: Origin on every response where Access-Control-Allow-Origin is set conditionally. Without it, CDN or proxy caches may serve a CORS response cached for one origin to a different origin, causing intermittent failures.

Never mirror the request Origin header back without validating it against an allowlist. This is an open CORS misconfiguration that effectively disables the same-origin policy for any attacker-controlled origin.

Do not install browser extensions that disable CORS either -- they mask the problem during development and expose you to real cross-origin attacks on every other site you visit.

Avoid adding CORS headers in both the application framework and Nginx simultaneously. Duplicate Access-Control-Allow-Origin headers cause the browser's CORS origin comparison to fail; the browser receives the response but blocks JavaScript from reading it, producing the same CORS error the fix was meant to resolve.

Navigation is one of the most important components of a website. It helps visitors discover content, move between pages, and understand how a site is organized. However, a navigation menu that works well with a mouse may create problems for keyboard users, people who rely on screen readers, or visitors using small mobile screens.

Building an accessible navigation menu involves more than adding a few ARIA attributes or increasing the size of clickable elements. Developers need to consider semantic HTML, keyboard interaction, visible focus indicators, responsive layouts, and predictable behavior.

In this tutorial, we will build a responsive navigation menu using HTML, CSS, and JavaScript. We will also examine common accessibility mistakes and explain how to test the finished component.

HTML provides several native elements that communicate the purpose and structure of a navigation interface.

element containing a list of links. This structure helps browsers and assistive technologies identify the navigation region and understand the available destinations.

The aria-label gives the navigation landmark a descriptive name. This becomes particularly useful when a page contains multiple navigation regions, such as a primary menu and a footer menu.

Using a list also communicates that the links form a related group. Each link has a meaningful destination, making it possible for visitors to navigate the site without relying on visual positioning alone.

A common mistake is using clickable

elements instead of links. Although JavaScript can make a div respond to clicks, it does not automatically provide the same keyboard behavior and navigation semantics as an anchor element.

For navigation to another page, use an anchor. For an action that changes the interface, use a button.

#10787. AI Agents Need Idempotency: The Distributed Systems Problem Hiding Inside Agentic AI

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

A customer wants a $480 refund for a faulty part of a shipment he received. After waiting for 30 seconds for the payment API to process the refund, the customer support AI sends another request. It ultimately is fulfilled. However, as it turns out, the first request had also been fulfilled. The only thing missing was the notification of the refund for the customer. So the customer received two refunds of $480 each instead of the one he was asking for.

The AI was acting appropriately within its given constraints; the surrounding system couldn’t tell if the initial action had already been taken and failed to deliver the result. A well-known problem in distributed systems is gaining more notoriety as AI-powered agents increasingly perform actions beyond simply generating text. Idempotence is the solution to this problem.

Idempotence means an action can be performed multiple times with the same result as performing it once. This concept is particularly important for an AI agent that issues refunds, creates tickets, sends emails, or updates business applications.

AI agents as distributed software components have simple processes.

Think → choose a tool → call an API → receive a result → decide what to do next.

As we have outlined, many of the agent actions will utilize services and networks that can have issues from time to time. Consider the simple action of asking a payment provider to issue a refund. There are three possible outcomes:

The payment service never gets the request.

The refund went through, and the agent got the answer.

The refund went through, but the agent never received it back.

The most severe case, however, is when the time to complete an operation exceeds the timeout, but the operation does complete successfully. Since there is no answer, the software agent never learns of the operation's successful completion and must attempt to complete the operation again.

Distributed systems have dealt with the issues of unreliable networks for a long time already (retries, duplicate requests, etc.). By introducing agents, we give the software more freedom to choose when and how to proceed.

Consider an agent with these tools: search_customer(), check_inventory(), refund_payment(), send_email(), create_order(), delete_account()

Calling search_customer() twice will usually not cause much trouble.

In other words, an agent runtime should be able to tell if a tool only gets data or makes changes to the outside world. In the second group are things like sending money, getting money back, placing orders, writing messages, making accounts, and changing infrastructure.

There are side effects to these treatments. It's risky to think that agents can just retry every failed tool call as they get access to more business systems.

One common way to handle the duplicate requests issue is to implement idempotency keys.

Idempotency-Key: refund-order-123-run-842

The service stores the idempotency key and the result of processing the associated request.

It allows the refund to be processed the first time the idempotency key is sent to the service by the agent. Thereafter, if the response to the refund is lost and the agent attempts to resubmit the refund with the same idempotency key, the service will recognize that the refund has already been processed and return the previous result to the agent instead of processing another refund.

Many of the world’s leading payment companies, including Stripe, PayPal, and Square, use idempotency keys to allow their customers to safely retry requests.

However, one important rule for agents is that the agent software or workflow system—not the AI model—creates the idempotency key, and it is up to date.

By the time the model retries the same step, the Operation ID will have remained the same. This means the system can recognize the request as another attempt to execute the same action as before and not a new action.

Things could be easy if we could tell the model to ‘remember if it has already issued one of these before issuing another.' But even in the production environment, this approach is not sufficient. The agent could crash. The context could go away. The workflow could be taken off to be executed on another machine. The problem is that the model lacks sufficient information about what has or has not happened in external systems. Instead, the system should keep a record of the execution state outside of the model. The model determines what should happen. The runtime determines safe execution.

Modern agent tools include a name, description, and input parameters for the production system. More importantly, the agent runtime also needs to know about the behavior of the individual tool. For example, ‘refund_order’ modifies the application outside this tool, so the operation must be re-executed with the same actionID used for the initial failure. Also, as an example, refunds larger than $5,000 require manual approval. On the other hand, a ‘search_customer’ action is only a read, so re-execution can occur without human intervention. Based on this information, the OS makes decisions about the danger of the individual tool call. Automatic re-execution is still possible, even if the search fails. However, refunds require a bit more caution to avoid double posting of money. Thus, in addition to the input models for the AI tools used in real life, so-called “execution rules” are also required. These rules state when re-execution, increased security, or human intervention is required.

Suppose an AI agent were to perform the following three actions: 1) Make whole the customer, 2) Send a confirmation email with the order update and a proof, and 3) Check the status of the order in process. We had described how stopping the AI from paying out twice was only half the problem; the system also needed to know where the work had stopped. To that end, we’d like to introduce the concept of durable execution. For durable execution, the agent must do more than simply remember the actions it has taken. We need to keep track of the progress of the actions of the AI. The refund action was marked complete, but the email action was not sent yet. Thus, when the agent is restarted, it continues from where it left off rather than starting over. To create reliable AI agents, we need a few things: stable operation IDs, irrevocable actions, durable state, controlled retries, and logging. There are also cases where one wants to perform a recovery or compensating action (e.g., the agent makes a reservation but then fails to perform the subsequent action). The recovery action would be to cancel the reservation that had been made.

While controls with a person in the loop are mostly suitable for fine-grained actions that cannot be undone, idempotence ensures that an action is not accidentally executed more than once, and human approval is required to decide whether the action should be executed in the first place. This point is illustrated by an example: An employee correctly approves a $10,000 refund. However, the payment request somehow times out and is automatically re-executed several times. Without adequate idempotency security, the customer might end up with even more refunds than intended. Note, however, that a person’s approval cannot prevent double killing in such high-risk agent processes. Therefore, additional decision controls and corresponding execution controls are usually required to ensure that all actions are executed safely and correctly.

Improving the model alone will not make the agent reliable unless we can answer all of these questions.

Much work in AI today focuses on making agents smarter, better at planning, and better to use as tools. But running agents in production has its own problems. API calls time out, processes crash, networks fail, and responses get lost, and the smartest agent can try again and again until it works. These are not new problems. Engineers working on distributed systems have been struggling with these same issues for decades. So long as the AI agent is confined to a simple test environment, of course it can query payment systems, customer information, and corporate tools. But when it is turned loose on the production corporation’s infrastructure (with all the payment systems, customer information, and corporate tools that entails), it must also be reliable. A smart model can figure out that a customer is due a refund. But a strong system can only give that customer a refund once. So the important question to ask of an AI agent before turning loose on it is, "Some powerful new tool: what happens if the action worked?" The answer will tell you whether or not the AI agent is currently able to operate reliably in production.

AI image generation has become a normal part of many web projects. However, the image a model produces is rarely the image a browser should receive. A single large PNG straight from a generator can weigh several megabytes, ignore the visitor's screen size, and slow down your Largest Contentful Paint (LCP) before the page has a chance to impress anyone.

The good news is that the fix is not complicated. If you treat the generated image as a high-quality master file and run it through a small, repeatable pipeline, you can ship images that look sharp on every device and load quickly on slow connections.

This tutorial walks through that pipeline from start to finish: generating at the right size and aspect ratio, choosing modern formats, creating responsive variants with Node.js, writing srcset and sizes correctly, and avoiding the performance mistakes that show up most often in audits.

Image generators are built to produce visually impressive results, not optimized web assets. Their output is usually a single file at one resolution, often in PNG format, and sometimes with an aspect ratio that does not match your layout.

Sending that file directly to the browser creates three problems. First, mobile visitors download far more pixels than their screens can display. Second, PNG is a poor choice for photographic images because its lossless compression produces large files. Third, without width and height information, the browser cannot reserve space for the image, which causes layout shifts as the page loads.

A web pipeline solves all three. You generate one master image, export multiple sizes in modern formats, and let the browser choose the best version for each visitor.

Optimization starts before you export anything. The most efficient pipeline begins with an image that already fits your layout.

Look at where the image will appear and note its aspect ratio at each breakpoint. A full-width hero might use 16:9 on desktop, while a blog thumbnail might use 4:3 or 1:1. Then identify the largest size the image will ever display. For a full-width hero, that could be 1920 pixels wide on large screens, or more if you support high-density displays at wide viewports.

Your master image should be at least as large as that maximum rendered width. Upscaling a small image later almost always introduces blurriness or artifacts.

Modern image-generation models can follow detailed instructions, so describe the technical requirements in your prompt, not just the subject. A location endpoint can return HTTP 200 and still be wrong by kilometers. That is the uncomfortable part of testing geospatial APIs: ordinary API checks tell you whether the request worked, not whether the geography is correct.

Spatial bugs can look harmless in code review. Latitude and longitude get reversed. A radius value is treated as degrees instead of meters. A query works near one city but behaves differently elsewhere because the geometry column uses the wrong type. The JSON is valid, the tests are green, and the map is still wrong.

In this tutorial, you will build a small FastAPI endpoint backed by PostGIS and then test the spatial behavior directly. The examples use deterministic fixtures positioned at known distances, so the tests verify geography rather than only response structure.

The API exposes one endpoint: GET /places/nearby. A client sends longitude, latitude, and a radius in meters. The service returns nearby places as GeoJSON features, ordered by distance.

The useful part is not the endpoint itself. The useful part is the test strategy. We will check coordinate validation, exact distance boundaries, GeoJSON coordinate order, and the database query that turns a radius into a spatial filter.

Use a geography column when the API is answering human-scale distance questions in meters. PostGIS can then calculate on the ellipsoid instead of treating longitude and latitude as flat Cartesian coordinates.

The endpoint below validates longitude, latitude, and radius with Pydantic, then sends a parameterized query to PostgreSQL. The SQL uses ST_DWithin to filter candidates and ST_Distance to return the measured distance.

The API accepts lon and lat as separate named parameters. That removes ambiguity at the HTTP boundary. GeoJSON still uses [longitude, latitude] when the response is created.

Hard-coding two real businesses and hoping their distance is approximately right makes a fragile test. A better approach is to create test points at exact distances from a fixed origin.

PostGIS can generate those fixtures with ST_Project. In the test database, create one point 500 meters away, one 950 meters away, and one 1,500 meters away. Now a 1,000-meter query has an unambiguous expected result: the first two belong in the response and the third does not.

This is the first test that actually proves something spatial. It is not checking that the endpoint returns a list. It is checking that the 1-kilometer contract means what the API says it means.

GeoJSON coordinates are longitude first, latitude second. Many developers naturally think latitude first because that is how coordinates are commonly spoken. A validation layer can catch the most obvious reversal before the database ever sees it.

Longitude must be between -180 and 180. Latitude must be between -90 and 90. That will not catch every reversal, because both numbers may sometimes fall inside both ranges, but it catches a large class of failures and gives clients a useful error instead of a misleading map.

A response can be syntactically valid JSON and still violate the GeoJSON contract. Assert the geometry type and the coordinate order. For a known query point, longitude should appear in element zero and latitude in element one.

Spatial boundaries deserve their own tests. A place at 999 meters should be included in a 1,000-meter search. A place at 1,001 meters should not. A place exactly at the boundary should behave consistently with the predicate you chose.

ST_DWithin includes features whose distance is less than or equal to the supplied threshold, so document that behavior and test it explicitly.

Unit tests are useful for request validation, but mocking the repository layer removes the most important part of this API: PostGIS itself. Keep a small integration-test database and run at least a few tests against the real extension.

That catches mistakes that mocks cannot: geography versus geometry behavior, SRID mismatches, spatial indexes, units, and changes to SQL functions. A location API is one of the cases where a cheap database integration test buys a lot of confidence.

Correctness is only half the story. A radius endpoint that scans every feature will work in development and become painful at production scale. Add a GiST index and inspect the query plan.

The exact plan depends on your data and PostgreSQL version, but you should see the spatial index participating in candidate filtering. Treat an accidental sequential scan on a large production table as a regression worth investigating.

For a real project, I would split the tests into two groups. Fast validation tests run on every commit. PostGIS integration tests run in CI with a temporary PostgreSQL/PostGIS service.

The CI gate should cover invalid coordinates, zero or negative radius values, known-distance fixtures, boundary behavior, GeoJSON output, and at least one query-plan or performance sanity check for larger datasets.

This is more work than asserting status_code == 200, but it tests the thing users actually care about: whether the API's answer is geographically true.

Location APIs fail in ways ordinary web tests are not designed to notice. The response can have the right schema, the database call can succeed, and every field can look reasonable while the location itself is wrong.

The fix is not a giant testing framework. #10741. Journey to 1 Million Gradio Users!

5 years ago, we launched Gradio as a simple Python library to let researchers at Stanford easily demo computer vision models with a web interface.

Today, Gradio is used by >1 million developers each month to build and share AI web apps. This includes some of the most popular open-source projects of all time, like Automatic1111, Oobabooga’s Text Generation WebUI, Dall-E Mini, and LLaMA-Factory.

How did we get here? How did Gradio keep growing in the very crowded field of open-source Python libraries? I get this question a lot from folks who are building their own open-source libraries. This post distills some of the lessons that I have learned over the past few years:

1. Invest in good primitives, not high-level abstractions

When we first launched Gradio, we offered only one high-level class (gr.Interface), which created a complete web app from a single Python function. We quickly realized that developers wanted to create other kinds of apps (e.g. multi-step workflows, chatbots, streaming applications), but as we started listing out the apps users wanted to build, we realized what we needed to do: go lower.

Instead of building many high-level classes to support different use cases, we built a low-level API called Gradio Blocks that let users assemble applications from modular components, events, and layouts. Despite generally being more work to use, gr.Blocks today represents 80% of the usage of Gradio—including the highly popular apps mentioned above.

With a small team, a focus on low-level abstractions has necessarily meant that we could not chase many tempting, high-level abstractions. But this focus saved us from two common pitfalls:

Customization-maintenance trap: high-level abstractions are easy to use, but users request extra parameters to customize them, which in turn leads to increased maintenance burden since every abstraction and parameter needs to be implemented, maintained, and tested to avoid bugs.

The productivity illusion: using high-level abstractions seems like less work, until a user needs functionality that is not supported (which can be hard to predict at the beginning of a project), forcing the developer to do a costly rewrite.

The first problem wastes our time as maintainers of Gradio, while the second problem wastes our users’ time. To this day, Gradio only includes two high-level abstractions (gr.Interface and gr.ChatInterface) which themselves are built with Blocks.

The advantage of having good primitives is even more dramatic in the age of AI-assisted coding, where we find that LLMs are generally good at combing through documentation and building complex applications out of primitives (see all the games being built with three.js for example). It doesn’t take much extra time to write low-level code if the AI is writing the code for you.

The best ambassador for your library is not you, but an enthusiastic user. It follows, then, that you should find ways for users to share your library or its products as part of their workflow. Gradio’s early growth was fueled by our “share links” feature (which created a temporary public link for your Gradio app in a single line of code). Instead of having to worry about packaging or hosting their code on a web server with the right kind of compute, Gradio users could share their apps with colleagues immediately.

After joining Hugging Face, we also benefited from being the standard UI for Hugging Face Spaces—widely used by the machine learning research community. The most viral Spaces drew millions of visitors, exposing developers to Gradio, who in turn shared and built their own Gradio apps, using those same Spaces (whose code was publicly available) as a resource to learn how to use Gradio.

Early on, we faced a critical decision: should Gradio be a general-purpose Python web framework, or should we focus specifically on building machine learning web apps? We chose the latter, and this has made all the difference.

In the crowded ecosystem of Python web libraries, we are frequently asked, "How is Gradio different from X?" Our concise answer—that Gradio is optimized for machine learning web apps—is memorable and fundamentally accurate. Each Gradio app ships with features particularly suited to ML workflows, such as a built-in queue that can manage long-running ML tasks efficiently, even with thousands of concurrent users. The components we have designed are specifically tailored to ML use cases. On the other hand, for a long time, Gradio did not even include features like link buttons, simply because our core users never needed it. By narrowing our focus, Gradio quickly became the go-to choice among machine learning developers—the default "UI for AI."

Of course, we benefited tremendously from choosing a niche that itself was growing. The recent headwinds that have propelled all things AI-related benefited us tremendously and we likely would not have experienced the same kind of growth if we had focused on data science or dashboards for example.

4. Your only roadmap should be rapid iteration

Unlike some other libraries, Gradio doesn’t publish roadmaps. Instead, we track emerging trends in machine learning and ship accordingly. In open-source software generally, and AI specifically, shipping features based on the needs of the community (and deprecating features that are no longer needed) is key to continuous growth. As a concrete example, in the early versions of Gradio we built specific functionality to allow developers to show the “interpretation” of their machine learning models—as this was a very popular use case around 2020-21. As interest in interpretation waned, we deprecated this and instead poured our efforts into audio/video streaming and chat-related features.

Our internal process is decentralized as well. Each of the 11 engineers and developer advocates on the Gradio team is encouraged to identify impactful ideas, prototype quickly, engage directly with the open-source community via GitHub, Hugging Face, and social media. Each team member brings these ideas back to the team and we continuously build and rebuild consensus around what ideas are likely to be impactful as we keep growing the most impactful directions.

5. Maximize ways users can consume your library's outputs

When you create a Gradio app and “launch()” it, you get a web application running in your browser. But that’s not all -- you also get an API endpoint for each Python function, as well as automatically-generated documentation for each endpoint. These endpoints can be consumed via Python or JavaScript Clients that our team has built, or directly using cURL.

The reason that we do this is because we want each minute that a developer spends with Gradio to be maximally useful. A single Gradio app should run locally or be deployed without any code changes on Hugging Face Spaces or on your server, or integrate into larger applications programmatically, or even be harnessed by AI agents through MCPs (more on that soon!). By focusing on maximum usability, we hope that developers can continue to get more and more out of the Gradio library.

The Llama 4 models were pre-trained with a context length of 256K. The Instruct models were fine-tuned to support much larger context lengths: 1M in the large 128 experts version (Maverick), and 10M (!) for the 16 experts version (Scout).

These large context lengths come with a few very interesting architecture choices. Until an official technical report is published, this is what we know so far.

NoPE (cute name, +1 charisma points), which was explored as far back as 2022, just forgoes the traditional positional encoding schemes, such as RoPE, that are most times applied in transformers models. In the case of Llama 4, NoPE layers are used every 4 layers. These layers are crucial for long context, as they use the full causal mask over the context.

For RoPE layers (three out of 4), chunked attention is used.

Meta refers to the interleaved use of NoPE layers, together with temperature scaling (as explained below), as the iRoPE architecture.

If you want to learn more about positional encodings, we recommend Chris' recent post.

As a way to reduce memory requirements, Llama 4 uses chunked attention in the layers that work with traditional RoPE positional encodings (three out of 4 decoder layers). The best way to visualize how chunked attention works is through this ASCII representation that was extracted from the transformers source code:

This diagram shows the attention mask that would be used if the chunked attention length was 3. In the case of Llama 4, chunked attention length is 8192. This means that RoPE layers can only keep track of context in 8K blocks, while NoPE layers have access to the full context. You can see it as a more memory and compute efficient version of Sliding Window Attention.

Attention blocks applied to long contexts have a problem: the attention probability scores fade closer to zero as the sequence length increases. This is a known consequence of applying the softmax function to very long sequences. To address this problem, Llama 4 uses a scaled softmax, which the model refers to as temperature tuning. This is applied in the NoPE layers, but not in the RoPE ones as these attend to shorter sub-sequences.

This method is a way to improve generalization for arbitrary context lengths, and probably one of the key factors to achieve 10M context length in Llama 4 Scout.

Llama Scout (the 16 experts version) uses an additional RMS normalization without learnable parameter of the Query and Key states in RoPE layers, after RoPE embeddings have been applied.

Llama Scout is a full MoE consisting of 16 experts. Llama Maverick uses 128 experts, but MoE and dense layers alternate. Therefore, experts are applied in half of the layers.

Llama Maverick was co-distilled from a larger model, Llama Behemoth, using a novel loss function that weight dynamically the student and teacher logit.

The models leverage MetaP, a methodology likely inspired by MuP, to optimally tune hyperparameters across different dimensions including training budget and model size.

One of the core capabilities of large language models (LLMs) is their ability to understand and follow human instructions. This skill is crucial for building reliable chatbots, virtual assistants, and AI systems that do what users ask. Without strong instruction-following, a model might generate correct information but in the wrong format, ignore user-specified constraints, or produce unwanted content. Instruction-Following benchmark is standardized, objective way to measure a model's instruction adherence and compare models fairly to drive improvements.

Our work took inspiration from the IFEval dataset. IFEval, originally introduced by Google, provides a structured benchmark designed to evaluate LLMs on their ability to follow verifiable instructions. It consists of prompts containing specific, objectively measurable commands such as “use exactly three bullet points,” “include the word ‘innovation’ twice,” or “limit your answer to 100 words.” English IFEval dataset contains around 500 prompts covering 25 different types of such verifiable instructions. Evaluation within IFEval is conducted through Python functions that automatically verify whether instructions are followed, avoiding the need for human evaluators or another AI judge. This makes the evaluations reproducible and unbiased. While IFEval has become the standard for assessing LLMs responding in English, a similarly detailed and structured resource is absent for Arabic.

Construction of our Arabic IFEval dataset began by carefully adapting approximately 300 prompts from the original English IFEval. This wasn't a straightforward, word-for-word translation; instead, we thoughtfully adjusted prompts to clearly reflect Arabic linguistic nuances and cultural contexts. Instructions that made little sense in Arabic, such as those involving English-specific vowel constraints, were either adapted to equivalent Arabic linguistic challenges or omitted entirely. Cultural references specific to English-speaking contexts were replaced with culturally relevant or Arabic-language equivalents to maintain contextual clarity. Additionally, we created unique Arabic-specific samples from scratch, specifically designed to emphasize distinctive Arabic phonetics, orthographic characteristics, and morphology, such as the careful use of diacritical marks (tashkīl), phonetic constraints like avoiding certain letters (e.g., writing without using the letter Alef (ا)), and leveraging root-based morphology to challenge models' word-selection abilities. All prompts underwent rigorous expert validation by Arabic linguists and domain experts who ensured grammatical accuracy, cultural appropriateness, and unambiguous clarity of each instruction.

To evaluate the models, we adopted a comprehensive methodology combining both explicit and implicit evaluation techniques. In this setup, a pre-trained image encoder (SigLIP, 14 patches at 384x384 resolution) generates image embeddings, which are then aligned with the LLM via a custom-trained multilayer perceptron (MLP) projector.

• Phase 1: Projector Pre-training – Only the projector is trained to map image features into the LLM’s latent space.

• Phase 2: High-Quality Vision Pretraining – Using refined datasets (e.g., OCR and re-captioned images), the entire architecture (encoder, projector, and LLM) undergoes joint training.

• Phase 3: Instruction Tuning – The model learns to follow user instructions via visual question answering (VQA), OCR, and other grounded vision tasks.

• Phase 4: Full Multimodal Tuning – Incorporates single/multi-image and video data, along with text-only examples, to optimize the model’s generalization to real-world, multi-input scenarios.

By sequentially exploiting vulnerabilities like obfuscated payloads and extension mechanisms, researchers have shown complex pathways for compromise that appear benign when examined individually. #10727. Prefill and Decode for Concurrent Requests - Optimizing LLM Performance

Handling load from multiple users in parallel is crucial for the performance of LLM applications. In the previous part of our series on LLM performance, we discussed queueing strategies for the prioritization of different users. In this second part, we will now focus on the concurrent processing of requests, and how it impacts relevant metrics such as latency and throughput as well as GPU resource utilization.

At TNG, we are self-hosting numerous Large Language Models on our cluster of 24 H100 GPUs. It supports 50 different applications, handles over 5,000 inferences per hour, and generates more than ten million tokens every day.

Most LLMs generate text token by token, which guarantees that every new token is computed based on all preceding tokens (this model property is called auto-regressive). The first output token depends on all prompt tokens, but the second output token already depends on all prompt tokens plus the first output token, and so on. As a consequence, token generation cannot be parallelized at the level of an individual request.

In LLMs with attention mechanisms, computing a new token requires calculating key, value, and query vectors for each preceding token. Fortunately, the results of some particular calculations can be re-used for subsequent tokens. This concept is known as key-value (KV) cache. For every additional output token, only one more set of key and value vectors needs to be calculated and added to the KV cache. For the very first output token, however, we start with an initially empty KV cache and need to calculate as many sets of key and value vectors as there are tokens in the input prompt. Luckily, and in contrast to any later token generation, all input tokens are known from the beginning, and we can parallelize the calculation of their respective key and value vectors. This difference motivates the distinction between the prefill (computing the first output token) and the decode phase (computing any later output token).

In the prefill phase, the calculations for all input tokens can be executed in parallel, while in the decode phase, no parallelization is possible on the level of individual requests.

The difference between the prefill and decode phases is also reflected in two key metrics for text generation: Time to first token and time per output token. The time to first token is given by the latency of the prefill phase, while the time per output token is the latency of a single decode step. Even though the prefill phase also generates only a single token, it takes much longer than a single decode step, because all input tokens need to be processed. On the other hand, the prefill phase is much faster with respect to the number of input tokens than a decode phase for the same number of output tokens (this difference is the reason why commercial LLM APIs charge input tokens at a much lower rate than ouput tokens).

Both latencies are relevant metrics for interactive applications like a chat bot. If users have to wait for more than 5 seconds before they see a response, they might think that the application is broken and leave. Similarly, if the text generation is as slow as 1 token per second, they would not be patient enough to wait until it is finished. Typical latency targets for interactive applications are 100-300ms per output token (i.e. a token generation speed of 3-10 tokens per second, at least as fast as reading speed, which ideally allows for skimming the output text as it is being generated), and a time to first token of 3 seconds or less. Both of these latency targets can be quite challenging to achieve, depending on the model size, hardware, prompt length, and concurrent load.

Other, non-interactive use cases might not be interested in the latencies of individual requests, but only in the total token throughput (tokens per second, summed up over all concurrent requests). This could be relevant when you want to generate translations for books, or summarize code files in a large repository.

As we will see in a later section, there generally is a trade-off between maximizing the total throughput and minimizing latencies for each individual request.

Because of the parallelized calculation for all input tokens, the prefill phase is very GPU compute-intensive. In contrast, the decode step for an individual output token utilizes very little computational power; here, the speed is typically limited by the GPU memory bandwidth, i.e. how quickly model weights and activations (including key and value vectors) can be loaded from and accessed within the GPU memory.

In general, token throughput can be increased until the GPU utilization (w.r.t. computational power) is saturated. In the prefill phase, a single request with a long prompt can already achieve maximum GPU utilization. In the decode phase, the GPU utilization can be increased by batch processing of multiple requests. As a consequence, when you plot the token throughput as a function of the number of concurrent requests, you see an almost linear increase in throughput at low concurrency, because this memory-bound regime benefits from larger batch sizes. Once the GPU utilization saturates and the compute-bound regime is entered, the throughput remains invariant to an increase in concurrency.

We will now consider how exactly an inference engine handles multiple requests that arrive within a short time interval.

Both the prefill and decode phases can make use of batching strategies to apply the same set of operations to different requests. But what are the consequences of running prefill and decode of different requests at the same time?

The most naive form of batching is called static batching. (1) You start with an empty batch, (2) you fill the batch with as many items as are waiting and as fit into the batch, (3) you process the batch until all batched items are finished, and (4) you repeat the procedure with a new empty batch.

All requests start their prefill phase at the same time. Since prefill is just a single, but heavily parallelized, GPU operation (think of it as a very large matrix multiplication), the prefill phases of all concurrent requests are completed at the same time. Then, all decode phases start simultaneously. Requests with fewer output tokens would finish earlier, but because of the static batching the next waiting request can only start once the longest batched request has been completed.

Static batching optimizes the time per output token, since the decode phase is uninterrupted. The drawback is a very inefficient resource utilization. Since a single, long prompt can already saturate the compute power during prefill, handling multiple prefills in parallel does not yield a speed-up and will certainly max out GPU utilization. In contrast, the GPU will likely be underutilized during the decode phase, since even a large number of concurrent decodes is not as compute-intensive as the prefill for a long prompt.

The biggest disadvantage, however, is the potentially long time to first token. Even if some short requests finish early, the next queuing request has to wait for the longest decode in the batch to finish before its prefill can begin. Because of this flaw of static batching, inference engines typically implement continuous batching strategies. Here, any completed request is immediately removed from the batch, and the batch space is filled with the next request in line. As a consequence, every continuous batching strategy has to deal with concurrency between prefill and decode phases.

In an attempt to reduce the waiting time of requests, inference engines such as vLLM and TGI schedule the prefill phase of new requests as soon as they arrive and fit into the current batch. It is possible to run the prefill of new requests in parallel with a single decode step for each of all previous requests, but since everything is executed in the same GPU operation, its duration is dominated by the prefill, and for every request in the decode phase only a single output token can be generated in that time. Therefore, this prioritization of prefills minimizes the time to first token but interrupts the decode phase of already running requests. In a chat application, users can experience this as pausing of the streamed token generation when other users submit long prompts.

In the following measurement you can see the effect of continuous batching with a prefill-first strategy.

One approach to alleviate the impact of interruptive prefills on running decodes is a chunked prefill. Instead of processing the entire prompt in a single prefill step, it can be distributed over multiple chunks. Then there can be as many concurrent decode steps during prefill as there are prefill chunks (as opposed to only a single decode step per concurrent request during the entire prefill). A chunked prefill step will still take longer than an isolated decode step, but for small chunk sizes the user now experiences only a slowing-down of token generation instead of a complete pause; this reduces the average time per output token. From the perspective of the interrupting request, a chunked prefill comes with some overhead and takes a bit longer than an isolated, contiguous prefill, so there is a small increase in the time to first token. With the chunk size we now have a tuning knob for prioritizing either the time to first token or the time per output token. Typical chunk sizes are between 512 and 8192 tokens (the vLLM default was 512 when chunked prefill was first implemented, and was later updated to higher values).

The biggest advantage of this strategy is, however, that chunked prefill maximizes resource efficiency. Prefill is compute-intensive, while decode is memory-bound. By running both operations in parallel, one can increase the overall throughput without being limited by GPU resources. Of course, maximum efficiency is only achieved at a certain chunk size, which in turn depends on the exact load pattern.

In a standard vLLM deployment and for evenly sized requests, we observed that chunked prefill increased the total token throughput by +50%. It is now enabled for every vLLM deployment of self-hosted LLMs at TNG. Overall, chunked prefill is a good default strategy for most use cases. Optimizing the chunk size, however, is quite difficult in environments with unpredictable load patterns (like TNG with its many diverse applications); typically, you stick with the defaults.

Most identity theft online starts with a password. Someone reuses one, a site gets breached, a fake login page collects a few more, and suddenly a stranger is inside an email account resetting everything else.

Passkeys are the industry’s attempt to remove that weak link. Apple, Google, and Microsoft all support them now, and plenty of big sites already offer them at sign-in. But do they actually make identity theft harder, or do they just move the problem somewhere else?

The honest answer is a bit of both. This article looks at how passkeys work under the hood, which attacks they shut down, which ones they don’t touch, and what you need to get right if you’re adding them to your own site.

Passwords have one basic flaw. They’re a shared secret. You know it, the server knows it (or a hash of it), and anyone who gets a copy can use it from anywhere.

Two-factor authentication helps, but not as much as people think. SMS codes can be intercepted or stolen through SIM swaps. One-time codes from an app can still be phished, because a fake site can simply ask for the code and pass it along in real time.

A passkey is a pair of cryptographic keys made for one specific website. It’s built on the WebAuthn standard from the W3C and the FIDO Alliance.

Nothing secret ever crosses the network, and nothing secret is stored on the server. That small change has big consequences.

This is the biggest win. Every passkey is tied to the domain it was created for. Your browser won’t use a passkey for example.com on examp1e-login.com, no matter how real the page looks. That protection only holds if the attacker can’t fall back to a password or a weak recovery path, which is why the rollout advice later in this article matters.

With a password, the user is the one who has to spot the fake. With a passkey, the browser checks the domain for them. People get tired and click bad links. The browser doesn’t.

Each passkey is unique to one site, so there’s nothing to reuse. An attacker can’t take a passkey from one breach and try it somewhere else, because there’s no shared value to try.

If an attacker dumps a site’s database, they get public keys. A public key can check a signature, but it can’t make one. So the stolen data can’t be used to sign in as anyone.

This doesn’t make a breach harmless (more on that below), but it does remove the part that usually leads straight to account takeovers.

This is where a lot of articles get too optimistic. Passkeys protect the login step. Identity theft is a much bigger problem than that.

Every site needs a way back in for people who lose their phone. If that recovery path is an SMS code, an email link, or a support agent who can be talked into resetting things, attackers will go after that instead.

A site with passkeys and a weak recovery flow is only as strong as the recovery flow. This is the part developers most often underestimate. The OWASP Forgot Password Cheat Sheet is a good checklist for hardening it.

A breach that exposes names, addresses, birth dates, or government ID numbers is still a breach. Criminals don’t need to log in to your accounts to open new ones in your name. They can apply for credit, file fake tax returns, or run scams with that data alone.

Passkeys do nothing about this kind of identity theft. It’s why credit monitoring, freezes, and alert services are still worth knowing about even when your logins are locked down. If you want a broader look at how those tools compare, these theft protection insights from Cybernews cover what different services actually monitor.

Someone can still call a person, pretend to be their bank, and talk them into approving something. Passkeys make that harder because there’s no code to read out loud, but scammers adapt. User education still matters.

#10723. PipelineRL

We are excited to open-source PipelineRL, an experimental RL implementation that tackles a fundamental challenge in large-scale Reinforcement Learning with LLMs: the trade-off between inference throughput and on-policy data collection. PipelineRL's key innovation is inflight weight updates during RL training (see Figure 1 below). This allows PipelineRL to achieve constantly high inference throughput and minimize the lag between the weights used for rollouts and the most recently updated model weights. The result: fast and stable RL training for large language models.

In this blog post, we show that 1) inflight weight updates do not harm the training process and 2) PipelineRL achieves competitive results compared to Open-Reasoner-Zero, while using a simpler RL algorithm. We also present the modular PipelineRL architecture that facilitates trying new inference / trainer combinations.

In conventional RL approaches (Figure 1a), there is a trade-off between high throughput inference and on-policy data collection. To explain this trade-off let us first define conventional RL algorithmically:

To achieve high throughput, the inference servers must use large batch sizes and, therefore, generate data for multiple policy optimization steps. However, each optimization step increases the lag between the current policy and the data collected using the inference policy, progressively making collected data more off-policy and less effective for training. On-policy learning requires data for a single optimization step. But producing small amounts of data with many GPUs is inefficient because this means the per-GPU batch size is small. Furthermore the batch size goes down as the inference server finishes the short sequences and has only the few longest sequences in progress.

PipelineRL (Figure 1b) remediates this trade-off through inflight weight updates. We update the weights in inference servers after each optimizer step without ever stopping inference. We only pause the inference at all inference servers for just the time needed to receive the new weights. Inflight weight updates allow the inference server to constantly maintain the optimal batch size while simultaneously ensuring data remains on-policy or near on-policy, which leads to better GPU utilization and more effective learning, respectively.

To demonstrate the effectiveness of PipelineRL and the benefits of inflight weight updates, we trained a 7B model and 32B model on the Open-Reasoner-Zero dataset. Looking at the learning curves we see that PipelineRL matches or exceeds the performance of Open-Reasoner on the popular reasoning test benchmarks: AIME 2024 and MATH 500 (see Figure 2 above).

Notably, our RL implementation is much simpler than Open-Reasoner-Zero. While Open-Reasoner-Zero uses a value function, our implementation is a simplified version of GRPO. In particular, we found that the trust region importance weight clamping is not needed for stable training. Neither was overlong sequence filtering or reward shaping from the DAPO paper. For normalizing the loss we just use the number of sequences in the batch as the denominator, giving equal weights to all tokens. We used no KL penalty and no entropy bonus (though our implementation does support reference model KL). Despite the simplicity of our implementation, or perhaps thanks to it, training is very stable as you can see in this wandb report.

One might expect that inflight weight updates would result in an unstable training process, since sequence generation proceeds with stale keys and values in the KV cache that was computed with a previous model version. However, our experiments indicate this does not adversely affect stability.

PipelineRL is built to be modular and take advantage of rapid improvements in highly-specialized inference and training software (SGLang, vLLM, Nvidia Dynamo, DeepSpeed, FSDP, TorchTitan, FastLLM, etc.). We propose clear contracts between the inference and training components, allowing easy integration of new inference and training solutions as they become available.

Compromised publisher accounts. If an attacker phishes the developer account, they can push a malicious update to every existing user. Cyberhaven’s extension was hit by a phished administrator account in late December 2024.

The defenses are mostly boring, which is a good sign. Hardware-key two-factor authentication on the publisher account, a short list of people allowed to publish, and a review step before each release stops most of it. Lockfiles, pinned versions and regular dependency audits cover the code side.

Most articles on this topic stop at the scary part. This one is written for people who build websites, so we’ll go a bit further: what goes into a fingerprint, what the collection code actually looks like, and what you can change in your own projects.

Think of a fingerprint as a stack of clues rather than a single value. Your time zone is shared by millions of people. So is your screen resolution. Put twenty clues like that together, though, and the crowd shrinks fast.

Here’s roughly where the clues come from.

HTTP headers. Before any JavaScript runs, every request already tells the server a lot. The User-Agent string and the Accept-Language header give away your browser, its version, your OS, and your languages. Chromium browsers also send Client Hints.

JavaScript APIs. Plenty of everyday APIs leak device details. screen.width and screen.height, navigator.hardwareConcurrency (your CPU core count), navigator.deviceMemory (Chromium only), navigator.platform, and your time zone all add something. Plugin lists used to be a goldmine, but modern browsers now return a fixed, generic list, so that one’s mostly dead.

Rendering. This is the clever bit. Ask two computers to draw the exact same text, and the pixels won’t match perfectly. Fonts, graphics drivers, and the GPU itself all nudge the output slightly. Same browser, same version, different hardware, different result.

Network details. Your IP address, connection type, and even the way your browser sets up a TLS connection can help. IPs change, so these clues are less reliable. Trackers mostly use them to back up a match they already suspect.

How unique does this make you? Back in 2010, the EFF’s Panopticlick study tested around 470,000 browsers and found that about 84% of them had a unique fingerprint. (The project still exists, now called Cover Your Tracks.) Later studies with bigger samples found lower numbers, especially on phones, since a lot of phones share near-identical hardware. The percentages move around, but the basic idea hasn’t changed.

Canvas fingerprinting gets talked about the most. Here’s a basic version:

WebGL fingerprinting follows the same idea with 3D graphics. A script draws a hidden scene and also reads the WEBGL_debug_renderer_info extension, which can reveal your GPU’s make and model. Audio fingerprinting is sneakier. The script generates a sound, runs it through an AudioContext, and hashes the result. Different audio stacks produce slightly different numbers.

It’s worth remembering that the Canvas API, WebGL, and the Web Audio API were built for charts, games, and music apps. Tracking is a side effect of how much they expose. The W3C’s guidance on mitigating fingerprinting in web specifications covers how standards authors try to avoid adding new signals.

You might not write a single line of fingerprinting code yourself and still end up involved. There are three common ways that happens.

Your third-party scripts can do it without asking you. Analytics tags, ad scripts, chat widgets, social buttons. Each of them can call the same APIs your own code can. If your page loads fifteen of them, that’s fifteen possible fingerprinters. Checking what each script does has quietly become part of the job.

Browsers are closing the door. Chrome froze most of the User-Agent string and moved detailed info into Client Hints. Safari has Advanced Fingerprinting Protection. Firefox blocks known fingerprinting scripts, and Brave randomizes values returned by fingerprintable APIs. If your site depends on the old, wide-open APIs, you’re building on ground that’s shrinking every release.

Most of this comes down to one rule: collect less, and know why you’re collecting what’s left.

Search your codebase for the high-entropy stuff: canvas exports, WebGL renderer lookups, font detection, and calls to navigator.userAgentData.getHighEntropyValues(). If a feature still works without them, take them out.

In many teams, the biggest win is boring. Someone added a fingerprinting library years ago for one fraud check, nobody reviewed it since, and it’s still loading on every page. Deleting it helps more than any clever fix.

The classic User-Agent string packs browser, exact version, OS, and CPU architecture into one header. Client Hints break that apart so you only get what you ask for.

By default, Chromium browsers already send three basic hints: Sec-CH-UA, Sec-CH-UA-Mobile, and Sec-CH-UA-Platform. For most sites, that’s plenty, and you don’t need to request anything extra. If a feature really does need more detail, ask for that one hint with Accept-CH:

Skip full version numbers, architecture, and device model unless you have a real reason. Each extra hint makes your visitors a little easier to tell apart.

Keep in mind that only Chromium-based browsers support User-Agent Client Hints. Firefox and Safari won’t send them, so you’ll need a fallback. Where you can, feature detection beats browser detection anyway.

Here’s an uncomfortable truth: once a script runs on your page, it can call canvas, WebGL, and audio APIs, and there’s no header that switches those off. What you can control is which scripts run and how close they get to your page.

None of these is a silver bullet. Together, they cut down how much code gets the chance to fingerprint your users at all.

If your app draws on canvas (dashboards, editors, browser games), that output can be fingerprinted too. Try not to hand raw canvas data to third-party scripts.

Fonts count as well. Load fifteen unusual web fonts and you’ve given every script on the page an easy font fingerprint. A system font stack blends in better, and for interface text, most users won’t notice the difference.

Sometimes you’ll want to keep a fingerprint, for example to flag logins from a device you haven’t seen before. That’s fine, as long as you treat it with care:

Before you ship, open your site in Firefox with Enhanced Tracking Protection set to Strict, and in Brave with fingerprinting protection turned on. If something breaks, it was relying on a signal browsers are trying to get rid of.

Fix the feature. Don’t ask users to turn their protection down. Browsers are only going to get stricter from here.

What works better is a browser with fingerprinting protection built in, such as Brave, Firefox on strict settings, Safari, or Tor Browser. These either add noise to the signals or make everyone look the same. Extensions that block canvas and font reads can help too. So can simply updating your browser, since each release tends to remove a few more leaky details.

No single tool will stop fingerprinting completely. The good news is that it doesn’t have to. Fingerprinting works on probabilities, so making the signals noisier is often enough to break the match.
