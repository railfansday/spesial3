Vibe coding accelerates prototyping dramatically, but "working" and "safe" are different properties. This playbook provides a repeatable, ordered checklist for auditing AI-generated Node.js applications before you run or ship them.

Vibe coding, the practice of prompt-driven development where a developer describes desired functionality and an AI model generates the implementation, accelerates prototyping dramatically. But "working" and "safe" are different properties, and AI models optimize aggressively for the former. A vibe-coded app security audit addresses the gap that opens when generated code ships without systematic review.

AI code generators pull from training corpora that include insecure patterns, deprecated APIs, and supply-chain antipatterns. The generated code often contains hardcoded secrets, unnecessary dependencies, overly permissive configurations, calls to eval(), disabled TLS verification, or lifecycle scripts that execute arbitrary commands during installation. None of this requires malicious intent from the model. It reflects the statistical reality that training data contains plenty of insecure-but-functional code, and the model has no threat model of its own.

The risk compounds because vibe-coded projects often include dependencies the developer never explicitly chose. The AI picks packages based on pattern frequency, not security posture, which means typosquatted or abandoned libraries can slip into a package.json without anyone noticing.

This guide targets Node.js and npm projects generated or scaffolded by AI tools. The goal is a repeatable, ordered checklist that answers two questions: "Is this safe to run?" and "Is this safe to ship?" The workflow chains together Git, npm script suppression, static analysis via Semgrep, dependency auditing, and Docker network isolation into a single copy-paste process. Every step builds on the previous one. Skipping steps weakens the guarantees downstream.

An AI-generated package.json may contain lifecycle scripts such as preinstall, install, or postinstall that execute arbitrary code the moment npm install runs. A postinstall hook pointing to curl ... | sh would download and execute a remote script with the permissions of the current user. Running this on a development workstation exposes SSH keys, cloud credentials, browser sessions, and anything else accessible to that user account.

Docker containers provide process and filesystem isolation, but they allow outbound network connections by default. A malicious script running inside a container can still exfiltrate data to an external server unless you apply additional flags. This step creates the isolated environment; later steps lock down network access and suppress script execution.

#10907. When AI-Generated Documentation Is Unreadable: A CI Playbook

Teams adopting LLMs for documentation are running into a predictable failure mode: AI-generated documentation that looks polished but collapses under actual use. The docs compile, the formatting is clean, the headings are logical, and yet nobody can follow the procedures they describe. Worse, when AI-generated docs become the input for further AI-generated docs, the result is a feedback loop of degrading quality that no amount of manual review can sustainably catch. This playbook provides a CI-enforced system, combining a doc skeleton, PR checklist, Vale prose linting, and structural shell checks, to reject unreadable documentation before it merges.

The pattern is now familiar enough that it surfaces regularly in engineering communities. Engineers describe the same frustration in community discussions: teams use LLMs to draft documentation, those docs get committed, and then other LLMs ingest them as context for generating further docs. Each generation drops decision rationale first, then environmental assumptions, leaving only bare commands wrapped in syntactically valid but semantically hollow instructions.

The symptoms are concrete and recognizable. You find giant CLI commands with unexplained flags that no reviewer questions because they "look right." Terraform blocks stretch 200 lines, dropped in without a single annotation explaining why a particular value was chosen. Nobody writes any human context around YAML walls. Verification steps that would confirm whether the procedure actually works? Missing entirely. The documentation exists, technically, but it serves no reader.

This is not a theoretical concern. It is the default outcome when AI generates documentation without structural constraints. The text is fluent. The Markdown renders correctly. The content is wrong, or at minimum, unverifiable.

Reviewers give documentation PRs less scrutiny than code PRs. They skim them. AI-generated text is particularly dangerous here because it reads as complete and professional. Clean formatting, complete sentences, and plausible-sounding steps are enough to pass a 30-second skim, and no one is running the commands or verifying the steps during the review process.

Without structural expectations, there is no objective standard against which to reject a doc PR. A reviewer might sense that something is off but lacks a concrete rule to point at. The cost of this gap surfaces downstream: onboarding engineers who cannot follow a setup guide, incident responders who discover runbooks are wrong under pressure, and knowledge transfer failures that compound over quarters.

The core mechanism for enforcing readability is a four-part skeleton that every documentation file must follow. Each section exists to surface a specific failure mode.

One to three sentences stating what the document enables the reader to do and when they would need it. The limit is deliberate. Forcing authors, whether human or AI, to articulate a document's purpose in three sentences or fewer exposes docs that exist for no clear reason. AI breaks the equation at its most fundamental point: the link between effort and value.

Most people discuss AI’s impact in one direction: “It makes work faster.” That’s true, but it’s only one-third of the story. Three things shifted at once.

1. The effort behind each deliverable dropped

Code assistants write boilerplate in seconds. Test cases get generated automatically. Documentation, bug triage, and first-line support can be partly automated. A task that took a team a week might now take two days.

On paper, that’s wonderful. In a time-and-material contract, it’s a problem, because fewer hours means less revenue for the same outcome.

2. Client expectations moved faster than vendor capabilities

Clients read the same headlines you do. They see demos of AI building an app in minutes. They don’t see the review, security checks, integration work, and edge cases that make production software hard. So they assume the price should fall, and they push for it in every negotiation.

The expectation of a discount arrives immediately. The efficiency gains arrive slowly and unevenly.

3. New costs appeared that nobody budgeted for

AI isn’t free to run. Companies now face costs they didn’t have before:

Usage-based bills for API calls, tokens, and cloud compute that grow with every project

Licensing fees for AI coding tools across hundreds of seats

Data preparation work, which is often the most expensive and least visible part of any AI project

Specialized talent such as ML engineers and prompt and evaluation specialists, who command premium salaries

Governance and security overhead, including legal reviews, client data policies, and compliance work

Constant retraining, because the tools change every few months

So revenue per project is under pressure while the cost of serving each project gets more complicated. That’s the squeeze.

Not every IT firm is suffering. The top tier is doing fine, and so are small specialists with a sharp niche. The ones in trouble are in the middle: capable and reputable, but not especially differentiated.

If you offer the same services as ten other vendors, your main lever in a negotiation is price. When AI lowers the cost of producing work across the whole industry, every vendor feels pressure to cut rates. Whoever blinks first resets the market for everyone.

Firms with unique domain expertise, proprietary tools, or deep client relationships can hold their ground. Generalists usually can’t.

They bought tools without changing the model

This is the most common mistake. A company rolls out AI assistants to all developers, celebrates the productivity boost, and then keeps selling the same way: same contracts, same staffing pyramids, same pricing logic.

The result is odd. Engineers finish work sooner, but the firm still bills by the hour, so efficiency directly cuts revenue. Or the firm keeps the bench full to maintain utilization, so efficiency creates idle capacity. Either way, the savings vanish.

Adopting AI without redesigning how you sell and deliver is like buying a faster truck but still charging by the mile.

IT services have traditionally relied on a wide base of junior engineers doing routine work, supervised by a smaller layer of seniors. AI is very good at routine work. That shrinks the base, which was both a revenue engine and a talent pipeline.

Average firms now face an uncomfortable choice. Keep a big junior base and watch margins erode, or shrink it and struggle to develop the senior engineers they’ll need in five years.

They lack the data and platforms to compete

Large players invest heavily in reusable accelerators, internal platforms, and proprietary datasets. These let them deliver at lower marginal cost with each new client. Average firms often rebuild from scratch on every project. That means their cost of serving each new customer stays high while their larger competitors’ costs fall.

This is the heart of the issue: growth is only valuable if each new customer costs less to serve than the last, or at least no more. For average firms, AI has quietly flipped that into the opposite direction.

Every client wants a custom AI experiment

Clients increasingly ask for pilots, proofs of concept, and “AI-enabled” versions of existing systems. Many of these never reach production. But each one consumes senior time, cloud budget, and management attention. Without discipline, a firm can end up doing lots of low-margin experimental work that looks like growth in the pipeline but behaves like cost in the books.

The firms handling this well aren’t necessarily the biggest. They’ve simply stopped treating AI as a tool and started treating it as a reason to redesign the business.

Instead of charging for effort, they charge for results: a migration completed, a process automated, a defect rate reduced. When AI makes delivery faster, the firm keeps part of the gain, because the client is paying for the outcome rather than the time spent.

This requires confidence in your estimates and a willingness to share risk. But it aligns incentives in a way hourly billing never can.

If you’ve built the same integration five times, it should be a product, or at least a reusable accelerator. Packaged services with fixed scope and pricing turn one-off labor into repeatable revenue. AI makes this easier, since it can handle much of the customization at the edges.

Many average firms track utilization and billing rates but not the true cost of delivering AI-related work. Stronger firms break it down: compute, licenses, rework, senior review time, and failed pilots. They know which accounts are actually profitable after AI costs, and they make decisions accordingly, including walking away from unprofitable work.

Training isn’t treated as an HR expense. It’s a margin strategy. A team that knows how to use AI tools well, review their output critically, and avoid expensive mistakes delivers faster and with fewer errors. A team that uses them poorly generates rework, security risks, and inflated cloud bills.

The gap between a well-trained team and an untrained one with the same tools can be larger than the gap between having the tools and not having them.

When routine coding becomes cheaper, value shifts toward the things AI can’t easily replace: understanding a client’s business, designing architecture, managing risk, integrating messy legacy systems, and taking accountability for results. Firms that invest in consulting depth and domain expertise can charge for judgment rather than keystrokes.

If you run or advise an IT company, you don’t need a grand transformation to start. Try these:

Audit your contracts. Identify which are purely time-and-material and which have room for fixed-price or outcome-based structures. Start by converting one or two with friendly clients.

Calculate true AI cost to serve. Add up tool licenses, compute, and extra review time per project. Many leaders are surprised by the number.

Find your repeatable work. List the five services you deliver most often and ask which could become a packaged offering.

Rethink your staffing pyramid. Decide deliberately how you’ll build junior talent when routine tasks are automated, rather than letting the pipeline dry up by accident.

Invest in structured training. Focus on practical skills: using AI tools responsibly, validating outputs, and understanding cost implications.

Prepare your pricing story. When clients ask for AI discounts, have a clear answer about where value comes from beyond effort: quality, accountability, speed to market, and risk reduction.

Track a small set of metrics. Revenue per employee, gross margin by account, AI spend as a percentage of delivery cost, and rework rates will tell you more than headline revenue growth.

AI hasn’t made IT services less valuable. It has made the old way of measuring and pricing that value outdated. When effort stops being the unit of worth, companies that built their models on selling effort face a real adjustment.

Average firms struggle because they are caught between two forces: clients expecting lower prices and new costs they didn’t plan for. The way out isn’t to resist AI or to adopt it blindly. It’s to rebuild the model around outcomes, reusable assets, skilled people, and honest numbers.

Revenue growth is still possible. But it now belongs to the companies that understand a simple truth: in the AI era, growing revenue is easy to want and hard to earn, and the real prize is growing it without growing your costs at the same pace.

#10877. Why AI Agents Break and How to Test Them?

AI agents pass internal testing, only to break once they're live. One widely cited estimate from Fiddler AI puts production failure rates for agents between 70% and 95%, depending on task complexity and how success is measured.

The reason behind it isn't complicated. Most testing only confirms an agent can complete a task once, under controlled conditions. But in production, that control disappears. The agent runs into a messier version of the same task: an ambiguous request, a longer conversation, or an API that returns something slightly unexpected. It starts making decisions nobody checked for, operating outside the only environment it was ever tested against.

This blog looks at why that kind of testing keeps missing what actually goes wrong, the specific ways agents break when handling real work, and what agent assurance should look like instead: proving an agent is safe to ship, rather than trusting its own account of what it did.

Traditional software testing is based on one simple assumption: same input, same output. If you give a program the same input twice, you get the same output twice. That's the whole logic. You write a test once, and it keeps working, because the code doesn't change on its own between runs.

AI agents don't work that way. Ask an AI agent to summarize the same document twice, and the two summaries may read nothing alike, while both remain perfectly reasonable. Ask it to complete a multi-step task, and it may take a different path each time, arriving at a good outcome on one run and a flawed one on the next.

That changes the question entirely. It's no longer "did this agent produce the output I expected?" It becomes: would this agent behave sensibly across the situations it'll actually encounter, not just the one scenario someone tested? That's a much harder thing to test, and it's where most teams building AI agents are still catching up.

Most of what makes agents unpredictable comes down to a handful of assumptions that hold true for traditional software but no longer hold once an agent takes over.

Traditional software fails visibly: if something goes wrong, you usually get an error or an obvious failure. Agents can be completely wrong and give no outward sign of it. They can also be told plainly not to do something and still do it because, in that moment, something else in the context outweighed that instruction.

Longer tasks expose another assumption. Traditional software doesn't forget what it was doing halfway through a run. An agent genuinely can. And while traditional software either finishes correctly or throws an error you can see, an agent can tell you it's done and still be wrong.

Once you see that gap, it explains almost every specific way agents actually break in production.

In July 2025, a SaaS founder named Jason Lemkin was testing an AI coding agent built by Replit. Partway through the trial, he told it directly to freeze all changes: no more edits to the codebase. The agent kept working anyway and, at some point, ran a database command it was not permitted to run, wiping out a live production database containing records for more than 1,200 executives and nearly 1,200 companies.

When Lemkin asked whether the damage could be undone, the agent told him no, that rollback wouldn't work here. He checked for himself. Rollback worked just fine.

Lemkin posted the exchange publicly as it happened, and Replit's CEO confirmed the incident and apologized. What makes it worth citing isn't just what happened, but how: the agent broke an explicit instruction, then answered a direct question about the damage with a confidently wrong answer that nearly prevented him from recovering his own data. That's the shape of failure worth paying attention to, not the mistake itself, but the confident wrong answer that followed it.

It also maps cleanly onto the specific ways agents break in practice, starting with the simplest one.

One of the most common failures is surprisingly simple: small errors compound.

An agent working through a multi-step task isn't producing one answer. It's making a chain of decisions, each one leaning on the last. If it misreads something early, say it pulls a number from the wrong row, or misunderstands part of what was asked, that mistake doesn't stay where it started.

That mistake becomes the input to the next step, then the one after that, until it's buried three or four layers deep by the time you see the result. The final answer still looks fine because every step after the mistake was a reasonable move given what that step had to work with.

Checking only the finished output rarely catches this, because it still reads as coherent. The agent built a consistent, logical-looking result on top of a wrong starting point, and you'd have to look at the steps themselves to see where things actually went wrong.

Another common failure appears when an agent has more than one way to complete a task. Given several tools or paths, it picks whichever looks like the best fit for the request, not necessarily the one that actually is.

Most of the time, those are the same. When they're not, nothing inside the agent raises a flag. It doesn't pause to think, "I'm not sure about this." It just picks and moves forward as if it were certain, running a search when a direct lookup would've been accurate, or summarizing a document when the real answer was sitting in a table it skipped past.

From the outside, the answer still looks perfectly normal. The mismatch only becomes visible if someone checks the choice the agent made, not just the text it handed back.

Long-running tasks introduce a different problem, and it's the one most closely tied to the Replit incident. Give an agent a boundary early on, like "don't touch a certain file" or "don't make changes during a freeze," and that instruction is at its strongest in the first few exchanges, when it's still the clearest thing in the conversation.

As the task runs longer, that boundary becomes an ever-smaller fraction of everything that's happened since, and nothing forces the agent to revisit it.

Microsoft researchers have shown that language models can refuse a harmful request made directly, yet comply when the same request is approached gradually over just a handful of turns.

Projects like LangWatch's open-source Scenario test exactly this by simulating long conversations instead of isolated prompts.

The instruction was never deleted. It just stopped being loud enough to win.

This may be the costliest failure of all, because it removes the one signal you'd normally trust to catch a problem. An agent finishes its steps, declares the task complete, and tells you so without checking whether that's actually true.

Lemkin had already seen a version of this in the days leading up to the deletion, when the agent reportedly produced fabricated test results and fake data.

Most agents don't have a built-in habit of asking that before declaring the job done, because finishing the steps and getting the right result were never the same check to them, even though from the outside they look identical.

Sometimes the environment changes instead. A button moves. An API response gets a new field. A file shows up in a slightly different format than usual. People barely notice changes like this and adjust without thinking twice.

An agent trained or tested in one environment doesn't have that instinct. Because nothing about the new input looks obviously broken, it keeps going with the same confidence as before.

Once you know how agents fail, testing is no longer about writing more test cases. It becomes about checking different things.

Don't grade an agent on whether each step looked reasonable. Grade it on whether the final result matches reality.

Did the number match the source? Did the file actually get updated the way it should have? That's the only check that catches failures where every individual step looked reasonable, but the final answer was still wrong.

A single prompt tells you almost nothing about how an agent behaves over the course of a real conversation. Test an agent with one bad request, and it may refuse because its instructions are still the loudest thing in the context. Run the same agent through a long, gradually escalating conversation, and it can end up somewhere it never would've gone if asked directly.

If your agent handles ongoing conversations, test it that way, not as a series of disconnected prompts.

Give the agent ambiguous instructions. Leave out the information it needs. Put it in an environment that's slightly different from the one it was built for.

You're not checking whether it succeeds. You're checking whether it notices something's wrong and says so, instead of confidently guessing and moving on.

When a test fails, knowing only that "the output was wrong" doesn't tell you anything useful. Knowing that "it picked the wrong tool at step two and never revisited that decision" does.

Without the trace, every failure turns into a new investigation. With it, you can usually see exactly where things went off.

One successful run tells you the agent can succeed. It doesn't tell you it succeeds reliably.

Run it five or ten times. Look at how much the results vary. A task with one clear right answer that produces different results each time is a warning sign, even if every individual run technically worked.

When you find a failure and fix it, don't just move on. Add that exact scenario to your test suite.

Agents change. Models get updated. Behavior you fixed last month can quietly come back, and you won't notice until it costs you something again.

None of this works as a one-time setup. A team that takes agent testing seriously ends up with a growing collection of past failures, adding each one the moment it's discovered, so nothing that broke once breaks the same way again.

It also means giving up the instinct to test an agent the way you'd test a normal feature, once, right before shipping. Teams doing this well run the same task repeatedly, watch full conversations play out instead of isolated prompts, and check results against the actual source rather than trusting how reasonable an answer sounds.

Doing all of this manually doesn't scale well, especially once an agent needs to be tested against dozens of realistic scenarios. For agents that talk to people, its agent testing uses autonomous evaluators that hold full chat, voice, or phone conversations with your agent and score each response for accuracy, safety, and compliance.

For agents that act, such as coding agents or agents that call tools and APIs, TestMu AI's Agent Assurance goes a step further. It reads the agent's codebase, writes the test suite, runs the agent for real, and grades each criterion against what actually happened: the files that changed, the artifacts produced, and the tool calls made, not the agent's own summary of its work.

The goal was never to test agents less because they're unpredictable. It's about building tests that expect unpredictability from the start and catch it before a user does.

Agents will keep getting better. That's not really in question. What's still uncertain is whether the way teams test them keeps pace.

Right now, most testing still checks whether an agent got the right answer once, in one attempt, under conditions that look nothing like how it'll actually be used. That's not really testing. It's almost a demo. And the gap between a demo and the real thing is exactly where failures happen.

Closing that gap doesn't take a research breakthrough. It takes treating an agent's work the way you'd treat a teammate's: verify the result instead of assuming it's right.

As web applications grow, JavaScript code can quickly become difficult to manage. What begins as a few functions in a single file may eventually include API requests, user interface logic, validation, data processing, and reusable utilities. Hooks operate on an event-driven model. They fire at specific points in Claude Code's agent loop, intercepting actions before or after they occur. Four lifecycle events are relevant:

PreToolUse fires before any tool call executes. This is the interception point for blocking actions. For file-write gating, the tool names to match are Write, Edit, and MultiEdit. You can also match against Bash for command-level gating.

After a tool call completes, PostToolUse runs. This is the point for validation: linters, formatters, or test suites check the result of an edit. Because the tool has already executed, an exit code of 2 from a PostToolUse hook does not block the original action. Instead, it surfaces the script's stderr as feedback to Claude, which can then issue a follow-up edit to correct the issues.

When the user submits a new prompt, UserPromptSubmit fires. This is useful for resetting state between conversational turns.

Notification fires when Claude sends a notification. Non-zero exit codes from Notification hooks do not block any action. (The documentation does not specify any exit-code effect for this event type.) This makes it useful only for logging or side effects.

The contract is simple. When a hook script exits with code 0, the action proceeds normally. Exit code 2 is the blocking signal. For PreToolUse, exit 2 blocks the tool call and the script's stderr is fed to Claude as feedback. Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Adding an event listener to window, document, or any DOM node outside the component's own render tree requires manual cleanup. Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. Declare the handler as a named function (or a variable holding the function) inside the effect, then pass that same variable to both addEventListener and removeEventListener.

If the handler depends on a prop or state value and is defined outside the effect (for example, with useCallback), that handler must appear in the dependency array. When the reference changes, React cleans up the old listener and attaches the new one. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

Consider a search component where the user types quickly. Each keystroke triggers a new fetch. The request for "rea" might take 300ms while the request for "react" takes 50ms. The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Note that the effect function itself is not async. An inner async function is declared and called immediately. This matters because useEffect expects its return value to be either undefined or a cleanup function. React ignores a returned promise and never registers a cleanup function from it.

The Ampere® PMU Profiler (APP) is a Python-based tool designed to provide deep insight into the microarchitectural behavior of applications running on Ampere CPUs (e.g., Ampere® Altra® and AmpereOne®). Unlike standard profilers that identify where time is spent (for example, which functions consume CPU time), the PMU Profiler explains why time is being spent by measuring low-level hardware events associated with the CPU pipeline and execution behavior.

A key outcome of APP is that it enables performance engineers to move from coarse symptoms to actionable causes. For example, while application-level profiling can show an expensive code path, APP can help identify whether the expense stems from inefficient instruction fetching, data cache misses, or other microarchitectural factors that are difficult or impossible to isolate using application-level tools alone. The document outlines a top-down performance analysis methodology and positions APP as an essential final step for expert-level tuning, particularly on Ampere platforms, where you must understand hardware-level bottlenecks and then apply targeted code optimizations.

APP is intended to complement system-level analysis rather than replace it. System-level profilers are useful for identifying high-level bottlenecks such as resource saturation or contention, but APP is focused on microarchitecture-level analysis by collecting hardware events. This makes APP especially valuable after system bottlenecks have been eliminated or ruled out, leaving "microarchitecture inefficiency" as the remaining likely cause of slowdowns.

The Ampere PMU Profiler uses the Linux perf utility with validated PMUs and metrics on Ampere CPUs. #10748. Prefill and Decode for Concurrent Requests - Optimizing LLM Performance

Handling load from multiple users in parallel is crucial for the performance of LLM applications. In the previous part of our series on LLM performance, we discussed queueing strategies for the prioritization of different users. In this second part, we will now focus on the concurrent processing of requests, and how it impacts relevant metrics such as latency and throughput as well as GPU resource utilization.

At TNG, we are self-hosting numerous Large Language Models on our cluster of 24 H100 GPUs. It supports 50 different applications, handles over 5,000 inferences per hour, and generates more than ten million tokens every day.

Most LLMs generate text token by token, which guarantees that every new token is computed based on all preceding tokens (this model property is called auto-regressive). The first output token depends on all prompt tokens, but the second output token already depends on all prompt tokens plus the first output token, and so on. As a consequence, token generation cannot be parallelized at the level of an individual request.

In LLMs with attention mechanisms, computing a new token requires calculating key, value, and query vectors for each preceding token. Fortunately, the results of some particular calculations can be re-used for subsequent tokens. This concept is known as key-value (KV) cache. For every additional output token, only one more set of key and value vectors needs to be calculated and added to the KV cache. For the very first output token, however, we start with an initially empty KV cache and need to calculate as many sets of key and value vectors as there are tokens in the input prompt. Luckily, and in contrast to any later token generation, all input tokens are known from the beginning, and we can parallelize the calculation of their respective key and value vectors. This difference motivates the distinction between the prefill (computing the first output token) and the decode phase (computing any later output token).

In the prefill phase, the calculations for all input tokens can be executed in parallel, while in the decode phase, no parallelization is possible on the level of individual requests.

The difference between the prefill and decode phases is also reflected in two key metrics for text generation: Time to first token and time per output token. The time to first token is given by the latency of the prefill phase, while the time per output token is the latency of a single decode step. Even though the prefill phase also generates only a single token, it takes much longer than a single decode step, because all input tokens need to be processed. On the other hand, the prefill phase is much faster with respect to the number of input tokens than a decode phase for the same number of output tokens (this difference is the reason why commercial LLM APIs charge input tokens at a much lower rate than ouput tokens).

Both latencies are relevant metrics for interactive applications like a chat bot. If users have to wait for more than 5 seconds before they see a response, they might think that the application is broken and leave. Similarly, if the text generation is as slow as 1 token per second, they would not be patient enough to wait until it is finished. Typical latency targets for interactive applications are 100-300ms per output token (i.e. a token generation speed of 3-10 tokens per second, at least as fast as reading speed, which ideally allows for skimming the output text as it is being generated), and a time to first token of 3 seconds or less. Both of these latency targets can be quite challenging to achieve, depending on the model size, hardware, prompt length, and concurrent load.

Other, non-interactive use cases might not be interested in the latencies of individual requests, but only in the total token throughput (tokens per second, summed up over all concurrent requests). This could be relevant when you want to generate translations for books, or summarize code files in a large repository.

As we will see in a later section, there generally is a trade-off between maximizing the total throughput and minimizing latencies for each individual request.

Because of the parallelized calculation for all input tokens, the prefill phase is very GPU compute-intensive. In contrast, the decode step for an individual output token utilizes very little computational power; here, the speed is typically limited by the GPU memory bandwidth, i.e. how quickly model weights and activations (including key and value vectors) can be loaded from and accessed within the GPU memory.

In general, token throughput can be increased until the GPU utilization (w.r.t. computational power) is saturated. In the prefill phase, a single request with a long prompt can already achieve maximum GPU utilization. In the decode phase, the GPU utilization can be increased by batch processing of multiple requests. As a consequence, when you plot the token throughput as a function of the number of concurrent requests, you see an almost linear increase in throughput at low concurrency, because this memory-bound regime benefits from larger batch sizes. Once the GPU utilization saturates and the compute-bound regime is entered, the throughput remains invariant to an increase in concurrency.

We will now consider how exactly an inference engine handles multiple requests that arrive within a short time interval.

Both the prefill and decode phases can make use of batching strategies to apply the same set of operations to different requests. But what are the consequences of running prefill and decode of different requests at the same time?

The most naive form of batching is called static batching. (1) You start with an empty batch, (2) you fill the batch with as many items as are waiting and as fit into the batch, (3) you process the batch until all batched items are finished, and (4) you repeat the procedure with a new empty batch.

All requests start their prefill phase at the same time. Since prefill is just a single, but heavily parallelized, GPU operation (think of it as a very large matrix multiplication), the prefill phases of all concurrent requests are completed at the same time. Then, all decode phases start simultaneously. Requests with fewer output tokens would finish earlier, but because of the static batching the next waiting request can only start once the longest batched request has been completed.

Static batching optimizes the time per output token, since the decode phase is uninterrupted. The drawback is a very inefficient resource utilization. Since a single, long prompt can already saturate the compute power during prefill, handling multiple prefills in parallel does not yield a speed-up and will certainly max out GPU utilization. In contrast, the GPU will likely be underutilized during the decode phase, since even a large number of concurrent decodes is not as compute-intensive as the prefill for a long prompt.

The biggest disadvantage, however, is the potentially long time to first token. Even if some short requests finish early, the next queuing request has to wait for the longest decode in the batch to finish before its prefill can begin. Because of this flaw of static batching, inference engines typically implement continuous batching strategies. Here, any completed request is immediately removed from the batch, and the batch space is filled with the next request in line. As a consequence, every continuous batching strategy has to deal with concurrency between prefill and decode phases.

In an attempt to reduce the waiting time of requests, inference engines such as vLLM and TGI schedule the prefill phase of new requests as soon as they arrive and fit into the current batch. It is possible to run the prefill of new requests in parallel with a single decode step for each of all previous requests, but since everything is executed in the same GPU operation, its duration is dominated by the prefill, and for every request in the decode phase only a single output token can be generated in that time. Therefore, this prioritization of prefills minimizes the time to first token but interrupts the decode phase of already running requests. In a chat application, users can experience this as pausing of the streamed token generation when other users submit long prompts.

One approach to alleviate the impact of interruptive prefills on running decodes is a chunked prefill. Instead of processing the entire prompt in a single prefill step, it can be distributed over multiple chunks. Then there can be as many concurrent decode steps during prefill as there are prefill chunks (as opposed to only a single decode step per concurrent request during the entire prefill). A chunked prefill step will still take longer than an isolated decode step, but for small chunk sizes the user now experiences only a slowing-down of token generation instead of a complete pause; this reduces the average time per output token. From the perspective of the interrupting request, a chunked prefill comes with some overhead and takes a bit longer than an isolated, contiguous prefill, so there is a small increase in the time to first token. With the chunk size we now have a tuning knob for prioritizing either the time to first token or the time per output token. Typical chunk sizes are between 512 and 8192 tokens (the vLLM default was 512 when chunked prefill was first implemented, and was later updated to higher values).

The biggest advantage of this strategy is, however, that chunked prefill maximizes resource efficiency. Prefill is compute-intensive, while decode is memory-bound. By running both operations in parallel, one can increase the overall throughput without being limited by GPU resources. Of course, maximum efficiency is only achieved at a certain chunk size, which in turn depends on the exact load pattern.

In a standard vLLM deployment and for evenly sized requests, we observed that chunked prefill increased the total token throughput by +50%. It is now enabled for every vLLM deployment of self-hosted LLMs at TNG. Overall, chunked prefill is a good default strategy for most use cases. Optimizing the chunk size, however, is quite difficult in environments with unpredictable load patterns (like TNG with its many diverse applications); typically, you stick with the defaults.

Regardless of the exact chunk size configuration, concurrent processing with chunked prefill comes with two challenges that we will address in the next article.
