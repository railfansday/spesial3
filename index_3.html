Creating responsive website layouts is a fundamental part of modern front-end development. Developers need interfaces that work across mobile phones, tablets, laptops, and large desktop displays without requiring separate markup for every screen size.

CSS Grid provides a powerful way to organize content into rows and columns. Unlike older layout techniques that often require additional wrappers or complicated positioning, Grid allows developers to define two-dimensional layouts directly in CSS.

When combined with flexible sizing functions, intrinsic layout techniques, and a small number of carefully chosen media queries, CSS Grid can make responsive interfaces easier to build and maintain.

This article explores practical CSS Grid techniques for creating flexible layouts, avoiding common mistakes, and writing cleaner responsive stylesheets.

CSS Grid is powerful, but it is not always the simplest tool for the job.

Flexbox is often a better fit for a one-dimensional layout, such as aligning a group of buttons in a row or arranging an icon beside a label.

Most accessibility problems on a website aren't hard to fix. Low-contrast text. An image with no alt text. A button that doesn't tell a screen reader what it does. None of these need a rebuild or a specialist.

Every year, WebAIM scans the home pages of the top million websites and checks them against basic accessibility standards. The 2026 report found that almost 96% of the pages scanned had at least one automatically detectable accessibility failure.

What stands out even more is what the errors actually are. The same problems have topped this report for seven years in a row. These aren't new, complex edge cases; they are the same simple, repeating mistakes.

In this guide, we'll look at what those top errors actually are, why they keep making it to production, and the simple workflow habits you can use to catch them before your users do. We'll also cover where tools like TestMu AI's Accessibility Testing Suite fit into that workflow.

It's easy to assume teams just don't care. But that's rarely the reason. Most developers know what alt text is for. Most designers know low contrast is a problem. The real issue is simpler; a few patterns explain most of it:

None of these come from not knowing accessibility rules. They come from how software is actually built: fast, in multiple moving pieces, with much of the page assembled from components and third-party code that nobody on the team wrote from scratch.

WebAIM's report found that a small number of accessibility issues account for most detectable WCAG failures across the top one million websites. The sections below explain what each issue is, why it matters, and how to fix it.

Poor contrast means the text color is too close to the background color, making it hard to read. For instance, light gray text (#999) on a white background (#FFF) yields a contrast ratio of 2.85:1, which is well below the standard requirement. For anyone with low vision or color blindness, that text becomes unreadable.

The Fix: WCAG asks for a contrast ratio of at least 4.5:1 for normal text. Running a quick check with tools like the WebAIM Contrast Checker or a Lighthouse audit will give you the exact ratio before your page ships. Because the tools lay it out so clearly, this is easily one of the quickest errors on this list to catch and fix.

Alt text is the written description a screen reader reads out loud in place of an image. Without it, a screen reader either skips the image entirely or announces the file name, which tells a user nothing about the image.

For example, if it's a product photo, a chart, or an icon that functions as a button, missing alt text means a screen reader user has no idea what they're looking at, what it does, or what happens when they click it.

The Fix: Describe what the image actually shows instead of just saying it's an image. If it's purely decorative and adds nothing a screen reader user needs, use an empty alt attribute (alt="") instead of leaving it off. That tells the screen reader to skip it cleanly.

Missing form labels appeared on 51% of home pages. This one is easy to miss because the form inputs often still look labeled. A form field looks perfectly labeled on screen when the label is simply placed next to the input box. A sighted user sees "Email" written next to a box and knows what to enter.

A screen reader, however, doesn't rely on visual placement. It relies on the HTML. If "Email" isn't actually connected to that input field in the markup, the field may be announced as simply "edit text" or "blank," leaving the screen reader user with no indication of what information it expects.

Placeholder text isn't a substitute either because it disappears as soon as the user starts typing.

Nearly half of all homepages contain links with no accessible name. The most common examples are icon-only links, such as a search icon, shopping cart, or social media icon. Sighted users recognize these icons immediately, but a screen reader may announce them simply as "link," giving users no indication of what each one does.

The Fix: Give every icon-only link an accessible name using visible text, aria-label, or another appropriate labeling method. This preserves the visual design while allowing screen readers to announce the link's purpose.

About 31% of home pages have buttons with no accessible name, and the share has risen every year since 2021. The usual culprits are icon-only buttons: a hamburger menu, a close "X" on a modal, a play button, or a carousel arrow. A screen reader announces these as just buttons, so users can't tell whether they open a menu, close a dialog, or submit a form.

The Fix: Give every button an accessible name. Use visible text where you can. For icon-only buttons, add aria-label (for example, aria-label="Close dialog") or visually hidden text inside the button. If the icon is an image, provide alt text that describes the action, not the image.

Around 14% of homepages don't specify the page's language. Without it, screen readers have to guess how the text should be pronounced, which can result in words being read with the wrong pronunciation or accent.

Many users rely on a keyboard instead of a mouse to navigate a website. If a menu only opens on hover, a custom dropdown only responds to clicks, or a button can't receive keyboard focus, those controls become unusable for them.

The Fix: Every interactive element should be reachable with Tab and Shift+Tab and operable with the keys users expect: Enter for links and buttons, Space for buttons and checkboxes, arrow keys inside menus, tabs, and radio groups, and Escape to close dialogs and menus. You can test this by trying to navigate the entire page using only the keyboard.

Developers sometimes remove the browser's default focus outline to improve the visual design but don't replace it with another focus style. As a result, keyboard users can no longer tell which element is currently selected as they move through the page.

The Fix: Never remove a focus outline without providing a clear replacement. Every interactive element should have a visible, high-contrast focus indicator that tells keyboard users where they currently are on the page.

Videos without captions exclude people who are deaf or hard of hearing and make content harder to follow when audio isn't available or practical. Captions also help users understand speech in noisy environments or when the audio quality is poor.

The Fix: Provide accurate captions for every video. If the video contains important spoken information, include a transcript as well. Automatically generated captions are a good starting point, but they should always be reviewed for accuracy.

On mobile, small buttons and links are hard to hit accurately. Users may tap the wrong control, trigger an unintended action, or have to try multiple times before the touch registers. WCAG 2.2 Level AA sets a minimum target size of 24x24 CSS pixels, with 44x44 CSS pixels recommended (WCAG AAA and Apple's own guidance).

The Fix: Give every tappable element enough size and padding to be reliably tappable, even if the visible icon inside it remains small. Aim for 44x44 CSS pixels, and never go below 24x24.

Run a scanner across a page, and it catches a good chunk of what's wrong. Missing alt attributes, contrast ratios below the required threshold, a form field with no label in the code. Automated scanners catch these immediately.

According to most industry estimates, automated tools catch about 30 to 40 percent of accessibility issues. That's worth running. It also means most of what actually breaks a page isn't something a scanner can see at all.

Take alt text, for instance. A scanner can confirm an image has an alt attribute. It can't tell you if that attribute says anything useful. "Image description here" and an actual description of the photo both pass the same check because the tool only confirms the field isn't empty.

Take another example of a custom div button with role="button". A scanner sees the role and perceives it as a button. It has no way of knowing that nobody added the keyboard handling that makes the button actually work, because that's not something a static scan can test. You'd only catch it by unplugging your mouse and tabbing through the page yourself.

Reading order works the same way. A page can pass every automated check and still present its content in an order that makes no sense once you strip away the layout and just listen to it, top to bottom.

None of this means automated tools aren't worth using. It means they're a baseline, not a final check. Treating a clean scan as proof that a page works is exactly how these errors keep making it to production in the first place.

Most of the errors covered here aren't difficult to fix on their own. The harder part is catching them before they enter your codebase. The best time to find these problems is while you're designing, building, and reviewing a feature, not right before a release.

Before shipping, spend a few minutes using the page yourself. Navigate using only the keyboard and verify that the focus indicator remains visible. That's what accessibility actually comes down to. It is not just a standard to meet, but the same usability you already care about, extended to people who navigate a page using assistive technologies.

They work well in short sessions, but as the context window fills during extended agentic loops, earlier instructions degrade in influence. Tool outputs, file contents, and intermediate reasoning bury the initial convention reminders. A long enough session means the agent effectively forgets what it was told. Any enforcement mechanism that relies solely on prompt text will exhibit this degradation pattern.

Claude Code hooks offer an alternative enforcement mechanism: shell scripts that bind to lifecycle events inside the agent loop. These scripts use exit codes to enforce rules. Exit 0 means proceed. Exit 2 blocks the action, and the script's stderr is surfaced to Claude as feedback. Any other non-zero exit code is a non-blocking error. This is deterministic. No matter how full the context window gets, an exit code of 2 stops the action every time.

Together, these hooks catch duplicated or unnecessary code before it lands and enforce style rules automatically.

Prerequisites: Claude Code installed and functional; a Node.js project with Prettier and ESLint already configured; jq installed (brew install jq / apt install jq); Prettier and ESLint must be installed as local node_modules dependencies (not relied upon via npx remote fetch); and basic familiarity with Bash scripting.

Hooks operate on an event-driven model. They fire at specific points in Claude Code's agent loop, intercepting actions before or after they occur. Four lifecycle events are relevant:

PreToolUse fires before any tool call executes. This is the interception point for blocking actions. For file-write gating, the tool names to match are Write, Edit, and MultiEdit. You can also match against Bash for command-level gating.

After a tool call completes, PostToolUse runs. This is the point for validation: linters, formatters, or test suites check the result of an edit. Because the tool has already executed, an exit code of 2 from a PostToolUse hook does not block the original action. Instead, it surfaces the script's stderr as feedback to Claude, which can then issue a follow-up edit to correct the issues.

When the user submits a new prompt, UserPromptSubmit fires. This is useful for resetting state between conversational turns.

Notification fires when Claude sends a notification. Non-zero exit codes from Notification hooks do not block any action. (The documentation does not specify any exit-code effect for this event type.) This makes it useful only for logging or side effects.

The contract is simple. When a hook script exits with code 0, the action proceeds normally. Exit code 2 is the blocking signal. For PreToolUse, exit 2 blocks the tool call and the script's stderr is fed to Claude as feedback. For PostToolUse, the tool has already completed, but exit 2 surfaces the script's stderr to Claude, which can take corrective action. The stderr content becomes part of the agent's reasoning context, which is what makes hooks corrective rather than merely restrictive. Any other non-zero exit code counts as a non-blocking error, not a block.

Configure hooks in the hooks object within .claude/settings.json for project-level scope or ~/.claude/settings.json for user-level scope. Each entry is keyed by event name and contains an array of matcher groups. Each group pairs an optional matcher (a pattern matching specific tool names) with a hooks array of one or more handlers, and each handler declares a type (command for a shell command) plus the command to execute.

This skeleton shows the structural pattern. The matcher field accepts pipe-delimited tool names. When a PreToolUse event fires for a Write tool call, Claude Code checks whether any hook entry matches, then executes the command, piping a JSON payload to its stdin containing the tool name and parameters.

The following configuration wires together all three lifecycle events. The PreToolUse entry fires before Write, Edit, or MultiEdit tool calls and blocks the first write attempt per prompt, printing a checklist for Claude to verify before proceeding. The PostToolUse entry fires after those same tool calls complete and runs Prettier (auto-fix) then ESLint (check) on the changed file. If ESLint finds issues, it exits 2 and prints them to stderr, surfacing the lint errors as feedback for Claude to self-correct. The UserPromptSubmit entry resets the pre-write gate so it re-arms on every new user prompt. No matcher is needed for UserPromptSubmit because this event has no associated tool. All three lifecycle events work together as a system: UserPromptSubmit resets state, PreToolUse enforces the gate, and PostToolUse validates output.

On the first file-write attempt after each new user prompt, the hook exits with code 2 and prints a checklist to stderr, which Claude Code feeds to Claude as the reason for the block. The checklist asks Claude to verify three things before writing new code: Does an implementation already exist in the project? Is there a standard-library equivalent? Is there a well-maintained dependency that handles this? This directly addresses the r/Frontend scenario where Claude wrote 1,000 lines duplicating existing functionality.

After Claude acknowledges the checklist (by seeing the stderr feedback, adjusting its plan, and attempting the write again), subsequent writes within the same prompt pass through. The gate opens for the duration of that conversational turn and re-arms when the user submits a new prompt.

The stateful pattern uses a temp file to track whether the gate has been opened. The file path follows the pattern /tmp/claude-hook-gate-$PPID. When the file exists, the gate is open and writes proceed. When it does not exist, the gate is closed and writes are blocked.

The UserPromptSubmit hook entry in settings.json handles the reset by running scripts/reset-gate.sh, which deletes this temp file, so every new user prompt re-arms the gate automatically.

Note on shared systems: The temp file path is predictable and based on a process ID, which can be a symlink attack surface on multi-user systems. On shared machines, consider using mktemp -d to create a session-specific directory and store the gate file there, or ensure /tmp permissions are appropriately restricted.

Each hook invocation spawns a new child process, so $PID (or $$) changes on every run. $PPID refers to the parent of the hook script. In the expected case, this is the Claude Code session process, which ties the gate state to the session rather than to the ephemeral script invocation.

However, this assumption should be verified in your environment. If Claude Code launches hooks through an intermediate shell (e.g., sh -c "bash scripts/..."), $PPID may point to that intermediate shell rather than the Claude Code session, and the value may change between invocations. Before relying on this mechanism, add a diagnostic hook that logs echo "PPID=$PPID" >> /tmp/hook-debug.log and confirm that the value is stable across multiple hook calls within a single session. If it varies, replace $PPID with a fixed session identifier.

The script canonicalizes the file path using realpath and verifies that it falls within the project root directory. This prevents path traversal attacks where a crafted path like /tmp/../etc/passwd could bypass simple prefix checks. PROJECT_ROOT derives from the script's own location ($(dirname "$0")/..), which also ensures ESLint and Prettier configs are discoverable.

Prettier runs with --write to fix formatting in place; its exit code is deliberately ignored with || true because formatting fixes do not block the pipeline. The command -v check ensures both Prettier and ESLint exist locally before attempting to run them. ESLint runs with --max-warnings 0 to treat warnings as errors, enforcing a strict zero-warning policy. The timeout 30 wrapper prevents ESLint from hanging indefinitely on large or problematic files.

ESLint exit codes are handled distinctly: exit code 1 indicates lint violations (actionable by Claude), exit code 2 indicates a configuration or fatal error (requires developer attention, not a code fix), and exit code 124 indicates a timeout. This distinction prevents Claude from endlessly retrying lint fixes when the actual problem is a broken ESLint configuration. In each failure branch the hook itself exits 2 and writes to stderr, the combination Claude Code surfaces to Claude as feedback.

Both tools are invoked via ./node_modules/.bin/ rather than npx to guarantee that locally installed versions are used. Using npx without --no-install can cause it to silently download packages at runtime if they are not found in local node_modules, introducing network latency, non-determinism, and unexpected cost during hook execution.

Files outside the project root, such as /tmp scratch files that Claude sometimes creates during multi-step operations, are skipped by the realpath canonicalization and project-root check. This is more robust than a simple prefix check against /tmp/* or /var/*, because it also catches path traversal patterns like /tmp/../etc/passwd and handles symlinks correctly.

Missing Prettier or ESLint binaries are handled gracefully. Both steps check for the binary with command -v before running. If ESLint cannot find a config file, it reports a fatal error (exit code 2), and that error flows through stdout to Claude with an explicit "configuration error" label, making it clear that the fix needed is not a code change. This is preferable to silently swallowing the failure.

Binary files and non-JS/TS files are handled by the extension filter in the case statement. The hook exits with code 0 for any unmatched extension, letting the write proceed without interference.

Layer the two: use CLAUDE.md for the "why" behind conventions, and hooks for the "must." CLAUDE.md explains that the team prefers existing utilities over new implementations, while the pre-write gate hook enforces that preference. CLAUDE.md describes the formatting standard; the post-edit hook runs the formatter. Neither mechanism replaces the other.

Hooks run synchronously. While a hook executes, the agent is blocked. Aim for under one second per hook invocation. Prettier and ESLint on a single file meet this target on typical developer hardware with local node_modules. Scripts exceeding two to three seconds will noticeably stall the agent loop. Running a full test suite as a hook would not be appropriate.

Hook input payloads follow a JSON structure that may evolve across Claude Code versions. grep or sed parsing is brittle and breaks on structural changes. jq provides safe, schema-aware extraction and handles missing fields gracefully with the // empty fallback pattern used in the scripts above.

When setting up hooks for the first time, appending output to a log file (>> /tmp/claude-hooks.log) helps diagnose issues with path extraction, exit codes, and unexpected tool names. Remove or disable logging once you have confirmed correct behavior over several sessions, to avoid filling disk space during long runs.

Astro pages render as static HTML by default. Zero JavaScript ships to the browser unless a developer explicitly opts in. Understanding how to verify AI UI changes requires recognizing two structural problems that distinguish AI-generated diffs from human-authored ones.

AI agents tend to touch many files per prompt. Two levels of structured output support differ in what they guarantee. JSON mode, available in providers like OpenAI and Gemini, guarantees that the model emits syntactically valid JSON. It does not guarantee any particular shape. The model might return {"foo": 42} when the application expected {"sentiment": "positive", "rating": 5}. Valid JSON is not the same as correct JSON.

Schema-constrained mode goes further. It enforces a declared JSON Schema at the token-generation level: the provider guides token decoding to produce output conforming to a specific structure. OpenAI supports this through the response_format parameter with type json_schema. Google Gemini offers it via generationConfig.responseSchema. vLLM provides schema-constrained decoding through its guided_json parameter. The strictness and subset of JSON Schema supported varies across providers, but the core mechanism is the same: constrain token sampling so only schema-valid sequences are generated.

Function calling (also referred to as tool calling) provides an alternative path to structured output. When a tool is defined with an input_schema, the provider forces the model to emit arguments matching the declared schema. This is Anthropic's primary structured output mechanism for Claude, which does not offer a dedicated response_format JSON schema mode. Instead, developers define a tool whose input schema matches the desired output structure, and the model returns the structured data inside a tool_use content block.

Use function calling when the application also needs to route actions based on the model's decision. Use response_format schema when the goal is purely typed data extraction. Both mechanisms benefit from the validation layer described below.

TypeScript's type system operates entirely at compile time. It erases all type information at runtime, which means a JSON.parse call returns any regardless of what interface was declared. Zod fills this gap by providing runtime type safety: it validates that a parsed object actually conforms to the expected shape, with rich error messages that pinpoint exactly which field failed and why. When an LLM returns "rating": "five" instead of "rating": 5, Zod reports the exact path, expected type, and received value. This level of detail is essential for debugging malformed LLM responses.

The zod-to-json-schema library converts a Zod schema into a standard JSON Schema object, enabling a single schema definition to drive both runtime validation and provider-level schema constraints.

This ProductReviewSchema becomes the single source of truth. The same Zod object validates LLM responses at runtime, generates the JSON Schema sent to providers, and infers the TypeScript type used throughout the application. There is no separate interface to keep in sync.

Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Adding an event listener to window, document, or any DOM node outside the component's own render tree requires manual cleanup. Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. Declare the handler as a named function (or a variable holding the function) inside the effect, then pass that same variable to both addEventListener and removeEventListener.

If the handler depends on a prop or state value and is defined outside the effect (for example, with useCallback), that handler must appear in the dependency array. When the reference changes, React cleans up the old listener and attaches the new one. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

Consider a search component where the user types quickly. Each keystroke triggers a new fetch. The request for "rea" might take 300ms while the request for "react" takes 50ms. The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Note that the effect function itself is not async. An inner async function is declared and called immediately. This matters because useEffect expects its return value to be either undefined or a cleanup function. React ignores a returned promise and never registers a cleanup function from it.

This article explores practical techniques for improving website performance using modern HTML, CSS, JavaScript, and browser development tools.

The first step in performance optimization is understanding how a website behaves under real conditions.

A page may feel fast on a powerful development computer but perform poorly on a mobile device or a slower network. Measuring performance helps developers identify the actual source of the problem instead of making changes based on assumptions.

Three important Core Web Vitals help evaluate the user experience:

Largest Contentful Paint (LCP): Measures when the largest relevant content element becomes visible.

Interaction to Next Paint (INP): Measures responsiveness across user interactions.

Cumulative Layout Shift (CLS): Measures unexpected visual movement during page loading and use.

Current good-target thresholds are an LCP of 2.5 seconds or less, an INP of 200 milliseconds or less, and a CLS of 0.1 or less, assessed at the 75th percentile of page visits.

Developers can investigate performance using Chrome DevTools, Lighthouse, and PageSpeed Insights.

Lab tests are useful during development, while real-user data can reveal problems that synthetic tests may not capture. Whenever possible, examine both.

Images often account for a significant portion of a webpage's downloaded resources. Large images can delay the appearance of important content, particularly on mobile connections.

Modern image formats such as WebP and AVIF can reduce file sizes compared with many traditional image formats, depending on the image and encoding settings.

The srcset attribute provides multiple image candidates, while sizes describes the expected rendered width under different conditions. The browser can use this information to select a suitable resource.

Performance optimization works best as an ongoing engineering practice rather than a one-time cleanup.

A repeatable process might include the following steps:

Record a baseline using representative devices and network conditions.

Identify the slowest important operation or resource.

Repeat the measurements under comparable conditions.

Test functionality, accessibility, and visual behavior.

Monitor real-user performance after deployment.

Automated performance checks can help detect regressions during development. However, a single Lighthouse score should not be treated as a complete representation of user experience because results can vary with test conditions.

The most useful optimization is one that produces a measurable improvement without introducing maintenance problems or degrading functionality.

Building a faster website requires a combination of careful measurement and practical engineering decisions. Responsive images, efficient script loading, appropriate caching, reduced layout work, and better task scheduling can all contribute to a smoother user experience.

The key is to prioritize improvements according to their actual impact. Reducing a large image may be more valuable than rewriting a small function, while splitting a JavaScript bundle may help only if the initial page does not need all of its code.

By using browser performance tools, testing realistic scenarios, and monitoring results after deployment, developers can build websites that are more responsive, efficient, and maintainable.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

#10901. TiDB Breach Exposes Flawed Cloud Security Assumptions

Cloud providers may be storing sensitive customer data, without either party knowing it. But when a provider is breached, the unseen information comes to light.

A breach of an open source database provider may have inadvertently highlighted a serious gap in the way companies think about their cloud security.

On Oct. 19, software maker PingCAP, which sells an SQL database program called TiDB, disclosed that it had been breached. According to PingCAP's website, it serves major American corporations like Atlassian, Square, and Pinterest, as well as major players in China's AI space, including Manus, Kimi, and more.

The perpetrator — the somewhat deceptively named "Fulcrum Security," or FulcrumSec, for short — is a relatively new extortionist group whose leak site already includes major organizations like LexisNexis, Novo Nordisk, and the Manchester Airports Group (MAG). Earlier this fall, FulcrumSec appears to have compromised PingCAP, enjoying something shy of unfettered access to all of its cloud management, financial, analytics, storage, and other systems for a month or more.

Related:LLMjacking Emerges as Thriving Cybercriminal Enterprise

The even bigger issue is whether the breach exposed downstream customers' sensitive data. Investigators are still working out the details, but early evidence suggests that customers may be at some risk. Though their actual databases weren't breached, the information their vendor stored about them may have been enough to cause serious issues.

In a security notification published 12 days after first having discovered the incident, PingCAP acknowledged that hackers had access to its systems from Sept. 9 to Oct. 7. Using stolen service account credentials, the company wrote, the unauthorized party accessed internal company systems and then copied data and source code.

PingCAP's own third-party-assisted investigation found no evidence that attackers ran malicious commands or maintained persistent access in their systems, nor did they access any customers' databases. Instead, it said, the threat actors accessed customers' billing and other business data, such as contract terms and pricing, as well as various information pertaining to cloud accounts and product usage — email addresses, SQL editor text and errors, etc. They also exported a table with encrypted API keys, though investigators said the encryption protected the keys from actually being used maliciously.

Dark Reading reached out to PingCAP for comment. A company spokesperson provided the following statement:

"Between September 9 and October 7, 2026, an unauthorized party used stolen service account credentials to access certain PingCAP internal systems, copy data, and obtain source code. PingCAP identified the activity on October 7 and began disabling the affected credentials that day. As of October 14, all identified compromised credentials have been invalidated, all identified unauthorized access paths have been blocked, and four vulnerabilities reported by our external incident response firm have been fixed and independently verified as remediated.

"Our investigation, supported by outside counsel and third-party forensic specialists, has found no evidence that data stored by customers in our TiDB cloud production services was impacted, and no evidence that the attacker ran commands or maintained persistent access in the production systems reviewed. Exported records included certain TiDB Cloud account information, business and billing details. API-key values in the exported data were encrypted, and we have found no evidence that any were decrypted or used. As a precaution, we have advised all customers to rotate their TiDB Cloud management API keys and remain alert to targeted phishing attempts. We will notify affected customers directly as customer-specific impact is confirmed, and we will continue to share verified updates on our Trust Hub: pingcap.com/trust-hub."

FulcrumSec, however, painted a bleaker picture.

In a name-and-shame post to its leak site, the hackers claimed to be in possession of all of PingCAP's service management records, its financial records, its files stored within Google Cloud, Jira support tickets, customer relationship management (CRM) data, analytics data, source code, plus a four-year-long log of every connection every one of its customers ever made to the TiDB Cloud service.

Crucially, the hackers did not claim to have stolen any TiDB databases straight up. Instead, they indirectly obtained a wealth of potentially exploitable user data like those aforementioned API keys and other secrets, and potentially sensitive internal data exposed by cloud database commands.

The attackers fingered individual enterprises caught in the crossfire: brand-name US companies like Airbnb and Booking.com, Asian corporate giants like Baidu and Fujitsu, and a few of the world's biggest video game companies, including Capcom, Konami, and Square Enix. Asia represented the biggest slice of the pie, with nearly 2,000 affected organizations in Japan, China, and Hong Kong, with another 500 from India.

Additionally, FulcrumSec said its unauthorized access lasted for nearly two months, not just one. It was so comprehensive and unthreatened that, in the meantime, they were able to stand up a mirror of PingCAP's own service management system. Instead of having to manually exfiltrate data, their replication feed automatically pulled fresh copies of the company's internal database every six hours, for 22 days.

Claims made by threat actors must always be met with a degree of skepticism, and Dark Reading did not independently confirm FulcrumSec's. Still, the group does have some record of reliability.

Last summer, for example, the group breached Manchester Airports Group (MAG), claiming to have stolen 86GB of data. That data turned out to contain far more genuine personally identifiable information (PII) than MAG copped to, according to reporting by BleepingComputer. And whereas some hackers exaggerate their winnings, this case was something of the opposite: That initial 86GB claim represented compressed data. The hackers clarified that the actual, uncompressed total stolen was 640GB.

Even if one were to completely ignore the hackers' account and take PingCAP's more limited assessment as the truth, it would still represent a potentially serious risk to customers.

Arguably the most acute dangers — more than the broad customer data, or the API keys if they are in fact protected — lie in the less obvious exfiltrated data. This includes Jira tickets, SQL histories, and places where organizations unknowingly leak internal data. For instance, when customers use their cloud-managed database services, they send commands to the vendors' servers. Those interactions can often carry corporate secrets or sensitive data of many other types.

"Vendors don't typically set out to store secrets. However, customers often pass them over to use features built for convenience, and the data can settle in places few people think of as credential stores," explains Crystal Morin, senior cybersecurity strategist at Sysdig.

Take PingCAP's SQL editor text and errors, for example, she says. "That's query history and error output, which is where secrets can accumulate when someone pastes a connection string to debug something on the fly," Morin adds. In FulcrumSec's name-and-shame post, for example, it highlighted exfiltrated SQL statements that listed in full view one medical clinic's roster of patients, and another's list of medical professionals.

Keeper Security chief information security officer Shane Barney seconds Morin's point. "The PingCAP incident illustrates a daily reality in enterprise security: Attackers do not need to compromise a customer's primary database directly if they can systematically harvest upstream credentials," he says. "In modern software-as-a-service (SaaS) ecosystems, customer metadata, API keys, and diagnostic query logs routinely seep into vendor environments through everyday operational telemetry. When service account credentials or administrative API tokens are stolen from a provider, that aggregated operational data transforms into a road map for exploitation."

Barney emphasizes the importance of cloud security hygiene — such as rotating vendor-facing API keys and eliminating hardcoded and long-lived secrets in developer workflows — and vetting one's managed service providers by demanding continuous third-party risk assessments and independent certifications and attestations such as SOC 2 Type II and ISO 27001.

Morin urges organizations to ask a few specific questions when vetting cloud providers. "Teams should seek to understand what customer-provided data the vendor retains and what its retention policy is. They should also ask whether they scan for secrets at ingest and redact what they find," she says. "Teams may also want to understand how service account credentials are handled, whether they’re short-lived, how they’re scoped, how often they rotate, and what detections fire on anomalous credential or account use."

And, she says, don't forget: "Inquire about breach notification, specifically the timeline and what triggers it."

Hydration is the process where React, running in the browser, attaches event handlers to server-rendered HTML and reconciles that static markup with the virtual DOM tree the client would have produced. For hydration to succeed, the HTML generated on the server must match, node by node, what the client renders on its initial pass. Any divergence triggers a hydration mismatch error.

The window object does not exist in Node.js. Because localStorage is a property of window, any direct access during server-side rendering fails. Developers hit one of two failure modes. The first is a hard crash: ReferenceError: localStorage is not defined, which kills the server render entirely. In the App Router, 'use client' components still pre-render on the server during next build, so this error fires during server pre-rendering, not in the browser. The second failure mode is subtler and more common: a developer wraps the access in a typeof window !== 'undefined' guard, which avoids the crash but causes the server to render with a default value (say, 'light') while the client reads a stored value (say, 'dark') from localStorage. React detects the difference and throws a hydration mismatch warning. This exact scenario has been reported repeatedly on Stack Overflow, often confusing developers who believe the guard should be sufficient.

The root cause is straightforward but easy to overlook: the server and client disagree on initial state.

Insuring an enterprise against attacks from rogue AI agents that attack the enterprise, or perhaps those created within the enterprise that breach the corporate environment and attack third parties, is uncommon coverage. AI coding tools can turn a plain-English description into a working web application in minutes. They can generate interfaces, connect APIs, create database schemas, and help developers move from an idea to a functional prototype faster than traditional workflows often allow.

But getting an application to run is not the same as making it production-ready.

These findings concern the applications examined, rather than every application developed with AI.

The lesson is not that vibe coding is inherently unsafe. It is that generating software quickly does not eliminate the engineering work required to protect data, verify behavior, and maintain reliability.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Consider a customer portal. An AI tool might generate a login page, a dashboard, and a database connection in a single session. The interface could look complete while the application still lacks proper authorization checks, reliable error handling, or protection against unauthorized data access.

These gaps become more consequential when an application stores personal information, processes payments, manages business records, or serves multiple customers.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Before generating substantial amounts of code, document:

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

For applications handling sensitive data, consider an independent security review before launch.

AI-generated applications often work well with expected inputs. Real users, however, submit incomplete forms, unexpected values, oversized files, malformed requests, and repeated actions.

Input validation and error handling help prevent these conditions from becoming application failures or security vulnerabilities.

Client-side validation improves the user experience, but it should not be the only line of defense. Requests can bypass browser validation entirely.

For file uploads, validate file types, enforce size limits, and store files using a design that prevents unauthorized access. Do not assume a filename or content type supplied by the browser is trustworthy.

A user-facing response might say, "We couldn't save your changes. Please try again." An internal log can record a request identifier, the relevant operation, and a sanitized diagnostic message.

Avoid exposing stack traces, database credentials, internal configuration, access tokens, or sensitive records in production responses.

Also test what happens when external APIs time out, database connections fail, or required environment variables are missing.

A production-ready application should fail predictably, protect sensitive information, and provide a clear path to recovery.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.

Asking an AI tool to generate tests is useful, but those tests must be reviewed. A test suite can pass while validating incorrect assumptions or ignoring the application's most important failure cases.

Start with critical workflows rather than trying to test every minor interface detail.

For an e-commerce application, these workflows might include account creation, product selection, checkout, payment confirmation, and order retrieval. For a business dashboard, they might include importing records, updating a customer, assigning permissions, and generating a report.

Pay particular attention to boundary conditions.

What happens when a form is submitted twice? When an API returns an unexpected response? When a database operation fails halfway through a workflow? When two users update the same record simultaneously?

These scenarios often reveal problems that a successful demonstration will not.

For applications that process transactions, test idempotency where appropriate so that retries do not unintentionally create duplicate payments, orders, or records.

Keep frameworks and libraries updated according to a deliberate maintenance process rather than automatically accepting every suggested upgrade.

Eight eMudhra intermediate Certificate Authority private keys are trivially recoverable from their public certificates. Any attacker can mint trusted TLS certificates for arbitrary domains. Browsers have already blocked these compromised intermediates through revocation mechanisms, but most non-browser runtimes — curl, Python, Node.js, Go, and Rust — still silently trust them. This affects any team operating server-side infrastructure, CI pipelines, or CLI tooling that makes outbound TLS connections. If your stack trusts the eMudhra chain, an attacker can forge certificates your code will accept without complaint.

This guide provides a diagnostic sequence: test every runtime in the stack against the compromised certificates, remediate by updating trust stores, and verify the fix sticks. The primary source for this disclosure is Scott Helme's detailed writeup.

In RSA key generation, you derive the private exponent d via the modular inverse of the public exponent e modulo λ(n) (the Carmichael totient of the modulus), where λ(n) depends on the prime factors of n. RSA's security depends entirely on d being large — typically hundreds of digits — making it computationally infeasible to derive from the public key alone.

eMudhra generated eight intermediate CA certificates with single-byte d values. Specific recovered values include d=4, d=56, and d=115, as documented in Scott Helme's disclosure post. These are not large numbers. They are recoverable from the public certificate in milliseconds. Anyone with access to the public certificate (which is, by definition, public) can reconstruct the private key and sign certificates that chain up to eMudhra's trusted root. That means arbitrary TLS certificates for any domain, indistinguishable from legitimate ones to any client that trusts the eMudhra chain.

An attacker holding one of these recovered keys can issue a certificate for any hostname, and any TLS client trusting the eMudhra intermediate will accept it without complaint.

Current browser versions already reject the compromised intermediates.

The problem lies everywhere else. Non-browser TLS clients skip revocation checks by default. curl does not check CRLs or OCSP unless explicitly configured to do so. Python's requests and urllib3 libraries rely on the certifi bundle and perform no revocation checking. Python's standard library urllib.request module uses the system SSL store, not certifi. Node.js's https module uses either a compiled-in root store or the system store depending on build configuration, with no active revocation. Go's crypto/tls loads system roots but does not perform revocation checks. Rust's rustls paired with webpki-roots uses a bundled Mozilla root set, while native-tls defers to the system store; neither checks revocation by default.

This creates a trust store gap. The system CA bundle on a Linux server, the certifi bundle shipped with Python, and the compiled-in roots in Node.js might all still contain the eMudhra intermediates or trust the root that chains to them. Without manual intervention, these runtimes remain vulnerable.
